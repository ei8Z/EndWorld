# NPC自主行为系统详细设计 V1.0

**所属项目**：末日求生 · AI叙事游戏 V3.0
**模块定位**：模拟层核心——管理NPC的自主行为、记忆与关系
**设计原则**：规则驱动为主，轻量AI增强为辅，分层管理
**依赖模块**：世界规则引擎（弱依赖——MVP阶段可用桩数据替代每日结算推送，仅区域事件响应§4.2和区域状态变更§7.1需要真实数据）


## 一、模块职责

NPC自主行为系统是V3.0模拟层的第二个核心组件。它负责让NPC在玩家不在场时也有自己的生活，让玩家再次相遇时能感受到时间流逝和关系变化。

**它做什么**：
- 管理NPC的时间表与日常节奏
- 驱动NPC基于需求做出行为选择
- 维护NPC对玩家的记忆与情感演变
- 处理NPC之间的互动
- 管理NPC的进入、离开与归来
- 向叙事层提供NPC当前状态

- **它不做什么**：
- 不生成叙事文本（由叙事Agent负责）
- 不模拟背景NPC的个体行为（背景NPC由世界规则引擎的群体标签管理）
- 不处理玩家行动的直接后果（由裁决Agent负责）


## 二、NPC三层结构

### 2.1 分层定义

**第一层：背景NPC（数十到数百个）**

不维护个体数据，只维护群体标签。由世界规则引擎管理。

群体标签结构：
- 所属场景/势力
- 大致人数
- 群体士气（0-100）
- 群体状态（如“最近伤亡3人”、“食物充足”）
- 对玩家的群体态度（欢迎/中立/警惕/敌意）

玩家与背景NPC互动时，若不满足提取条件，则只更新群体标签。若满足提取条件，则从中“提取”一个具体NPC进入第二层。

**第二层：接触NPC（预计10-30个）**

玩家直接交互过、且互动产生了“可被引用的后果”的NPC。

拥有完整的个体数据：性格标签、需求、记忆、时间表、好感度。

NPC行为系统的核心管理对象。所有接触NPC在每游戏日结算时更新状态。

**第三层：关键NPC（预计3-5个）**

与玩家有深度关系或对剧情有重大影响的NPC。

在第二层基础上增加：
- 更复杂的记忆结构（详细记忆队列扩展为10条）
- 情感演变轨迹（关系阶段追踪：陌生人→熟悉→信任→亲密/破裂）
- 自主决策能力（可选择使用轻量AI增强其行为真实感）
- 与其他关键NPC的关系网
- 
### 2.2 提取规则：从背景到接触

当玩家与背景NPC的互动产生“可被引用的后果”时，该NPC从背景层提取到接触层。

提取条件（满足任一即触发）：
- 好感度变化绝对值 ≥ 10
- 产生了承诺（NPC要求玩家做某事，或玩家要求NPC做某事）
- 发生了物品转移（给予或接受）
- NPC向玩家透露了独特信息（情报、秘密、个人背景）

不触发提取的情况：
- 礼节性对话（“你好”、“今天天气不错”）
- 单方面观察（“我看了一眼士兵们”）
- 无后果的群体交流（“我向哨卡的士兵们点了点头”）

触发提取时，系统即时创建一个接触NPC实例，赋予基础属性：
- 从群体标签中推断性格标签（随机分配或根据场景预设）
- 战斗角色根据其身份自动判定（见§3.1基础信息）
- 初始好感度 = 群体态度基准值 + 本次互动变化值
  - 群体态度基准值映射：欢迎→+30 / 中立→0 / 警惕→-20 / 敌意→-50（好感度范围-100~+100）
  - 本次互动变化值：裁决Agent在判定互动时，以群体态度基准值为虚拟基准线计算出的变化量
  - 若该变化值的绝对值 ≥ 10，触发提取；提取后的初始好感度 = 基准值 + 变化值
- 初始需求随机分配：基础值 = 30 + random(0, 40)，再根据当前势力/区域状态修正（势力食物短缺→食物需求+20；区域高威胁→安全需求+20），上限100
- 默认时间表基于其身份和所在场景
- 记忆队列初始化为空，第一条记忆记录本次交互

**提取衰减规则**：
提取条件的权重随时间衰减，防止过时的互动永久占用接触NPC配额：
- 权重衰减函数：每日衰减 1/23（从第7天权重1.0线性降至第30天权重0.0），即 `weight = max(0, 1.0 - (daysSinceLastInteraction - 7) / 23)`
- 连续30天无互动 → 触发降级检查：若该NPC非关键NPC且无未完成的承诺，降级为背景NPC
- 降级时，NPC的结构化数据存档（保留好感度和记忆摘要），在群体标签中更新"对玩家态度"

**降级NPC的再提取规则**：
当已降级的NPC因新的互动再次满足提取条件时：
- 若距降级时间 < 90游戏日：从存档中恢复好感度和记忆摘要（记忆摘要中的远期摘要保留，详细记忆清空——降级期间无个体记忆记录）。恢复后的好感度 = 存档好感度 × max(0.3, 1.0 - 距降级天数/90)。此衰减确保"被遗忘"的NPC不会以完整好感度突然重现
- 若距降级时间 ≥ 90游戏日：视为全新NPC，从群体态度基准值开始，不恢复存档。叙事Agent在叙事中不再提示"你似乎认识这个人"
- 再提取后的NPC重新分配时间表和初始需求（与全新提取相同），但性格标签从存档恢复

**新提取NPC的当日结算参与规则**：
- 若提取时间距下次每日结算 > 6游戏小时：参与当日结算（正常更新需求、互动判定）
- 若提取时间距下次每日结算 ≤ 6游戏小时：跳过当日需求更新和互动判定（仅执行时间表布置），从次日结算开始完整参与
- 此规则防止新提取NPC在属性尚未稳定的状态下参与互动判定产生不合逻辑的行为

### 2.3 关键NPC的判定标准

以下条件满足任一，接触NPC升级为关键NPC：
- 好感度达到80以上或降至-50以下
- 与玩家互动超过10次
- 在剧情管理器中注册为关键剧情角色
- 玩家主动标记（如选择“这是我可以信任的人”）


## 三、NPC核心属性

### 3.1 基础信息

- NPC ID：唯一标识
- 姓名：显示文本
- 身份：如”哨卡士兵”、”流浪商人”、”势力领袖”
- 战斗角色：枚举（战斗人员/非战斗人员/领袖）
  - 战斗人员（哨兵、士兵、守卫）：计入势力兵力，战斗战损概率×1.0
  - 非战斗人员（平民、商人、工匠）：不计入势力兵力，战斗战损概率×0.3
  - 领袖（势力领袖、关键决策者）：计入势力兵力，死亡判定前触发AI评估
- 所在场景/势力：当前位置或所属势力
- 性格标签：如”谨慎”、”慷慨”、”多疑”、”勇敢”、”自私”
- 状态标签：如”受伤”、”饥饿”、”士气低落”、”心怀感激”

> **战斗角色分布与势力武装率的一致性**：势力内接触NPC的战斗角色分布应大致符合该势力的武装率（来自世界规则引擎§2.2）。至少 floor(势力武装率 × 该势力接触NPC数) 个接触NPC应为战斗人员。新提取NPC的战斗角色优先填补缺口（若势力战斗人员比例低于武装率，新NPC优先设为战斗人员）。此约束为弱校验——允许暂时偏离，但每日结算时输出偏差警告日志。

### 3.1.1 势力-区域-NPC 关联模型

为避免三份文档中势力/区域/NPC的映射关系模糊，明确定义三者层级：

```
世界规则引擎管理                      NPC行为系统管理
┌─────────────────┐                ┌─────────────────┐
│ 势力(Faction)    │──控制────────→│ 区域(Region)     │
│ · 资源池         │                │ · 威胁等级       │
│ · 兵力/士气      │                │ · 资源丰度       │
│ · 控制区域列表   │                │ · 包含多个场景    │
└─────────────────┘                └────────┬────────┘
                                            │ 包含
                                            ▼
                                ┌─────────────────┐
                                │ 场景(Location)   │
                                │ · NPC可位于此    │
                                └────────┬────────┘
                                         │ 位于
                                         ▼
                                ┌─────────────────┐
                                │ NPC             │
                                │ · 所属势力=所在  │
                                │   区域的控制势力  │
                                │   (默认，可覆盖) │
                                └─────────────────┘
```

**关联规则**：
- 一个 Region 包含多个 Location（场景）。NPC 位于某个 Location
- NPC 的”所属势力”默认为其所在 Region 的 ControlFaction，但可被覆盖（如流浪商人无势力归属）
- NPC 跨 Region 移动时：NPC行为系统在移动决策生效时立即发送 `NpcMovementNotification`（见世界规则引擎§6.1），世界规则引擎据此更新：原势力人口-1，目标 Region 势力人口+1，若NPC更换势力归属则同步更新关系矩阵
- 背景NPC的群体标签绑定在 Region 级别，由世界规则引擎管理

### 3.2 时间表

每个接触NPC维护一个精确的时间段-位置映射：

**时间表结构**：时间段标签 → 位置ID

**预设时间段**：
- 清晨（5:00-8:00）
- 上午（8:00-12:00）
- 下午（12:00-17:00）
- 傍晚（17:00-20:00）
- 夜晚（20:00-5:00）

**时间表生成**：
- NPC实例化时根据其身份自动生成默认时间表
- 时间表可因事件临时覆盖（见第五节）

**位置来源的两种机制**：

NPC的当前位置由两种机制驱动，优先级不同：

| 优先级 | 来源 | 驱动方式 | 更新频率 |
|--------|------|----------|----------|
| 1（优先） | 行为决策覆盖 | 需求驱动的紧急行为（饥饿→抢粮、安全→逃跑） | 每日结算时判定 |
| 2（默认） | 时间表查表 | 跟随GameClock实时查表（非决策，无需判定） | 随GameClock实时变化 |

**行为决策覆盖的时长规则**：
- 生存需求覆盖（饥饿/口渴/医疗）→ 持续到需求满足或下次每日结算（以先到者为准）
- 安全需求覆盖（威胁逃跑/躲避）→ 持续到威胁解除
- 覆盖解除后，NPC回归当前时段的时间表位置，记录位置恢复事件

**时间表异常处理**：
NPC出现在非预期位置时，视为异常，需要触发解释机制：
- 系统生成一个简短的结构化说明（如”听到枪声前来查看”、”被上级临时调派”）
- 若该异常对剧情有重大影响，升级为轻量AI评估
- 异常解除后，时间表恢复正常

### 3.3 需求系统

每个NPC维护一组需求，每个需求有紧迫度评分（0-100）。

> **结算频率**：需求紧迫度在每游戏日结算时一次性推进24小时（与V3.0总纲§3.5对齐）。行为决策在每日结算时统一判定，消除"需求触发"与"行为响应"之间的时间差。

**需求类型及基础权重**：

| 需求类型 | 权重 | 紧迫度日增量 | 等效小时速率（仅供参考） |
|----------|------|-------------|------------------------|
| 生存-食物 | 最高 | +120/游戏日 | （等效+5/小时） |
| 生存-饮水 | 最高 | +192/游戏日 | （等效+8/小时） |
| 生存-医疗 | 最高 | 受伤时+360/游戏日 | （等效+15/小时） |
| 安全 | 高 | 区域威胁>50时+240/游戏日 | （等效+10/小时） |
| 社交 | 中 | 生存和安全满足时+72/游戏日 | （等效+3/小时） |
| 自我实现 | 低 | 其他需求满足时+24/游戏日 | （等效+1/小时） |

> **与玩家消耗速率差异说明**：NPC的需求增长速度约为玩家的1.7~2倍。设计意图——NPC没有玩家的"背包管理"优势，物资获取效率更低，在末日环境中面临更严峻的生存压力。这一差异是有意为之，用于驱动NPC主动向玩家求助或交易。

**需求驱动行为**：
NPC的当前行为倾向由紧迫度最高的需求决定：
- 生存需求最高 → 寻求交易、求助、自行搜索物资
- 安全需求最高 → 加强防御、减少外出、依赖信任的人
- 社交需求最高 → 主动交谈、寻求陪伴、表达情感
- 自我实现最高 → 尝试领导、主动探索、帮助他人

**需求满足**：
- 食物需求：进食后归零，下一次每日结算时跳过食物需求的推进（等效锁死24游戏小时）。若进食发生在两次结算之间，以最近一次结算为基准计算
- 饮水需求：饮水后归零
- 医疗需求：接受治疗后归零。治疗来源优先级：
  1. 玩家主动治疗（玩家使用医疗物资治疗该NPC）
  2. 所在势力自动分配——仅在该势力医疗物资 ≥ 20 单位时触发，消耗 20 单位势力医疗物资（≈ 1.0 个标准医疗包，见世界规则引擎§3.1换算表伤病治疗行）可消除 1 个 NPC 的医疗需求（治愈一次）
  3. 若无以上来源，NPC保持受伤状态，医疗需求持续增长

势力自动分配的治疗在每日结算时统一执行，与NPC需求更新同步：
  1. 收集所有状态标签为"受伤"的该势力接触NPC
  2. 按分诊优先级排序（领袖 > 战斗人员 > 非战斗人员）
  3. 依次消耗势力医疗物资进行治疗，直至医疗物资耗尽或无更多受伤NPC
  4. 未被治疗的NPC保持受伤状态，等待次日结算或玩家治疗

势力自动分配的治疗优先级（体现末日环境下的残酷分诊）：
  1. 领袖（势力领袖、关键决策者）→ 优先确保指挥链
  2. 战斗人员（哨兵、士兵、守卫）→ 保障战斗力
  3. 非战斗人员（平民、商人、工匠）→ 在前两类满足后分配剩余医疗物资
势力医疗物资耗尽时，所有NPC等待玩家提供治疗或自然恶化

**日常防疫消耗与伤病治疗的区分**：
- 日常防疫（预防性用药、消毒、绷带更换）：每人每日消耗 1 单位，已包含在宏观公式"人口 × 人均日消耗"中（见世界规则引擎§3.1），不单独扣费
- 伤病治疗（手术、伤口缝合、感染处理）：每次消耗 20 单位（≈ 1 个标准医疗包），从势力资源池额外扣除，由每日结算统一分配
- 玩家使用自己的医疗物资治疗 NPC 时，消耗玩家背包中的 1 个完整医疗包——与势力治疗的 20 单位成本等价（一致性保证：无论玩家自己治疗还是委托势力治疗，治愈一次伤病的代价相同）
- 势力医疗物资池同时承担日常防疫和伤病治疗两类消耗——在资源紧张时，势力可能面临"维持日常防疫"与"治愈现有伤员"之间的分配决策（由势力领袖性格决定优先级：谨慎保守→优先日常防疫，激进扩张→优先伤病治疗）
- 安全需求：区域威胁下降后逐步降低
- 社交需求：有意义的社交互动后归零
- 自我实现：完成个人目标后归零

**需求过载致死**：若NPC的食物或饮水需求连续3个每日结算均处于100（饱和），在第3次结算时触发死亡判定——NPC因饥饿或脱水而死亡。触发死亡判定的同时，NPC行为系统立即向世界规则引擎发送 PopulationChangeNotification（见§4.4），同步更新势力人口统计。

**紧迫度触顶与溢出规则**：
- 每日结算推进后，紧迫度上限为100（超出部分不保留，不溢出）
- 多个NPC同需求触顶时，按需求权重（食物/饮水/医疗 > 安全 > 社交 > 自我实现）决定优先级
- 同需求同权重时，按NPC与玩家的好感度（负优先——敌人更危险）、战斗角色（战斗人员优先）排序
- 大多数NPC的大多数时间都处于需求饱和状态——这不是bug，是设计意图：末日世界本就稀缺，NPC总是在"需要什么"的状态中

### 3.4 记忆系统

**记忆队列结构**：最近N条详细记忆 + 远期摘要

| NPC层级 | 详细记忆队列容量 | 压缩为摘要的时机          |
|---------|-----------------|-------------------|
| 接触NPC | 6条 | 第7条记忆加入时，最旧的一条压缩  |
| 关键NPC | 10条 | 第11条记忆加入时，最旧的一条压缩 |

**详细记忆条目**：
- 时间戳
- 地点
- 交互摘要（一句话描述）
- 情感变化（好感度变化值+情感倾向标签）

**环境记忆（Environment Memory）**：

详细记忆的三种来源（玩家交互、NPC间互动社交快照、MemOS文本）覆盖了人际交互，但宏观事件——势力覆灭、尸潮过境、同伴阵亡——同样需要进入NPC的记忆，否则NPC在经历巨变后面对玩家询问时只能检索到日常琐事，叙事失真。

当以下宏观事件被推送至NPC时，系统自动在NPC的详细记忆队列中插入一条环境记忆：

| 触发条件 | 记忆格式 | 示例 |
|----------|----------|------|
| NPC响应区域事件（§4.2 事件→行为映射表中的事件类型） | `[时间] [区域事件名称] 发生，我[行为]` | `[Day 8 上午] 尸潮接近 发生，我逃往避难所` |
| 收到 CasualtyReport 且伤亡名单中包含与该NPC好感度绝对值≥20的其他NPC | `[时间] [姓名] 在 [战斗/事件] 中 [死亡/重伤]` | `[Day 12] 李队长 在 灰烬匪帮袭击 中 阵亡` |
| 所属势力发生状态变更（食物短缺、士气下降、势力迁移、势力覆灭） | `[时间] 势力 [状态变更描述]` | `[Day 15] 势力 红松幸存者营地 因饥荒宣告解散` |

环境记忆计入详细记忆队列（会触发正常压缩规则），与玩家交互记忆和社交快照共用队列容量。
仅在以下情况跳过环境记忆插入：与前一条记忆的时间差 < 1游戏小时 且 事件类型相同（防止事件传播产生连续重复记录）；该NPC因 SimulationFreeze 处于冻结状态时。

> 设计意图：环境记忆确保NPC在面对宏观变故时拥有可被叙事Agent检索的因果链——当玩家询问”发生了什么”时，NPC的记忆中有具体事件而非仅数值变化。这与社交快照（§4.3）的设计意图一致——记忆应该是”故事可读”的，而非仅数值可查。

**远期摘要**：
由被压缩的详细记忆合并而来。合并算法为客户端模板拼接（非AI驱动，零延迟）：新摘要 = 旧远期摘要 + “；” + 被压缩记忆的交互摘要（若旧摘要为空则直接使用交互摘要）。当摘要长度超过150字时，保留最近的150字并追加”...”。环境记忆在压缩时与交互记忆等同处理——多条环境记忆可被合并为一条远期环境摘要（如”我的家园被战火摧毁，同伴们陆续死去”）。远期摘要无需AI驱动（成本考量），其精度足以让裁决Agent和叙事Agent了解NPC的历史脉络。

**远景记忆保护**（Remote Memory Preservation）：
当以下任一条件满足时，触发记忆保护：
1. NPC的状态为”被俘”、”失踪”或”玩家连续30天未访问该NPC所在Region”
2. **高事件密度触发**：NPC在1个游戏日内收到 ≥ 3 条环境记忆（来自 CasualtyReport、势力状态变更、区域事件响应），表明当前处于战争/灾难/崩溃等极端状态

保护措施：
1. 该NPC的记忆压缩频率降为正常的1/3（如接触NPC每24条新记忆才压缩1条，关键NPC每30条才压缩1条。计算公式：`压缩间隔 = 队列容量 × 4（接触NPC）/ × 3（关键NPC）`）
2. 压缩时优先保留标记为”与玩家相关”的记忆条目（玩家参与的记忆不压缩，或最后被压缩）。在高事件密度触发时，”与玩家相关”的记忆当日绝对不压缩
3. 若详细记忆队列中所有条目均为非玩家相关，至少保留1条与玩家相关的最早远期摘要不被合并
4. NPC被玩家重新接触（解救/重逢/高事件密度结束后首次互动）时，记忆压缩频率恢复正常

**记忆检索优先级**：
1. 首先检索详细记忆（匹配当前情境）
2. 其次检索远期摘要（补充背景）
3. 最后检索MemOS中的交互文本（补充叙事细节，非结构化）

### 3.5 情感系统

**好感度**：-100到+100

> **与现有代码的兼容说明**：当前 V2.x 代码中 `NpcRelation.affinity` 使用 0~100 范围（百分比语义）。V2.6 实现时需做数据迁移：`newAffinity = (oldAffinity - 50) * 2`，将现有存档中的好感度映射到新范围。同步更新 `NpcUpdate.affinityDelta` 的语义文档。

**关系阶段**：

| 好感度范围 | 关系阶段 | 说明 |
|-----------|---------|------|
| -100 ~ -60 | 仇恨 | NPC主动与玩家为敌 |
| -60 ~ -20 | 敌意 | NPC不信任玩家，可能设防 |
| -20 ~ +20 | 中立/陌生 | 初识或冷淡 |
| +20 ~ +50 | 熟悉 | NPC认识并接受玩家 |
| +50 ~ +80 | 信任 | NPC愿意透露个人信息，接受委托 |
| +80 ~ +100 | 亲密 | NPC主动提供帮助，可托付重要任务 |

**阶段跨越**：
当好感度跨越关系阶段边界时，触发特殊处理：
- 记录跨越事件（用于叙事Agent生成”关系质变”叙事）
- 更新NPC的行为模式（如从”警惕”变为”开放”）
- 若跨越涉及关键NPC，触发轻量AI评估

**生存状态突变**（与好感度跨越并列的AI触发条件）：
当NPC发生以下生存状态突变时，触发特殊处理：
- 重伤（因战斗、灾难或需求长期不满足）→ AI评估NPC行为模式的转变
- 失去庇护所（所在Location被摧毁或废弃）→ AI评估迁移方向和生存策略
- 失去重要的人（同场景内好感度最高的NPC死亡）→ AI评估情感反应和行为变化

**AI评估的增强输入**（针对关键NPC的关系质变）：
当触发好感度阶段跨越或生存状态突变的AI评估时，除标准上下文外，额外包含：
1. 该NPC的全部详细记忆（当前队列中的所有条目，不压缩）
2. 远期摘要
3. 从MemOS检索与该NPC相关的历史交互片段（若可用，最多3条）
4. 好感度变化的完整时间序列（每个关键变化节点的时间、原因、变化值）

这些增强输入仅供AI评估使用，不改变记忆系统的正常压缩行为。

**情感倾向标签**：附加情感描述，如”感激”、”失望”、”亏欠”、”敬佩”、”恐惧”。一个NPC可同时有多个情感倾向标签，但只展示最强的2-3个。


## 四、NPC自主行为机制

### 4.1 日常行为驱动

NPC的日常行为由时间表+需求共同驱动。

**行为优先级**：
1. 生存需求（饥饿/口渴/受伤）→ 覆盖时间表，优先满足
2. 安全需求（区域威胁骤升）→ 覆盖时间表，寻找安全
3. 时间表常规行为
4. 社交/自我实现需求（在前三项满足后浮现）

**需求中断规则**：
当NPC在执行时间表行为时，若更高优先级需求触发：
- 当前行为终止
- NPC转向满足紧急需求
- 记录中断事件（供叙事Agent使用）

**行为决策的时间表兼容规则**：
- 行为决策在每日结算时判定，但决策的"执行"可能延迟到下一个合适的时间段
- 若决策行为（如进食）对应的目标位置在当前时间段不可用（如深夜食堂关闭），行为标记为"排队等待"，在目标位置的第一个可用时间段执行
- 紧急生存需求（食物/水连续3日触顶即将触发需求过载致死，或安全需求因即时推送触发）无视时间段限制，立即执行

**加速模式下的批量追赶**：
当玩家进入加速模式时，NPC行为系统不逐小时结算。加速结束时一次性批量追赶整个时间段的推进（时间表、需求、互动、离开判定）。世界叙事Agent的摘要流中应包含显著NPC行为（死亡、离开、关系阶段跨越）。详见V3.0总纲§3.3。

**批量追赶的需求过载致死判定**：
加速期间的批量追赶不能仅检查终态需求值——必须逐游戏日模拟需求推进以正确判定"连续3日饱和"：

```
对每个接触NPC:
  currentUrgency = 加速开始时的需求值
  consecutiveSaturatedDays = 加速开始时的连续饱和天数（继承自上次每日结算的记录）
  
  for day in 1..加速跨越的游戏日数:
    currentUrgency = min(100, currentUrgency + 日增量)
    if currentUrgency >= 100:
      consecutiveSaturatedDays += 1
      if consecutiveSaturatedDays >= 3:
        触发需求过载致死 → 标记NPC死亡，记录死亡游戏日，跳出循环
    else:
      consecutiveSaturatedDays = 0
  
  若未死亡: 最终需求值 = currentUrgency，持久化最终值和连续饱和天数
```

此规则确保批量追赶下的致死判定与逐日结算等价——不会因批量处理而漏判或误判死亡。

### 4.2 区域事件响应

当世界规则引擎推送区域状态变更时，NPC行为系统执行”中断检查”。

**区域事件响应的作用范围**：
- **接触NPC**：个体级别执行中断检查（按下表事件→行为映射）
- **背景NPC**：群体级别响应——更新该Region的群体标签（如”因尸潮逼近，群体状态变为'恐慌中'”、群体士气-20）。群体标签的更新由世界规则引擎在每日结算时直接处理，NPC行为系统仅处理接触NPC的个体响应
- 若事件直接影响某个Location，该Location内的接触NPC优先响应（中断等级+1）

**事件→行为映射表**：

| 区域事件 | NPC默认行为 |
|----------|------------|
| 尸潮接近 | 前往安全区域或避难所 |
| 势力冲突 | 躲避或参战（取决于NPC身份和性格） |
| 资源发现 | 前往探索（若NPC有此需求） |
| 天气骤变 | 寻找庇护所 |
| 势力撤离 | 跟随撤离或留下（取决于NPC对势力的忠诚度） |

**性格对响应的影响**：
- 勇敢型：冲突时倾向参战，灾难时倾向帮助他人
- 谨慎型：冲突时倾向躲避，灾难时优先自保
- 自私型：资源发现时抢先行动，灾难时不帮助他人
- 忠诚型：跟随势力决定，维护势力利益

### 4.3 NPC间互动

**结算时机**：
- 每游戏日结束时（与V3.0总纲§3.5对齐）
- 玩家从一个Region移动到另一个Region时：触发目标Region内NPC的分阶段异步互动预演（见V3.0总纲§3.5）。预演规则：
  - 当玩家距目标Region边界<1个Location时（或导航目标明确为该Region时），后台分批启动预演
  - 仅涉及同Location内的NPC对（跨Location不触发预演）
  - 单批次上限5对NPC，批次间隔≥100ms，总超时3秒（超过则放弃剩余NPC对，等待每日结算）
  - 仅判定非致死互动——死亡、离开、关系破裂等重大结果推迟到下一次每日结算
  - 预演前对参与NPC执行轻量需求追赶：
    - 追赶比例 = (当前GameClock总分钟数 - 上次每日结算时的总分钟数) / 1440
    - 追赶后的需求值 = 当前存储需求值 + 日增量 × 追赶比例
    - 追赶后的需求值同时写入NPC持久状态（追赶量 ≤ 1天，不影响每日结算的正式写入，且确保互动判定所用的需求值与持久状态一致）
    - 若追赶比例 < 1/24（不足1游戏小时），跳过追赶
  - 预演结果在玩家实际跨越边界时应用；若玩家取消移动，丢弃缓冲区
- 世界规则引擎推送区域状态变更时（分双通道处理，见下）

**区域状态变更的双通道推送**：
- **即时推送通道**：玩家行动触发世界规则引擎阈值跨越时，规则引擎立即推送变更给NPC系统，NPC立即执行中断检查
- **每日推送通道**：常规每日结算结果，与每日结算合并处理

**互动判定**：
在结算点，检查NPC对之间的互动条件，按空间距离分为两级：

**同场景（Location）内的NPC对**：适用全部互动类型（日常社交、资源分享、争执、合作、关系破裂）。这是互动判定的主要范围。

**同势力但不同场景的NPC对**：仅触发以下有限互动（不要求物理接触）：
- 势力内部秩序变化——群体士气在同势力NPC之间传播（士气±5/日）
- 势力领袖决策影响——自上而下的指令传播（领袖的行为决策覆盖下属的目标倾向）
- 同势力NPC对的好感度不直接调整（缺乏面对面互动）

**互动类型与触发条件**：

| 互动类型 | 触发条件 | 结果 |
|----------|----------|------|
| 日常社交 | 任意两个NPC同场景，概率50% | 好感度微调（±5） |
| 资源分享 | 一方有需求，另一方有资源 | 需求方需求降低，给予方好感度+10 |
| 争执 | 双方需求冲突（如同一资源） | 双方好感度-10，可能影响群体士气 |
| 合作 | 共同面对威胁或共同目标 | 双方好感度+10，合作成果体现 |
| 关系破裂 | 好感度持续下降跨过阈值 | NPC可能离开场景或势力 |

**互动粒度**：
常规互动只记录结果（数值变更），不模拟过程。以下罕见情况触发轻量AI评估：
- 涉及关键NPC
- 互动可能导致NPC死亡或永久离开
- 互动涉及道德困境（背叛、牺牲、重大承诺）
- 互动可能显著改变势力内部结构

**NPC间互动的社交快照**：
即使是常规互动（不触发AI），也应在双方记忆队列中插入一条简化的社交快照：
- 格式：[时间] 与 [对方NPC姓名] 发生 [互动类型]，原因：[触发条件摘要]
- 示例：[Day 5 下午] 与 李队长 发生 争执，原因：食物资源竞争
- 社交快照计入详细记忆队列（会触发压缩规则），与玩家交互记忆共用队列容量
- 仅在以下情况跳过社交快照：互动类型为"日常社交"且好感度变化 < |5|

社交快照确保NPC的情感变化有叙事支撑——当玩家询问NPC A对NPC B的看法时，叙事Agent可以从记忆中检索到具体原因而非仅看到好感度数值。

### 4.4 NPC的离开与归来

**离开判定**：每游戏日结算时，基于以下条件判定：

| 离开原因 | 触发条件 | 结果 |
|----------|----------|------|
| 死亡 | NPC受伤且未获得医疗（医疗需求连续3个每日结算处于100，见§3.3），或所在场景遭遇灾难，或收到世界规则引擎的 CasualtyReport 中标记该NPC为死亡（战斗伤亡），或核心生存需求（食物/水）连续3游戏日处于100饱和状态（需求过载致死，见§3.3） | NPC被标记为已死亡 |
| 迁移 | 所属势力撤离，或区域威胁等级过高 | NPC迁移至新场景/势力 |
| 外出探索 | NPC需求驱使其外出（如寻找物资） | NPC暂时离开，预期归来时间≤3游戏日 |
| 关系破裂 | 对玩家好感度跨过仇恨阈值，或与势力内多数人不和 | NPC永久离开，可能加入敌对势力 |
| 被驱逐 | 违反势力规则，或被势力领袖判定为威胁 | NPC被标记为被驱逐 |
| 玩家邀请同行 | 玩家主动邀请NPC一同前往其他Region | NPC临时跟随玩家移动，所属势力保持不变（除非玩家邀请其加入新势力）。同行期间NPC需求由玩家背包或沿途势力资源满足。玩家可在任意时刻解除同行关系。若玩家死亡，NPC触发独立迁移判定 |

**势力覆灭时的迁移判定**：
当势力兵力降至0（世界规则引擎§3.3）或势力解散（§3.2）时，该势力的所有接触NPC触发迁移判定。迁移判定应接收同一结算周期内场景3/4的AI评估结果作为上下文：
- 若NPC在此次结算中已经历场景3（战斗死亡判定）→ 迁移判定基于场景3的输出（kill/spare/severe_injury）而非独立重判
- 若NPC在此次结算中已经历场景4（生存状态突变）→ 迁移判定使用场景4的行为模式结论（retreat_to_safety/seek_help等）作为迁移方向的依据
- 若NPC未经历场景3/4 → 独立判定迁移方向
此规则确保同一结算周期内的多个判定路径信息一致，避免"刚被救下又因势力覆灭而死"的逻辑矛盾。

**归来机制**：
当NPC标记为”外出探索”且归来时间到达时：
- NPC重新出现在原场景
- 更新状态（探索结果：可能带回物资、受伤、或空手而归）
- 记录归来事件

**外出超时处理**：
- 最大外出时长 = 3游戏日
- 超时未归 → 标记为”失踪”，触发轻量AI评估判定结果：死亡/被俘/加入其他势力/重伤返回
- 失踪NPC的接触层数据保留7天（等待可能的AI评估结果），超期则降级为背景NPC

**死亡路径优先级**：

NPC 死亡有四条独立路径，可能在同一日结算中同时触发。多条路径同时触发时按以下优先级裁决：

| 优先级 | 死亡路径 | 叙事价值 | 说明 |
|--------|----------|----------|------|
| 1 | CasualtyReport 战斗死亡 | 最高——有明确的因果关系和戏剧性 | 世界规则引擎推送 |
| 2 | 环境致死 | 高——外部事件驱动（灾难、尸潮） | §4.4 环境条件触发 |
| 3 | 伤病恶化致死 | 中——渐进式悲剧（医疗需求过载） | §4.4 医疗需求连续3日触顶 |
| 4 | 需求过载致死 | 反映资源危机（饥饿/口渴慢性死亡） | §4.4 食物/水需求连续3日触顶 |

当高优先级路径触发时，低优先级路径的死亡判定自动取消（NPC 不会同时死于两个原因）。
只有最高优先级的原因被写入环境记忆（见 §3.4）和推送至叙事Agent。

**对叙事层的影响**：
玩家到达场景时，系统提供该场景应有的NPC列表及状态摘要：
- 谁在场
- 谁不在了（及原因）
- 谁是新的（背景NPC被提取或外来NPC）

**死亡判定与CasualtyReport的关系**：
NPC死亡有四条独立路径（详见上方"死亡路径优先级"表），可能在同一结算中同时触发——优先级表定义了裁决规则。
例如：NPC在战斗中断腿→CasualtyReport标记为newInjury→伤情在后续结算中恶化为死亡（此时路径3"伤病恶化"覆盖路径1的newInjury标记，而非同时触发两条死亡判定）。

**非战斗死亡与降级的人口同步**：

接触NPC因非战斗原因死亡（需求过载致死、伤病恶化致死、环境致死）时，
NPC行为系统立即向世界规则引擎发送 PopulationChangeNotification：

```
PopulationChangeNotification {
  npcId: String
  factionId: FactionId
  change: -1
  reason: "starvation" | "dehydration" | "injury_deterioration" | "environment"
  timestamp: GameDateTime
}
```

接触NPC降级为背景NPC时（提取衰减 §2.2 或数量上限降级 §8），发送：
```
{ npcId, factionId, change: 0, reason: "demotion_to_background" }
```
——人口总数不变，但世界规则引擎需同步更新其内部子计数（背景NPC人口+1，接触NPC数量-1）。

世界规则引擎收到后更新势力人口统计和宏观公式中的 `macroPopulation` 参数。
此通知与 CasualtyReport（战斗死亡）和 NpcMovementNotification（迁移）共同构成
宏观-微观人口同步的完整闭环。


## 五、时间表中断处理

### 5.1 中断类型

**临时中断**：因事件临时改变位置，事件结束后恢复时间表。
- 触发源：区域事件、玩家互动、NPC间互动
- 持续时间：事件持续期间
- 处理：记录当前时间表位置，事件结束后恢复

**永久调整**：因状态质变导致时间表长期变更。
- 触发源：需求长期得不到满足、势力归属变更、角色身份变化
- 处理：生成新时间表，旧时间表存档

### 5.2 中断时的解释机制

当NPC出现在非预期位置时，系统为该异常生成解释：

**轻度异常**（临时中断，持续时间<1游戏日）：
- 系统自动生成简短的结构化说明（如“因事件X临时在此”）
- 不需要AI调用
- 提供给裁决Agent，用于叙事中的一句话解释

**重度异常**（永久调整，或异常原因复杂）：
- 触发轻量AI评估
- AI输出异常的原因和影响
- 提供给叙事Agent，用于生成更详细的叙事


## 六、与MemOS的协作

MemOS 是 V3.0 的记忆基础设施，提供两个核心能力：(1) 存储玩家-NPC 交互的完整叙事文本（非结构化），(2) 通过云端 `memos-extractor-0.6b` API（`/extract/memory`）将对话文本自动抽取为结构化记忆条目。

### 6.1 存储职责划分

| 数据类型 | 存储位置 | 说明 |
|----------|----------|------|
| NPC结构化数据 | NPC行为系统（本地数据库） | 时间表、需求、好感度、记忆摘要、关系网。权威数据源。 |
| 玩家-NPC交互文本 | MemOS | 交互时的叙事片段。非结构化补充记忆。 |
| NPC间互动结果 | NPC行为系统（本地数据库） | 纯结构化数据，不入MemOS。 |

### 6.2 写入策略

玩家-NPC交互在以下任一条件满足时写入 MemOS：
- 涉及关键NPC
- 好感度变化绝对值 ≥ 10
- 产生了承诺（NPC要求玩家做某事，或反之）
- 发生了物品转移（给予或接受）
- NPC向玩家透露了独特信息（情报、秘密、个人背景）

**写入内容**：叙事Agent为该次交互生成的完整叙事文本（即 GameResponse.header 的完整内容）。

**写入时机**：交互完成后异步写入，不阻塞玩家下一轮行动。写入失败不影响游戏流程——MemOS 是补充存储，NPC 结构化数据始终是权威。

### 6.3 检索协调

当玩家与NPC再次相遇时：
1. NPC行为系统提供该NPC的精确结构化状态（好感度、当前需求、最近记忆摘要、关系阶段）
2. MemOS检索与该NPC相关的历史叙事片段：按时间倒序返回最近 5 条，每条限 200 tokens。若NPC记忆队列中的远期摘要已覆盖某条MemOS记录的时间段，则以远期摘要为准（NPC结构化记忆为权威）
3. 裁决Agent和叙事Agent接收两者结合的信息

**"环境线索"模式**：当远期摘要完全无某时间段的覆盖时，MemOS 记录不再仅以"不确定的模糊记忆"形式提供。若 `memos-extractor-0.6b` 已从该段对话中抽取了结构化记忆条目（见 §6.4），这些条目与 MemOS 原始文本一起，以"环境线索"形式提供给叙事Agent——叙事Agent 可以通过场景中的物理痕迹、其他NPC的转述、或玩家的内心闪回等方式自然地呈现这些信息，而非仅依赖"你似乎想起来..."的不确定性表述。

**优势**：
- NPC的客观状态精确可查（不受记忆噪声影响）
- MemOS的叙事检索保留交互的文学细节
- 通过 extractor 的结构化抽取，MemOS 文本与 NPC 结构化记忆之间不再是"不可逾越的墙"

### 6.4 每日记忆抽取（memos-extractor-0.6b 集成）

每日结算时，NPC行为系统批量调用 MemOS 的 `/extract/memory` API，将当日积累的玩家-NPC交互文本自动转化为结构化记忆条目。

**API 参数**（参见 MemOS 记忆抽取文档）：
```
POST /extract/memory
输入: { messages: [{role, content}, ...], extraction_types: ["memory", "preference"] }
输出: {
  memory_detail_list: [{memory_key, memory_value, memory_type, tags}],
  preference_detail_list: [{preference, reasoning, preference_type}]
}
限制: 8,000 tokens 输入上限，同步模式
```

**调用流程**：
1. 每日结算时，收集当日所有满足写入条件（§6.2）的玩家-NPC交互文本
2. 按 NPC 分组，每组交互文本作为 `messages` 数组（8,000 tokens 约容纳15-20条交互）
3. 调用 `/extract/memory`，抽取 `memory` 和 `preference` 两种类型
4. 抽取结果处理：
   - `memory_detail_list` 条目 → 注入对应NPC的记忆队列（作为新的详细记忆，条目格式：`时间戳=[交互时间] + 地点=[交互场景] + 交互摘要=[memory_value] + 情感变化=[从原文推断]`），触发正常压缩规则
   - `preference_detail_list` 条目 → 更新 NPC 的行为倾向标签（如 `preference="偏好简洁直接的交流方式"` → 影响该NPC在后续叙事中的对话风格）
5. 抽取失败或API异常 → 跳过当日抽取，不重试。NPC仅依赖手动维护的记忆队列（降级策略）。连续5日抽取失败 → 暂停该NPC的自动抽取30游戏日

**与手动记忆的关系**：通过 extractor 自动注入的记忆条目与手动维护的详细记忆共用队列容量，遵循相同的压缩规则（§3.4）。extractor 抽取的记忆条目标记来源为 `source: "memos_extracted"`，与玩家直接互动产生的记忆（`source: "player_interaction"`）区分。


## 七、与V3其他模块的交互

### 7.1 接收：来自世界规则引擎

世界规则引擎每日结算后，向NPC行为系统推送（**每日推送通道**）：
- 当前区域的状态变更（威胁等级变化、控制势力变化）
- 全局事件影响（该NPC所在区域是否被事件波及）
- 所属势力的状态变更（食物短缺、士气下降、势力迁移）

此外，当玩家行动导致模拟层阈值跨越时，世界规则引擎通过**即时推送通道**立即通知：
- 触发条件：玩家行动 → 裁决Agent判定生效 → 模拟层数据跨过阈值（见世界规则引擎§4.1-4.2）
- 推送内容：变更的区域/势力状态 + 跨越的阈值类型
- NPC行为系统收到后立即执行中断检查（见§4.2-4.3），不等待每日结算

此外，当战斗结算产生伤亡时，世界规则引擎推送 `CasualtyReport`（见世界规则引擎§3.3），NPC行为系统据此更新接触NPC的死亡/伤病标记。

NPC行为系统据此更新NPC的位置、状态、需求。

### 7.2 输出：向裁决Agent和叙事Agent

当玩家与NPC交互时，NPC行为系统提供：

**静态信息**（每次交互都提供）：
- NPC姓名、身份、性格标签
- 与玩家的关系阶段和好感度

**动态信息**（仅在变化时提供）：
- NPC当前需求（如果与上次见面不同）
- NPC最近经历的重要事件（如果与玩家相关或影响NPC状态）
- NPC对玩家的情感倾向（如果有变化）
- NPC的异常位置解释（如果触发）

### 7.3 与剧情管理器的协调：冻结/解冻协议

剧情管理器优先级高于模拟层。当关键剧情节点涉及特定NPC时，需冻结该NPC的自主行为。

#### SimulationFreeze 规范

剧情管理器在关键节点开始时，发出冻结请求：

```
SimulationFreeze {
  targetType: "npc"
  targetIds: [...]
  freezeBehavior: "full" | "needs_only" | "position_only"
  maxFreezeDays: Int (超时自动解冻，默认5天，PlotManager在构造时强制指定)
}
```

> **路由说明**：SimulationFreeze 由 PlotManager 统一发出，按 `targetType` 路由到对应子系统：
> - `targetType = "npc"` → 仅发给NPC行为系统，行为枚举：`full` / `needs_only` / `position_only`
> - `targetType = "faction" | "region"` → 仅发给世界规则引擎，行为枚举：`full` / `resources_only`
> 
> NPC行为系统不接收 `targetType = "faction" | "region"` 的冻结请求，反之亦然。

- `full`：完全冻结——NPC的需求、位置、行为决策均不变化（用于关键对话、战斗场景）
- `needs_only`：仅冻结行为决策——需求值继续增长，但NPC不做反应（用于短期剧情）
- `position_only`：仅冻结位置——NPC不移动，但需求和低优先级行为继续（用于等待场景）

#### 解冻追赶规则

剧情节点完成后，PlotManager 调用 `thaw(targetIds)`：

- 若 `累计冻结天数 = 0`：无追赶，NPC从当前状态继续
- 若 `累计冻结天数 > 0`（仅 `needs_only` 和 `position_only` 模式积累）：执行批量追赶，复用加速模式批量追赶的逐日模拟逻辑（见§4.1"批量追赶的需求过载致死判定"），确保连续饱和天数正确判定
- 解冻时补写冻结期间的环境记忆：从世界规则引擎和NPC系统的变更日志中提取冻结期间发生的宏观事件（势力状态变更、区域事件、CasualtyReport 中涉及该NPC认识的其他NPC的伤亡），以环境记忆格式插入NPC的详细记忆队列。补写遵循正常记忆压缩规则。此机制防止NPC解冻时对冻结期间的重大变化"一无所知"

#### 协调优先级

- 剧情管理器可覆盖NPC的特定状态（如强制好感度变化、强制位置变更）
- 世界规则引擎的冻结由各自的模块独立管理（见世界规则引擎文档§6.4）
- NPC行为系统和世界规则引擎的冻结是独立的——可以只冻结NPC而不冻结势力


## 八、性能与复杂度控制

**NPC数量控制**：
- 接触NPC上限：30（超过上限时，最不活跃的接触NPC降级为背景NPC）
- 关键NPC上限：5
- 降级时，NPC的结构化数据存档，仅保留群体标签

**两种降级机制的交互规则**：
- **时间衰减优先**：每日结算时，先检查是否有NPC满足"连续30天无互动"条件（§2.2），若有则降级
- **上限补充**：若时间衰减降级后接触NPC仍超过30，按"最近互动时间"排序，降级最久未互动的NPC
- "最不活跃"的判定标准 = 距离上次玩家互动的游戏天数最长
- 两种降级路径均执行相同的数据存档流程（保留好感度和记忆摘要，更新群体标签中的"对玩家态度"）
- **批量提取优化**：同一游戏日内的多个NPC提取请求在每日结算时批量处理——先收集所有候选提取NPC，再一次性执行所有降级（时间衰减→上限补充），最后统一插入新NPC。避免逐个提取触发多次上限检查的重复计算

**结算计算量**：
- 每游戏日遍历所有接触NPC一次
- 对于10-30个接触NPC，每次结算的计算量在毫秒级
- NPC间互动判定仅在同一场景的NPC对之间进行，进一步降低计算量

**AI调用频率**：
- 日常行为：零AI调用
- NPC常规互动：零AI调用
- 罕见情况（涉及关键NPC、生死、道德困境）：轻量AI调用
- 预计AI调用频率：每几个游戏日一次


## 九、开发建议

### 9.1 最小可行实现

首次实现建议只包含：
- 接触NPC（不区分关键NPC）
- 基础时间表（固定模板，按身份分配）
- 两个需求（食物、安全）
- 好感度系统和关系阶段
- 记忆队列（6条详细记忆）
- 基础的NPC间互动（仅日常社交和资源分享）
- NPC离开与归来（仅死亡和迁移）

这个最小版本可在3-4天内实现，足以验证NPC行为系统的核心循环。

### 9.2 渐进扩展

验证通过后逐步加入：
- 关键NPC特殊待遇
- 完整需求系统（五个需求维度）
- 复杂NPC间互动（争执、合作、关系破裂）
- 时间表中断处理
- 轻量AI增强（用于罕见情况）
- 与MemOS的检索协调

### 9.3 调试工具

> **移动端适配**：本项目为 Android 应用，调试面板不建议内置于应用 UI 中。推荐方案：

> - 或使用 Android Debug Bridge 转发到本地 Web 调试面板
> - 关键状态变更（罕见情况触发、NPC降级/升级、关系阶段跨越）写入 Room DB 的调试日志表

调试功能清单：
- 显示所有接触NPC列表（含层级的筛选）
- 查看单个NPC的完整状态（时间表、需求、记忆、关系）
- 模拟时间推进，观察NPC状态变化
- 记录罕见情况触发日志
