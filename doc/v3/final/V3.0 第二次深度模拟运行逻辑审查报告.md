## 一、场景E：跨Region移动 + NPC异步预演

### 预设状态

```
玩家位置：红松营地（Region_A, Location_主广场），目标：蓝河哨站（Region_B）
红松营地(Region_A): 控制势力=红松幸存者, 接触NPC: [老张, 王二, 李队长]
蓝河哨站(Region_B): 控制势力=蓝河军事哨站, 接触NPC: [赵指挥官, 孙医生, 周侦察兵]
玩家距Region_B边界: 0.5个Location
```

### 步骤追踪

```
Step 1: 玩家发出移动行动 "前往蓝河哨站"
        ↓
Step 2: GameRepository 检测到玩家距Region_B边界 < 1 Location
        触发跨Region异步预演机制
        ↓
Step 3: 后台启动分批预演 Region_B 的NPC互动
        批次1: [赵指挥官, 孙医生] → 日常社交, 好感度+3
        批次2: [孙医生, 周侦察兵] → 资源分享(医疗情报), 好感度+8
        批次3: [赵指挥官, 周侦察兵] → 合作(例行巡逻), 好感度+5
        ↓
        ⚠️ 逻辑缺口 #1: 预演中的NPC需求追赶值丢失

        预演对参与NPC执行轻量需求追赶：
        "追赶比例 = (当前GameClock - 上次每日结算) / 1440"
        "追赶后的需求值 = 当前存储需求值 + 日增量 × 追赶比例"
        "此追赶仅用于本次互动判定，不写入持久存储"
        
        问题：假设当前时间距上次每日结算已过16游戏小时。
        赵指挥官食物需求追赶值 = 当前值 + 120 × (16/24) = 当前值 + 80
        
        预演判定：赵指挥官食物需求=当前值+80 → 较高 → 
        互动判定时可能触发"资源分享"行为（需求驱动）。
        
        但追赶值不持久化。如果玩家实际跨越边界：
        - 预演结果被应用（包括互动结果：好感度变化、社交快照）
        - 但需求追赶值被丢弃 → 赵指挥官的食物需求回到"当前值"
        - 这意味着：赵指挥官"在互动中表现出饥饿并得到了孙医生的食物"，
          但互动后他的饥饿程度"回退"到了互动前的水平
        
        这种"互动结果保留但驱动原因消失"是不合逻辑的。

        更严重的情况：如果追赶值让某个NPC的需求恰好跨过100阈值
        （如食物需求从90→追赶+80=170→clamp到100），预演中该NPC
        可能触发"需求驱动行为"（向其他NPC求助），产生社交快照。
        但跨越边界后追赶值丢弃，需求回到90——NPC的行为失去了动机支撑。

Step 4: 玩家实际跨越边界
        应用预演缓冲区 + 补算未覆盖的NPC对
        ↓
Step 5: 裁决Agent判定移动行动（正常流程）
        输入RulingContext: zoneState=Region_B, controllingFaction=蓝河哨站,
        nearbyNpcs=[赵指挥官(来自NPC系统), 孙医生, 周侦察兵]
        
        ⚠️ 逻辑缺口 #2: 跨越边界后裁决Agent的nearbyNpcs数据来源

        玩家跨越到Region_B后，裁决Agent需要Region_B的NPC信息。
        但NPC行为系统的正式状态是"按每日结算节奏更新"的。
        
        玩家跨越边界时可能距上次每日结算还有几小时——
        此时NPC系统还没有正式结算Region_B的NPC状态。
        
        裁决Agent收到的nearbyNpcs来自NPC系统的"当前快照"——
        但这个快照可能包含了预演中的临时状态（追赶值已丢弃），
        也可能完全不包含预演产生的互动结果（因为预演结果暂存缓冲区）。
        
        当预演缓冲区被应用时，NPC间的好感度变化、社交快照等被写入持久存储。
        但裁决Agent在Step 5调用时，这些写入是否已经完成？
        
        如果裁决Agent在缓冲区写入前被调用 → nearbyNpcs是预演前的状态
        如果裁决Agent在缓冲区写入后被调用 → nearbyNpcs包含了预演产生的变化
        
        时序依赖于实现细节，文档未定义。
```

## 二、场景F：剧情管理器冻结/解冻 + 每日结算交叉

### 预设状态

```
游戏时间：第10天 08:00
剧情管理器触发关键节点："红松营地的背叛"（预计持续2游戏日）
冻结目标：NPC[李队长] freezeBehavior="full"
        势力[红松幸存者] freezeBehavior="resources_only"
玩家位于红松营地，正在与李队长对话
```

### 步骤追踪

```
Day 10 08:00: 剧情节点开始
  PlotManager 发出 SimulationFreeze:
    → NPC系统: targetType="npc", targetIds=[李队长], freezeBehavior="full"
    → 世界规则引擎: targetType="faction", targetIds=[红松幸存者], freezeBehavior="resources_only"
  
  李队长: 完全冻结(需求/位置/行为不变)
  红松营地: 资源池继续每日更新，但冲突和事件不触发

Day 10 午夜: 每日结算
  世界规则引擎:
    Step 1: 红松营地资源更新正常执行（resources_only模式）
    Step 2: 状态检查正常
    Step 3-5: 跳过（resources_only冻结冲突和事件）
    
    ⚠️ 逻辑缺口 #3: 冻结势力仍参与资源更新但跳过冲突判定——
    敌对势力可能在此期间进攻被冻结的势力吗？
    
    世界规则引擎§6.4: "resources_only：仅冻结冲突和事件"
    这意味着被冻结的势力不会主动发起冲突（Step 3跳过），
    但敌对势力是否可以向被冻结势力发起冲突？
    
    如果是——被冻结势力不会"反击"（冻结了冲突判定），
    敌对势力单方面攻击无抵抗的势力 → 不合理。
    
    如果不是——敌对势力在Step 3的遍历中被跳过，
    因为"相邻且敌对"的判定需要双方都参与。
    
    文档未明确敌对势力对被冻结势力的冲突处理。

  NPC系统:
    李队长: 完全冻结，需求/位置不变
    其他NPC: 正常结算（推进需求、互动、离开判定）
    
    ⚠️ 逻辑缺口 #4: 冻结NPC与其他NPC的互动被阻断——
    但世界没有"暂停"
    
    李队长被冻结在原地（position locked），但其他NPC正常移动和互动。
    如果NPC王二在结算中因需求驱动"离开红松营地"——
    李队长不会对此有任何反应（冻结了行为决策）。
    
    解冻后，李队长"发现王二已经离开"——但在冻结期间，
    李队长的记忆中没有王二离开的环境记忆（冻结阻止了记忆写入）。
    
    这导致NPC的记忆出现"跳跃"：冻结前王二在场，解冻后王二消失了，
    中间没有任何过渡。NPC文档§3.4的环境记忆机制应在解冻时
    补写冻结期间错过的环境事件。

Day 12 08:00: 剧情节点完成（冻结2天）
  PlotManager 调用 thaw():
    李队长: 累计冻结天数=2 → 执行批量追赶
    红松营地: 累计冻结天数=2 → 执行批量追赶(冲突+事件)
    
    ⚠️ 逻辑缺口 #5: 解冻批量追赶与加速模式批量追赶的公式复用
    
    NPC文档§7.3定义了解冻追赶:
    "一次性推进冻结期间的需求值，基于新状态判定是否需要立即触发行为"
    
    但解冻追赶的公式是什么？
    第一次深度模拟在NPC文档§4.1新增了加速模式批量追赶的详细伪代码，
    包含逐日模拟需求推进以正确判定"连续3日饱和"。
    
    解冻追赶是否复用同一套逻辑？如果是——NPC的连续饱和天数
    是从冻结前继承的，冻结期间每天都在模拟中推进。
    如果不是——需求值可能一次性增加N×日增量，跳过连续饱和判定。
    
    文档未说明解冻追赶是否复用加速批量追赶的伪代码逻辑。
```

### 本场景结论：发现 3 个运行时逻辑缺口

## 三、场景G：长周期连续7日模拟

### 预设状态

```
初始：第1天 00:00
势力：红松营地(人口120, 食物360天, 兵力30, 士气65)

区域：Region_A(红松), Region_B(匪帮), Region_C(蓝河) 三角相邻
关系：红松-匪帮(敌对), 匪帮-蓝河(敌对), 红松-蓝河(中立)
```

```
  "势力兵力降至0时，所有剩余接触NPC触发'迁移'或'被俘'判定"

  ⚠️ 逻辑缺口 #8: 战斗幸存判定与势力覆灭迁移判定的竞争
  
  李队长在同一次结算中经历了:
  1. 战斗伤亡随机抽中(触发场景3)

  3. 场景4连锁触发(重伤→行为模式转变)

  势力覆灭的迁移判定仍然会触发。李队长刚从战场上"被部下冒死掩护撤退"，
  立刻面临"势力覆灭，向何处迁移"的判定。
  
  这两个判定应该合并处理: 场景3的AI已经评估了李队长的战斗结果，
  迁移判定应基于场景3/4的结论(重伤+行为模式="retreat_to_safety")，
  而非独立重新判定。
  
  但当前文档中，势力覆灭的迁移判定(NPC§4.4)与AI评估(场景3+4)
  是两个独立路径，没有信息传递。
```

### 长周期模拟总结

7天模拟暴露了系统在**连续多日运行**时的累积效应问题：
- AI评估的stateChanges对后续每日结算的机制影响不足（缺口6）
- 极端状态（食物归零）的处理链断裂（缺口7）
- 单次结算内多个独立判定路径的信息隔离（缺口8）

## 四、场景H：NPC提取 + 立即深度互动

### 预设状态

```

        ⚠️ 逻辑缺口 #9: 新提取NPC的npcDepthContext为空
        
        裁决Agent的RulingContext中:
        nearbyNpcs包含哨兵甲:
          姓名:哨兵甲, 身份:哨兵, 性格:谨慎, 好感度:+35(熟悉),
          关系阶段:熟悉, 当前需求:食物55, 安全30, 情感倾向:[]
        
        npcDepthContext(若行动涉及特定NPC)应包含:
          "该NPC的完整上下文（记忆摘要、互动历史）"
        
        哨兵甲刚被提取，记忆队列只有1条(提取时的互动)。
        MemOS中无历史交互片段。
        
        这本身不是问题——新NPC确实没有丰富的历史。
        但裁决Agent的System Prompt(§2.2)包含"NPC深度规则"——
        它期望对NPC有一定深度的了解。对于只有1条记忆的新NPC，
        裁决Agent的判定可能过于依赖性格标签和当前需求，
        导致"邀请同行"这类深度社交行动的判定结果不够 nuanced。

Step 5: 假设裁决Agent判定"部分成功"——哨兵甲同意同行但表示担忧
        
        ⚠️ 逻辑缺口 #10: NPC跟随玩家跨Region移动的数据流
        
        如果哨兵甲同意同行，玩家带着哨兵甲移动到Region_B(蓝河哨站):
        - NPC行为系统发送NpcMovementNotification(§3.1.1)
        - 世界规则引擎更新人口统计
        - 哨兵甲的所属势力从红松变为蓝河哨站(默认)
        
        但哨兵甲的好感度是基于"红松营地的哨兵"身份建立的。
        他跟随玩家离开了自己的势力——这对他的需求、时间表、
        记忆意味着什么？
        
        NPC文档未定义"NPC因玩家邀请而跨势力移动"的处理规则。
        NPC的跨Region移动在§4.4中仅涵盖了:
        - 迁移(势力撤离/区域威胁)
        - 外出探索(需求驱动)
        - 关系破裂(永久离开)
        - 被驱逐
        
        没有涵盖"玩家主动邀请同行"。
```

### 本场景结论：发现 2 个运行时逻辑缺口

## 五、场景I：正常模式玩家死亡

### 预设状态

```
游戏时间：第8天 22:00
玩家HP: 5, 状态: 重伤(未处理), 饱食度: 10, 口渴度: 5
附近NPC: 孙医生(蓝河哨站, 好感度+60, 信任)
玩家行动: "尝试自行处理腹部伤口"
```

### 步骤追踪

```
Step 1: 裁决Agent判定
        输入RulingContext: HP:5, 伤病:重伤, NPC:孙医生在场
        裁决输出: result="失败", dcValue=18, rollValue=5, 
                  narrativeSummary="你的手抖得厉害，缝针偏离了伤口..."
                  injuriesApplied:[{type:"伤口恶化", severity:"致命"}]
        ↓
Step 2: ActionResult应用到生存状态机
        HP:5 → HP:0 (伤口恶化导致)
        触发死亡判定: HP降至0且无救治可能
        ↓
        ⚠️ 逻辑缺口 #11: 正常模式死亡后的叙事生成路径不完整
        
        V3.0总纲§7.2:
        "若死亡发生在正常/减速模式 → 由叙事Agent以特殊模式生成
         （输入包含死亡原因和角色最终状态）"
        
        但Agent §3.3定义的叙事Agent输入是:
        "玩家行动标签 + ActionResult + PostRuling WorldSnapshot + 
         PlotContext + 记忆上下文"
        
        "特殊模式"是什么？Agent §3.3中没有对应的方法定义。
        
        与加速退出模式不同(有独立的buildStorytellerAccelExitUserMessage),
        死亡叙事模式没有独立的PromptBuilder方法。
        
        叙事Agent的System Prompt(§3.2)包含:
        "角色定义、五感描写、节奏控制、建议选项生成规则"
        
        在死亡场景中:
        - "建议选项生成规则"不适用(死人不需要建议选项)
        - "节奏控制"需要切换到"终结叙事"模式
        - 输出应包含"死亡叙事"而非"suggestions"
        
        但System Prompt没有任何死亡模式的提示。
        
        第一次深度模拟修复了世界叙事Agent的死亡报告模式(加速死亡),
        但正常/减速模式的死亡叙事路径仍然缺失。

Step 3: 死亡后处理
        V3.0总纲§7.2: 玩家可选择读档/观察世界/继承
        
        ⚠️ 逻辑缺口 #12: "观察世界"模式的Agent切换
        
        "观察世界"意味着玩家不再有角色，但世界继续运行。
        这带来几个问题:
        1. 叙事Agent还调用吗? 以什么身份叙事? (没有了"玩家角色")
        2. 裁决Agent还调用吗? (没有玩家行动)
        3. 世界规则引擎和NPC系统继续每日结算 —— 但不再有"玩家所在区域"
           的概念，世界叙事Agent的"信息以玩家为中心"原则失效
        4. 谁来触发加速/减速? (玩家可以观察但不能行动)
        
        这些在文档中完全没有定义。观察者模式需要一个全新的Agent交互模型。
```

### 本场景结论：发现 2 个运行时逻辑缺口
