## 一、场景T：天气→资源消耗→裁决DC的多层连锁

### 预设状态

```
季节：冬季（季节修正=0.3）
天气：暴风雪（playerAction触发时的瞬时天气）
玩家HP: 85, 饱食度: 40, 口渴度: 30
区域: 荒野（资源丰度15, 末日等级影响系数0.6）
```

### 连锁追踪

```
Step 1: 池-流模型每游戏日结算
  食物生产 = Σ(资源丰度15 × 0.6) × 采集效率
  采集效率 = 基础采集率 × 季节修正0.3 × 末日等级修正 × 人力修正
  → 冬季使采集效率降到正常30%，食物生产锐减

Step 2: 玩家行动 "在暴风雪中徒步前往蓝河哨站"
  裁决Agent判定:
    RulingContext.zoneState → 天气信息传入?
    
    ⚠️ 逻辑缺口 #1: RulingContext不包含天气/环境信息
    
    RulingContext(§6.1.1)包含:
    - worldSnapshot(玩家状态)
    - zoneState(威胁等级/控制势力/状态标签)
    - controllingFaction(资源概况/目标)
    
    但"当前天气"不在zoneState中——zoneState只有"状态标签"。
    "暴风雪"是否作为状态标签存在? 如果是临时的瞬时天气(非每日结算周期)，
    可能不在状态标签中。
    
    裁决Agent如何得知当前天气并据此调整DC?
    方案A: 通过zoneState的状态标签("暴风雪中")
    方案B: 通过playerAction的上下文(玩家输入中提及)
    
    方案A依赖天气被正确写入zoneState——但天气变更的触发机制是什么?
    文档未定义天气系统。
    
    方案B依赖玩家显式描述天气——不可靠。

Step 3: 水消耗的天气修正
  世界规则引擎§3.1: "水消耗 = 人口 × 人均日水消耗 × 天气修正（炎热×1.3，正常×1.0，寒冷×0.8）"
  
  ⚠️ 逻辑缺口 #2: 天气修正是每日固定值还是可动态变化
  
  公式中的"天气修正"是三个固定档位(炎热/正常/寒冷)。
  但实际天气可能是动态变化的(暴风雪、热浪、雨天等)。
  
  "暴风雪"属于"寒冷"大类(×0.8)，还是应该有自己的修正?
  极端天气(暴风雪、热浪)的消耗速率应与普通天气不同。
  
  文档只定义了三个天气档位，未定义极端天气的修正系数。

Step 4: 季节与天气的叠加
  冬季(季节修正0.3) + 暴风雪(可能属于寒冷, ×0.8)
  这两个修正是相乘(0.3×0.8=0.24)还是取最不利?
  
  ⚠️ 逻辑缺口 #3: 季节修正与天气修正的叠加方式未定义
  
  季节影响"生产端"(采集效率)，
  天气影响"消耗端"(水消耗速率)。
  两者作用于不同环节，应分别应用(不冲突)。
  
  但如果存在同时影响同一环节的季节+天气因素(如"冬季暴风雪"
  对移动DC的同时影响)，叠加方式需要明确定义。
```

### 本场景结论：发现 3 个运行时逻辑缺口

```
玩家位置: 红松营地
附近NPC: 李队长(信任), 老张(熟悉)
当前场景: 营地广场, 傍晚
```

### 步骤追踪

```
Step 1: 叙事Agent生成正常模式suggestions
  V3.0总纲§3.2: suggestions时间跨度为"30分钟-数小时选项"
  
  叙事Agent的System Prompt(§3.2): "建议选项生成规则"

    {label:"与李队长商讨防御计划", timeCost:"1小时", type:"社交"},

    {label:"在营地周围巡逻", timeCost:"2小时", type:"安全"},
    {label:"前往蓝河哨站", timeCost:"4小时(跨Region)", type:"移动"}
  ]
  
  ⚠️ 逻辑缺口 #4: suggestions的timeCost与实际时间推进的关系
  
  suggestions中的timeCost("1小时")是"建议值"还是"精确值"?
  玩家选择后，游戏时间推进1小时——
  但如果裁决Agent判定"部分成功"或"失败"，
  实际消耗的时间是否与建议的timeCost一致?
  
  例: "搜索物资"建议30分钟 → 裁决判定失败(找了很久没找到) →
  实际消耗可能更长(如1小时)?
  
  文档未定义建议timeCost与ActionResult中实际时间消耗的关系。

Step 2: 玩家切换到减速模式
  V3.0总纲§3.4: suggestions展示"秒级/分钟级选项"
  
  叙事Agent重新生成suggestions:
  {label:"侧身闪避", timeCost:"2秒", type:"战斗"},
  {label:"反击头部", timeCost:"1秒", type:"战斗"},
  ...
  
  ⚠️ 逻辑缺口 #5: 速度模式切换时suggestions立即作废但无通知
  
  V3.0总纲§3.3: 加速时"suggestions折叠作废"
  
  但减速↔正常切换时呢? 正常模式下的"30分钟"选项在减速模式下
  会变成"10秒"选项吗? 还是完全重新生成?
  
  如果玩家在正常模式下看到"前往蓝河哨站(4小时)" → 
  切换到加速模式 → 这个选项被折叠作废 → 
  但这恰恰是加速模式最适合的行动(长距离移动)!
  
  加速模式下无suggestions(只有时间流摘要面板)——
  但玩家可能想在加速前选择一个"目标行动"让自动导航执行。
  
  ⚠️ 逻辑缺口 #6: 加速模式下无"加速目标"设定机制
  
  当前设计: 加速→自动导航按生存本能行动→无策略性选择。
  但玩家可能想: "加速前往蓝河哨站"而非"加速+自动导航瞎逛"。
  
  加速模式缺少"加速目标"的元指令——玩家只能被动等待
  自动导航做生存本能决策，不能指定"向蓝河哨站方向前进"。
```

## 三、场景V：processPreRuling拆分后 — 玩家物资捐赠的阈值即时触发

### 预设状态

```
玩家物资: 食物×10份, 水×5000ml
势力蓝河哨站: 食物储备50人口天(刚好1天, 人口50), 弹药充足
V2.8新增方法: advanceWorldTime(hours), processPlayerAction(action, minutes)
```

### 步骤追踪

```
Step 1: 玩家行动 "向蓝河哨站捐赠5份食物"
        类型: 非对抗行动(捐赠)
        ↓
Step 2: processPlayerAction(action, 0分钟) 调用
        捐赠不消耗时间? 
        
        ⚠️ 逻辑缺口 #7: 非对抗行动的时间消耗定义缺失
        
        世界规则引擎§3.1: "若为捐赠或合法领取 → 跳过裁决Agent判定，
        由 GameRepository 直接执行换算"
        
        跳过裁决Agent意味着跳过"行动消耗时间"的判定——
        但捐赠本身是否需要时间? 
        
        如果捐赠0时间 → 玩家可以瞬间捐完所有物资 → 不合理
        如果捐赠消耗少量时间(如5分钟) → 谁决定这个时间? 
        裁决Agent被跳过了, GameRepository只有换算逻辑。
        
        文档未定义"跳过裁决Agent"时的时间消耗默认值。

Step 2: GameRepository直接执行换算
  标准单位换算: 5份食物 = 5 × 2000 kcal = 10000 kcal = 5人口天
  蓝河食物储备: 50 → 55人口天 (从1.0天→1.1天, 仍在危机阈值<3天内)
  
Step 3: 势力资源池变更 → 立即触发阈值检查
  食物储备从50变为55 → 但仍在危机中(<3天) → 不触发新的阈值跨越
  (阈值只在"跨过"边界时触发，数值改善不触发)
  
  ⚠️ 逻辑缺口 #8: 阈值检测只在"恶化方向"触发
  
  世界规则引擎§4.1: "每次状态变更后，检查是否有指标跨过阈值"
  
  但"跨过"的定义是单向(恶化方向)还是双向(改善也算)?
  如果食物从2.9天恢复到3.1天(跨过3天危机线回到正常)——
  是否触发"危机解除"的评估?
  
  文档未定义阈值"解触"逻辑。如果只有恶化触发、改善不触发，
  那么"危机解除"永远不会被AI评估——势力从危机中恢复的过程
  没有AI辅助判断。
```

### 本场景结论：发现 2 个运行时逻辑缺口

## 四、场景W：区域人口归零 — 死城状态下的系统行为

### 预设状态

```
Region_C(原蓝河哨站):
  控制势力: 蓝河哨站(已解散, 第12天)
  所有接触NPC: 赵指挥官(阵亡), 孙医生(迁移至Region_D), 周侦察兵(失踪)
  背景NPC人口: 0 (全部死亡或迁移)
  区域状态: 威胁等级85, 资源丰度10, 状态标签:["尸潮后恢复中", "势力解散"]
```

### 步骤追踪

```
Step 1: 玩家来到Region_C
  zoneState: 威胁等级85, 控制势力=null(无主之地), 
           状态标签:["尸潮后恢复中", "势力解散"]
  nearbyNpcs: [] (空列表)
  controllingFaction: null

Step 2: RulingContext组装
  裁决Agent接收: nearbyNpcs=[]——空列表是合法的吗?
  
  ⚠️ 逻辑缺口 #9: RulingContext在无NPC区域的叙事生成
  
  叙事Agent收到的WorldSnapshot和zoneState描述了一个
  "空无一人、威胁等级85的死城"。
  
  叙事Agent的System Prompt(§3.2): "角色定义、五感描写、节奏控制"
  但没有指导如何在"无人区"生成叙事。
  
  正常叙事依赖nearbyNpcs提供社交上下文——
  无人区叙事需要完全不同的叙事策略(环境描写为主、氛围营造)。

Step 3: 玩家行动 "在废弃的蓝河哨站中搜索"
  裁决Agent判定: nearbyNpcs=[], activeEvents可能仍活跃(尸潮恢复中)
  
  EventDeck仍可能触发遭遇事件(在威胁85的区域搜索→遇到丧尸)
  但"社交类"行动无法执行(没有NPC可以互动)
  
  ⚠️ 逻辑缺口 #10: 无NPC区域中social类suggestions应被过滤
  
  叙事Agent生成的suggestions可能包含社交类选项——
  但在无人区这些选项毫无意义。
  
  suggestions的生成应该感知nearbyNpcs是否为空——
  如果为空, 过滤所有社交类选项, 仅保留探索/移动/生存类。
  
  文档未定义suggestions的"场景合法性过滤"规则。

Step 4: 每日结算 — 无主区域的模拟
  世界规则引擎§3.2: "无主区域自动被相邻势力的最强方'宣称'"
  
  相邻Region_B(灰烬匪帮, 兵力25): 宣称Region_C
  相邻Region_D(新势力?): 孙医生迁移至此
  
  ⚠️ 逻辑缺口 #11: "宣称"无主区域的势力是否需要实际占领
  
  "宣称"不同于"控制"——宣称只是声明所有权。
  匪帮宣称了Region_C, 但如果没有实际派兵占领,
  Region_C仍然是实际无主状态(威胁85, 有利可图但危险)。
  
  "宣称"状态对玩家有何影响?
  - 玩家进入"被匪帮宣称"的区域 → 匪帮是否会视为入侵?
  - 如果匪帮不实际控制 → 威胁等级是否变化?
  
  文档未定义"宣称"与"控制"的差异及其游戏影响。
```

## 五、场景X：AI调用中断恢复 — 应用进程被杀后的状态一致性

### 预设状态

```
玩家刚发出行动 → 裁决Agent API调用中(已发送, 等待响应)
应用进程被系统杀死(内存不足/用户强制关闭/崩溃)
```

### 步骤追踪

```
Step 1: 应用重启
  Room数据库恢复: 世界状态, NPC状态, 玩家状态(最近存档点)
  裁决Agent调用: 已发送但响应丢失(无状态HTTP请求)
  
  ⚠️ 逻辑缺口 #12: AI调用中途失败时的状态回滚
  
  正常流程: 玩家行动 → 裁决Agent → ActionResult → 应用状态变更 → 叙事Agent
  
  如果在步骤"裁决Agent调用中"应用被杀:
  - 玩家行动已被解析并发送给AI
  - AI可能已经完成了判定(或正在处理)
  - 但ActionResult从未到达客户端
  - 世界状态未被修改(因为ActionResult尚未应用)
  
  重启后:
  A) 重新发送AI请求 → AI可能处理两次(第一次的响应丢失但AI侧已消耗token)
  B) 放弃该行动 → 玩家看到"行动中断"并需要重新输入
  C) 检查是否有未完成的Action → 从Room数据库读取pending状态
  
  文档未定义AI调用中断的恢复策略。当前V2.x代码的降级策略
  只处理API异常(网络超时/服务不可用)，不处理进程级别的中断。

Step 2: 如果应用在"ActionResult已应用但叙事Agent未完成"时被杀
  状态机的变更已持久化(生存状态机写入Room)
  但叙事文本未生成
  
  重启后: 
  - 世界状态已更新(ActionResult已应用) ✓
  - 玩家状态已更新 ✓
  - 但缺少叙事文本——玩家看到状态栏更新了但不知道为什么
  
  ⚠️ 逻辑缺口 #13: 重启后缺少"补生成"叙事的能力
  
  系统可以检测到: "上次会话在ActionResult应用后、叙事生成前中断"。
  此时应补调用叙事Agent(使用已持久化的ActionResult)。
  
  文档未定义这种"补生成"模式。
```

### 本场景结论：发现 2 个运行时逻辑缺口
