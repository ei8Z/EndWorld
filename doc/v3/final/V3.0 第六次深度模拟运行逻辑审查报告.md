## 一、场景Y：接触NPC上限竞争 — 30个槽位的零和博弈

### 预设状态

```
当前接触NPC: 29个（接近上限30）
新互动触发提取: 玩家与3个不同背景NPC在同一个游戏日内产生"可被引用的后果"
  - 哨兵丙(透露情报)
  - 难民丁(物品转移——玩家给了食物)
  - 工匠戊(产生了承诺——"明天帮我修理装备")
```

### 步骤追踪

```
Step 1: 哨兵丙提取 → 30/30(满)
        哨兵丙成为第30个接触NPC
        ↓
Step 2: 难民丁提取 → 31/30(超限!)
        上限补充规则触发: 降级最久未互动的接触NPC
        ↓
Step 3: 按"最近互动时间"排序所有31个NPC
        假设最久未互动的是"商人甲"(23天前)
        商人甲降级为背景NPC → 30/30
        难民丁成为新的接触NPC(插入第30位)
        ↓
Step 4: 工匠戊提取 → 31/30(再次超限!)
        再次降级新的"最久未互动"NPC → 29/30
        工匠戊成为接触NPC
        ↓
        ⚠️ 逻辑缺口 #1: 同日批量提取时的降级竞争
        
        三个NPC在同一天被提取，但每次提取单独触发上限检查。
        结果是: 哨兵丙挤掉商人甲 → 难民丁挤掉新的"最不活跃" → 
        工匠戊再挤掉一个。
        
        一天内可能有3个活跃NPC被降级，而3个全新的NPC加入。
        这种周转速度是否合理?
        
        更关键的是: 刚刚被提取的哨兵丙(好感度+35)在下一次上限检查时
        可能被难民丁的提取触发降级——因为哨兵丙的"最近互动时间"
        虽然仅过了几分钟，但如果有28个NPC最近互动时间都比哨兵丙晚...
        
        实际上，"最久未互动"是按天数排序的。同一天内的互动，
        按"游戏内时间戳"排序。哨兵丙在上午10:00被提取，
        难民丁在上午10:05触发上限检查——哨兵丙的互动时间是10:00，
        所有29个老NPC的互动时间都更早(昨天或更早)，
        所以哨兵丙不会在当天被降级。✓
        
        但当新NPC数量>空闲槽位时，"时间衰减优先"规则首先执行。
        一天内可能有多个NPC满足"连续30天无互动"被降级(腾出槽位)，
        然后新NPC按上限补充规则依次填充。
        
        两种降级机制的顺序是明确的(§8): 时间衰减优先 → 上限补充 ✓

Step 5: 被降级的商人甲再次互动
        10天后，玩家在市场中遇到"商人甲"(已降级为背景NPC)
        玩家与商人甲交易 → 再次触发提取
        
        第三次深度模拟已修复再提取规则:
        - 距降级<90天 → 从存档恢复好感度(衰减后)
        - 好感度恢复公式: 存档好感度 × max(0.3, 1.0 - 10/90) = 存档值 × 0.889
        
        商人甲原来的好感度+45 → 恢复 = 45 × 0.889 ≈ 40 ✓
        
        ⚠️ 逻辑缺口 #2: 再提取时若接触NPC已达上限, 恢复的NPC优先级?
        
        商人甲被再提取时, 接触NPC=30(满)。
        上限补充规则触发 → 降级当前最久未互动的NPC。
        
        但商人甲刚刚互动 ← 互动时间是"现在" ← 刚刚发生的互动
        → 商人甲不会被立即降级。
        
        被挤掉的可能是另一个刚被提取不久的新NPC。
        这种"零和博弈"可能导致:
        - 活跃NPC被新NPC不断挤掉 → 只有最活跃的30个留在地表
        - 这是设计意图 ✓ (限制计算量)
        
        但有一个边缘情况: 如果玩家在短时间内与大量背景NPC互动
        (如在集市中逐一交谈)，每次提取可能触发上限检查。
        在最坏情况下，一次集市访问可能触发10+次上限检查和降级操作。
        
        文档未定义"批量提取"的优化——是否可以先收集所有提取请求，
        一次性排序并降级，而非逐个触发上限检查?
```

## 四、场景BB：玩家行动跨午夜 — 每日结算插入时序

### 预设状态

```
游戏时间：第5天 23:45 (距午夜15分钟)
玩家行动："仔细搜索仓库" (建议timeCost: 30分钟)

```

### 步骤追踪

```
Step 1: processPlayerAction(action, 30分钟)
        时钟推进: 23:45 → 00:15 (跨过午夜!)
        ↓
        ⚠️ 逻辑缺口 #8: 行动跨午夜时每日结算的插入时序
        
        玩家行动消耗30分钟游戏时间。
        这30分钟跨过了第5天→第6天的午夜。
        
        触发每日结算的时机是什么?
        A) 在行动执行前检测"会跨午夜" → 先结算再执行行动
        B) 行动执行完毕后检测"已跨午夜" → 后补结算
        C) 行动执行中在午夜点暂停 → 插入结算 → 继续行动
        
        V3.0总纲§3.5: "游戏内每经过1天（午夜跨过）触发每日结算"
        
        但"跨过"是由生存状态机的GameClock检测的。

        如果A(先结算再行动):
          23:45结算第5天 → 午夜触发第6天每日结算 → 
          然后执行行动(30分钟, 消耗资源) → 行动消耗从第6天开始计
        
        如果B(后补结算):
          23:45执行行动(30分钟) → 00:15 → 检测到已跨午夜 →
          执行第6天每日结算 → 行动消耗在第5天资源基础上
        
        两种时序产生不同的资源消耗结果:
        - 方式A: 每日结算先执行, 资源池先扣减一天 → 玩家行动消耗时资源更少
        - 方式B: 玩家行动先消耗 → 每日结算后扣减时资源更少
        
        差异虽小, 但在资源紧张时(食物仅够1天)可能导致
        死亡/解散判定恰好触发或恰好不触发。
        
        文档未定义行动跨午夜时的结算插入时序。

Step 2: 如果玩家行动触发即时阈值推送
        行动消耗导致势力资源池跨过阈值 → 即时推送
        但午夜也触发了每日结算(包括阈值检测)

        同时午夜到达 → 每日结算Step 2也检测到弹药危机阈值
        
        两次推送是否合并? 还是会触发两次AI评估?
        
        世界规则引擎§4.2: "即时推送"和"每日推送"是两个独立通道。
        合并规则仅适用于Step 6("若触发数>1，合并为一次AI评估")——
        但Step 6是每日结算的一部分。
        
        即时推送在每日结算之前触发 → NPC系统收到第一次中断检查 →
```

## 五、场景CC：多区域同时战斗 — 跨区域CasualtyReport聚合

### 预设状态

```
同一每日结算周期:
  战斗1: 红松(Region_A) vs 匪帮(Region_B) — 相邻区域A-B边界
  战斗2: 匪帮(Region_B) vs 蓝河(Region_C) — 相邻区域B-C边界
  匪帮同时参与两场战斗!
```

### 步骤追踪

```
Step 1: 冲突判定(Step 3)
  红松-匪帮: 判定触发冲突 ✓
  匪帮-蓝河: 判定触发冲突 ✓
  
  ⚠️ 逻辑缺口 #10: 同一势力同时参与多场战斗的兵力分配
  
  匪帮兵力=60。兰彻斯特公式使用"兵力"计算战斗力。
  但匪帮同时在两场战斗中:
  
  战斗1(匪帮 vs 红松): 匪帮使用兵力60 → 战力=60²=3600
  战斗2(匪帮 vs 蓝河): 匪帮也使用兵力60 → 战力=60²=3600
  
  这等价于匪帮有120兵力(60×2)同时投入两场战斗——
  兵力被重复计算了!
  
  合理的处理: 匪帮需要将60兵力分配到两场战斗。
  但如何分配? 平均分配(30+30)? 按威胁权重分配?
  
  文档未定义同一势力在多场同时战斗中的兵力分配规则。
  当前兰彻斯特公式隐式假设每场战斗是独立的(兵力不共享)。

Step 2: 战斗结算(Step 4)
  假设采用独立兵力(不复用):
  战斗1: 匪帮(60²=3600) vs 红松(30²=900) → 匪帮损失50%=30, 红松全灭
  战斗2: 匪帮(60²=3600) vs 蓝河(40²=1600) → 匪帮损失~33%=20, 蓝河全灭
  
  匪帮在两场战斗后: 60 - 30 - 20 = 10兵力
  但匪帮同时投入两场战斗 → 每场都应该用"实际可用兵力"
  
  如果匪帮分兵: 30+30:
  战斗1: 匪帮(30²=900) vs 红松(30²=900) → 战力1:1 → 双方损失~50%=各15
  战斗2: 匪帮(30²=900) vs 蓝河(40²=1600) → 战力比0.56 → 匪帮损失81%=24, 蓝河损失33%=13
  
  匪帮两场后: 30-15 + 30-24 = 15+6 = 21兵力
  与不复用(10兵力)差异巨大!
  
  ⚠️ 逻辑缺口 #11: 多场战斗的结算顺序影响结果
  
  如果串行结算(先战斗1再战斗2):
  战斗1后匪帮兵力=60-30=30
  战斗2用30兵力: 匪帮(30²=900) vs 蓝河(40²=1600)
  → 战力比0.56, 匪帮损失81%=24, 残6兵力
  
  如果并行结算(用初始兵力):
  两场都用60 → 总损失30+20=50, 残10兵力
  
  结果不同! 文档未定义多场同时战斗的结算顺序。
```
