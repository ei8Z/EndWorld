
## Phase 1：第一轮玩家行动 — "在红松营地仓库中搜索医疗物资"

### 文档描述

```
1. 玩家输入行动文本 → ActionParsed: {type: "搜索", target: "仓库", method: "仔细", riskLevel: "低", estimatedTimeMinutes: 30}
2. sendActionStream() → seedStateMachine() → initV3World()（首次）
3. processPreRuling(30分钟) → 时间推进 → 午夜检测（第1天未跨午夜）
4. 组装 RulingContext（总纲 §6.1.1）:
   - playerAction: ActionParsed
   - worldSnapshot: HP/SP/饱食度/物资背包/伤病（来自生存状态机）
   - zoneState: 威胁等级25, 控制势力=红松营地, 状态标签=[], 天气=晴朗
   - controllingFaction: 红松幸存者营地(人口120, 食物360天, 目标:防守, 领袖:谨慎)
   - nearbyNpcs: 从NPC行为系统查询红松营地(R01)的接触NPC
   - activeEvents: 从世界规则引擎查询影响R01的全局事件
   - npcDepthContext: 无(首次行动，无特定NPC)
5. 裁决Agent: Pro/max/8192/非流式, 8-20秒
   输入: System Prompt(buildReasonerSystemPrompt) + User Message(buildReasonerUserMessage)
   输出: ActionResult{result:"部分成功", dcValue:14, rollValue:12+2=14,
         resourceChanges:[], 
         narrativeSummary:"你在仓库角落找到了几卷绷带和半瓶消毒酒精..."}
6. 应用ActionResult: 
   → 生存状态机: 无资源消耗(搜索行动)
   → 模拟层: 无直接变更(搜索不改变世界状态)
7. 叙事Agent: Pro/medium/8192/流式, 3-8秒
   输入: 玩家行动标签 + ActionResult + PostRuling WorldSnapshot + PlotContext + 记忆上下文
   输出: GameResponse{header.story:"仓库的铁门发出刺耳的...", suggestions:[...], statusUpdate:...}
8. syncGameData → persistV3State (V3状态写Room DB)
```

### 对应代码检查

| 步骤 | 文档要求 | 代码实现 | 状态 |
|------|----------|----------|------|
| 1 | ActionParsed | `BranchClassifier` 解析 + `ActionParsed` 数据类 | ✅ |
| 2 | seedStateMachine + initV3World | `sendActionStream` 中调用 | ✅ |
| 3 | processPreRuling + 午夜检测 | `sm.processPreRuling()` + `sm.clock.currentDay > prevDay` 检查 | ✅ |
| 4 | RulingContext 7字段 | 代码中 `buildWorldProgressString` + `buildNpcDepthContext` 提供部分字段，但 `zoneState`/`controllingFaction`/`activeEvents` **不来自V3模拟层** | ⚠️ |
| 5 | 裁决Agent调用 | `ReasonerApiClient.reason()` | ✅ |
| 6 | ActionResult应用 | `sm.applyActionResult()` | ✅ |
| 7 | 叙事Agent调用 | `StorytellerApiClient.tell()` 流式 | ✅ |
| 8 | 持久化 | `syncGameData()` + `persistV3State()` | ✅ |

### 发现的代码差异

| # | 问题 | 严重度 |
|---|------|--------|
| 3 | **RulingContext 的 zoneState/controllingFaction/activeEvents 不来自V3模拟层** — 当前代码中 `preSnapshot` 来自 `SurvivalStateMachine.generatePreRulingSnapshot()`，其 `zoneState` 字段只包含V2的 `WorldSnapshot` 信息（威胁等级/控制势力/状态标签）。V3的世界规则引擎产出的 `regions`、`factions`、`activeEvents` 没有被注入到 RulingContext 中。裁决Agent收到的仍是V2格式的上下文，缺少V3模拟层的精确数据。 | 🔴 |
| 4 | **nearbyNpcs 不来自V3 NPC系统** — 文档要求 `nearbyNpcs` 从NPC行为系统提供（姓名/身份/性格/好感度/关系阶段/当前需求/情感倾向/距上次互动天数），但代码中 `buildNpcDepthContext` 使用的是V2的 `NpcRelation`（来自Room DB的旧表），不包含V3 NPC系统的需求、记忆、情感倾向。 | 🔴 |

## Phase 2：第二轮玩家行动 — "向哨兵丙打听尸潮的动向"

### 文档描述（V3.0 总纲 §5.1 + NPC §2.2 提取规则）

```
预设: 哨兵丙是背景NPC(红松营地, 群体态度: 欢迎→+30)

1. 玩家输入 → ActionParsed: {type: "社交", target: "哨兵丙", method: "打听情报", riskLevel: "低", estimatedTimeMinutes: 15}
2. 裁决Agent判定: 
   - NPC深度上下文: 哨兵丙是背景NPC，npcDepthContext 仅包含群体标签
   - 判定"透露了独特信息(尸潮情报)" → 触发提取条件
3. ActionResult: {result:"成功", narrativeSummary:"哨兵丙告诉你，东边的尸潮正在向蓝河哨站方向移动..."}
4. NPC提取(文档 §2.2):
   - 系统即时创建接触NPC实例
   - 初始好感度 = 群体态度基准值+30 + 互动变化值+5 = +35
   - 性格标签: 随机→"谨慎"
   - 战斗角色: 哨兵→战斗人员(CombatRole.COMBATANT)
   - 初始需求: 30+random(0,40)=55, 势力食物充足无修正
   - 记忆队列: [Day 1 14:15 与玩家对话 透露尸潮情报 +5好感]
   - 提取时间距下次结算>6小时 → 参与当日结算
5. 叙事Agent生成叙事 + suggestions(包含"前往蓝河哨站预警"选项)
6. 状态持久化: syncGameData → persistV3State
```

### 对应代码检查

| 步骤 | 文档要求 | 代码实现 | 状态 |
|------|----------|----------|------|
| 1 | ActionParsed | ✅ | ✅ |
| 2 | 裁决Agent判定 + NPC上下文 | ✅ ReasonerApiClient | ✅ |
| 3 | ActionResult + 提取判定 | 代码中 `ReasonerApiClient.reason()` 返回 `ActionResult`，但**提取条件检查未实现** | 🔴 |
| 4 | NPC提取创建 | `NpcBehaviorEngine.initializeNewNpc()` 存在，但**从未在GameRepository中被调用** | 🔴 |
| 5 | 叙事Agent | ✅ | ✅ |
| 6 | 持久化 | ✅ `persistV3State()` | ✅ |

### 发现的代码差异

| # | 问题 | 严重度 |
|---|------|--------|
| 5 | **NPC提取逻辑完全缺失** — 文档定义了5条提取条件（好感度变化≥10/产生承诺/物品转移/透露独特信息），但代码中 `processMainline` 收到 `ActionResult` 后仅调用 `sm.applyActionResult()` 和 `syncGameData()`，没有检查提取条件并调用 `npcEngine.initializeNewNpc()`。 | 🔴 |

## Phase 3：物资清算（每日结算触发）

### 文档描述（世界规则引擎 §5 + V3.0 总纲 §3.5）

```
时间: 第1天 → 第2天 午夜（24:00）

Step 1: 资源更新（池-流模型）
  - 红松营地: 食物360-120=240 (从4天→2.8天, 跨过3天危机阈值!)
  - 灰烬匪帮: 食物560-80=480 (7天→6天, 正常)
  - 蓝河哨站: 食物200-50=150 (4天→3天, 跨过7天警告阈值)
  - 游荡尸潮: 食物0 (无消耗, 不死生物)

Step 2: 状态检查（阈值检测）
  触发: 红松食物危机(<3天) + 蓝河食物警告(<7天)

Step 3: 冲突判定
  红松-匪帮(敌对): 兵力比60/30=2.0, 战力比4.0
  冲突概率=0.05×2.0×1.33×1.0=0.133 → 未触发
  匪帮-蓝河(敌对): 兵力比60/40=1.5, 战力比2.25
  冲突概率=0.075 → 未触发

Step 4: 战斗结算（无战斗触发，跳过）

Step 5: 事件传播
  当前无活跃全局事件 → 跳过传播
  概率自动生成: 4势力×0.03=0.12/日 < minEventsPerDay=1 → 保底生成1个新事件
  → 生成"难民潮"(强度50, 源区域R05, 影响R05)

Step 6: 阈值触发处理
  合并2个触发 → 调用轻量AI场景1
  AI输入: [红松食物危机: 食物2.8天] + [蓝河食物警告: 食物3天]
  AI输出: {evaluation:{mostLikelyReaction:"红松向蓝河求援", 
           stateChanges:[{target:"红松", attribute:"势力目标", newValue:"寻求同盟"}]
           ...}}

Step 7: NPC行为系统结算
  哨兵丙(新提取的接触NPC):
    需求推进24h: 食物55→min(100,55+120)=100(饱和Day1)
    NPC间互动: 哨兵丙所在R01有其他接触NPC? 
    → 当前仅有哨兵丙 → 无NPC间互动
  其他接触NPC(如有): 同样推进需求

Step 8: MemOS每日抽取
  收集哨兵丙的交互文本 → POST /extract/memory
  → 若无满足写入条件的交互，跳过
```

| 3 | 冲突判定 | `DailySettlement.execute()` — `shouldConflictOccur()` | ✅ |
