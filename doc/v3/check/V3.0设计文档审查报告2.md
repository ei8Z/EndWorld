### 🔴 问题1：加速模式结算策略前后矛盾

**涉及文档**：《V3.0 总纲》§3.3 第4步 vs §3.5 末段

**矛盾描述**：
- §3.3 加速模式步骤4：**"世界规则引擎持续结算（每游戏日一次）"**——暗示逐日连续结算
- §3.5：**"加速模式特殊处理：采用批量追赶模式——加速结束时一次性计算"**——明确定义为批量追赶

两段描述在同一份文档中互相矛盾。批量追赶策略是一轮审查的修订结论，但 §3.3 的步骤分解未同步更新。

**修改建议**：将 §3.3 步骤4 改为："世界规则引擎标记为追赶模式——不逐日连续结算，而是在加速结束时一次性批量追赶整个时间段的模拟效果（含跨午夜时的每日结算补执行）"

### 🔴 问题2：NPC间互动结算触发器三文档不一致

**涉及文档**：《NPC》§4.3 vs 《V3.0》§3.5

**矛盾描述**：
- NPC §4.3 定义三个结算时机："每游戏日结束时"、"**玩家离开一个场景时**"、"世界规则引擎推送区域状态变更时"
- V3.0 §3.5 只定义了一个时机："游戏内每经过1天（午夜跨过）→ NPC行为系统完整结算"
- "玩家离开场景"这个触发器在总纲中完全缺失

此外，"玩家离开一个场景"没有定义什么算"离开"——换Location？换Region？进入加速模式？

**修改建议**：
- V3.0 §3.5 增加："玩家离开一个场景（跨Region移动）时：触发该场景内NPC的即时互动结算（轻量，仅涉及当前在场的NPC对）"
- NPC §4.3 明确"离开场景"的定义："玩家从一个Region移动到另一个Region时触发"
- NPC §4.3 的"世界规则引擎推送区域状态变更时"拆分为两个通道（见问题10）：
  - **即时推送**（玩家行动触发阈值跨越）→ NPC 立即执行中断检查
  - **每日推送**（常规每日结算结果）→ 与每日结算合并处理

### 🔴 问题3：SimulationFreeze 的 freezeBehavior 枚举在两份文档中不对称

**涉及文档**：《NPC》§7.3 vs 《世界规则引擎》§6.4

**矛盾描述**：

| 系统 | 支持的 targetType | freezeBehavior 枚举 |
|------|-------------------|---------------------|
| NPC | `"npc" \| "faction" \| "region"` | `full` / `needs_only` / `position_only` |
| 世界规则引擎 | `"faction" \| "region"` | `full` / `resources_only` |

问题：
1. NPC 文档声称 `targetType` 包含 `"faction"` 和 `"region"`，但 NPC 系统自身不管理势力/区域——它只有 NPC。势力/区域的冻结应由世界规则引擎处理。
2. 对于同一个 `targetType: "faction"`，NPC 系统定义了 `needs_only` 模式但世界规则引擎没有——如果 PlotManager 发出 `{targetType: "faction", freezeBehavior: "needs_only"}`，NPC 系统能解释但世界规则引擎无法解释。
3. 枚举值语义不对齐：NPC 的 `needs_only`（冻结行为决策，需求继续增长）和世界规则的 `resources_only`（冻结冲突和事件，资源继续更新）是不同的概念，但名称暗示相似语义。

**修改建议**：
- NPC 文档 §7.3 的 `targetType` 改为仅 `"npc"`（NPC 系统不管理势力/区域级别的冻结）
- 在 PlotManager 层面定义统一的 `SimulationFreeze` 枚举，分发给各子系统时按 targetType 路由：
  - `targetType = "npc"` → 仅发给 NPC 系统，行为枚举：`full` / `needs_only` / `position_only`
  - `targetType = "faction" | "region"` → 仅发给世界规则引擎，行为枚举：`full` / `resources_only`
- 或者在三份文档中统一定义一个顶层 `SimulationFreeze` 协议，由 PlotManager 负责拆分路由

### 🔴 问题4：SimulationFreeze 超时自动解冻默认值不一致

**涉及文档**：《世界规则引擎》§6.4 vs 《NPC》§7.3

**矛盾描述**：
- 世界规则引擎 §6.4：`maxFreezeDays: Int (超时自动解冻，默认5天)`
- NPC §7.3：`maxFreezeDays: Int (超时自动解冻，默认3天)`

同一字段名、同一语义（超时保护）、同一协议（SimulationFreeze），但默认值不同。如果 PlotManager 发出一个不指定超时的冻结请求，NPC 在 3 天后解冻恢复自主行为，而势力资源池还要等 2 天才解冻。这会导致：NPC 因饥饿去领物资，但势力资源仍被冻结无法分发——逻辑断裂。

**修改建议**：统一为 5 天。由 PlotManager 在构造 `SimulationFreeze` 时强制指定 `maxFreezeDays`，不为空时覆盖子系统默认值。

### 🟡 问题5：食物需求锁死时间在每日结算粒度下的语义模糊

**涉及文档**：《NPC》§3.3

**问题描述**：
"食物需求：进食后归零，饱食度满后锁死24游戏小时"

在每日结算粒度下，24游戏小时恰好等于一次结算间隔。这意味着"锁死24小时"="跳过下一次每日结算的食物需求增长"。但如果进食发生在两次结算之间（由玩家行动触发），锁死计时从何时开始？锁死到期时恰好落在下一次结算还是两次结算之间？

**修改建议**：改为："食物需求：进食后归零，下一次每日结算时跳过食物需求的推进（等效锁死24游戏小时）。若进食发生在两次结算之间，以最近一次结算为基准计算。"

### 🟡 问题6：NPC跨Region移动的通知协议未定义

**涉及文档**：《NPC》§3.1.1 vs 《世界规则引擎》§2.4

**问题描述**：
- NPC §3.1.1："NPC 跨 Region 移动时：原势力人口-1，目标 Region 势力人口+1"——暗示NPC系统执行移动
- 世界规则引擎 §2.4："NPC跨区域移动 → 世界规则引擎收到通知"——暗示被动接收

两者都没有定义通知的数据格式、调用时机（移动决策时立即通知还是每日结算时批量通知）、以及NPC更换势力归属时如何更新关系矩阵。

**修改建议**：在世界规则引擎 §6.1 中增加一个 `NpcMovementNotification` 数据结构：
```
NpcMovementNotification {
  npcId: String
  fromRegion: RegionId
  toRegion: RegionId
  oldFaction: FactionId?
  newFaction: FactionId?
  timestamp: GameDateTime
}
```
NPC行为系统在NPC移动决策生效时立即发送此通知，世界规则引擎据此更新势力人口统计。

### 🟡 问题7：NPC好感度修改权限在V3.0三层分级下的归属矛盾

**涉及文档**：《V3.0》§2.2 vs 《NPC》§7.3

**问题描述**：
- V3.0 §2.2 数据权威表：NPC好感度 → 来源"世界规则引擎、NPC行为系统" → 修改权限"仅模拟层可修改"
- NPC §7.3："剧情管理器可覆盖NPC的特定状态（如强制好感度变化、强制位置变更）"

模拟层权威和剧情管理器覆盖权限之间存在优先级矛盾。如果 PlotManager 强制设定了好感度=+80（跨越到"信任"阶段），这算不算"模拟层修改"，还是"剧情覆盖"？NPC行为系统的阈值检测（NPC §3.5 "阶段跨越触发AI评估"）是否应该对剧情覆盖的变化也触发？

**修改建议**：在 V3.0 §2.2 的"修改权限"列中增加脚注："* 剧情管理器在关键节点期间可通过 SimulationFreeze 协议临时获得覆盖权限，覆盖操作标记为 `source: plot_override`，不触发阈值AI评估。节点完成后权限归还模拟层。"

### 🟡 问题8：V3.0 §3.5 中"生存状态机被动消耗"的归属位置误导

**涉及文档**：《V3.0》§3.5

**问题描述**：
当前 §3.5 将"生存状态机按玩家实际消耗的时间推进被动消耗"放在"每游戏日"的 bullet 下，与 NPC 每日结算和世界规则引擎每日结算并列。但实际上玩家的被动消耗是**跟玩家行动走的**（每次 processPreRuling 按玩家的行动时间推进），不是跟每日结算走的。放在每日结算 bullet 下会造成"玩家被动消耗也是每日一次"的误解。

**修改建议**：将生存状态机被动消耗从每日 bullet 中提出，作为独立段落："生存状态机的被动消耗不跟随每日结算——每次玩家行动时，按该行动消耗的实际时间推进（与V2.x逻辑一致）。"

### 🟡 问题9：NPC 位置更新与行为决策的粒度混淆

**涉及文档**：《NPC》§3.2 vs §4.1

**矛盾描述**：
- §3.2 定义精细时间表（清晨→诊所、上午→食堂、下午→哨塔），暗示 NPC 位置随 GameClock 实时变化
- §4.1 和 §3.3 强调"行为决策在每日结算时统一判定"

核心模糊点：行为决策（如饥饿 NPC 决定去抢粮）产生的**位置覆盖**持续多久？三种可能均未在文档中定义：
1. 覆盖直到需求满足
2. 覆盖到下一个时间表时段
3. 覆盖到下一次每日结算

此外，时间表驱动的常规位置变化（查表）与需求驱动的紧急位置变化（覆盖）之间的切换协议缺失。

**修改建议**：
- 明确"位置"分为两种来源：**时间表查表**（跟随 GameClock 实时，非决策）和**行为决策覆盖**（每日结算触发）
- 定义覆盖时长规则：生存需求覆盖 → 持续到需求满足或下次每日结算（以先到者为准）；安全需求覆盖 → 持续到威胁解除
- 覆盖解除后 NPC 回归当前时段的时间表位置，记录位置恢复事件

### 🟡 问题10："玩家即时行动"触发的规则引擎推送不应合并到每日结算

**涉及文档**：《V3.0》§5.1、《世界规则引擎》§4.2、《NPC》§4.3

**矛盾描述**：
问题 2 的原始修改建议是将"世界规则引擎推送区域状态变更时"合并到每日结算中。但这一建议忽略了 V3.0 §5.1 的"直接影响"路径：

> 通过裁决Agent→ActionResult→生存状态机，影响当前场景的状态（如炸毁军火库→该区域物资-30%）。立即反映在模拟层数据中。

推演：玩家炸毁军火库 → 裁决Agent判定生效 → 弹药储备跨过世界规则引擎 §4.2 危机阈值 → 触发即时 AI 评估 → NPC 系统应在下一秒就收到通知。如果将推送合并到每日结算，NPC 对重大变故的响应会延迟最长 24 游戏小时——一个哨兵在军火库被炸后继续站岗一整天，叙事上不可接受。

**修改建议**：NPC §4.3 保留双通道推送，与问题 2 的修正建议对齐：
- **即时推送通道**：玩家行动触发世界规则引擎阈值跨越时，规则引擎立即推送变更给 NPC 系统
- **每日推送通道**：常规每日结算结果，与每日结算合并处理
- 世界规则引擎 §6.1 增加即时推送的触发条件说明

### 🟢 问题11：V3.0 路线图中 V2.5 优先级标记细节

**涉及文档**：《V3.0》§9

**问题描述**：
- 修订后 V2.5（世界规则引擎）优先级标记为 🔴 最高
- 修订后 V2.6（NPC行为系统）优先级标记为 🔴 最高
- 但备注中写"可并行于V2.5"

将 V2.6 从原来的 🟡 高 升级为 🔴 最高 是正确的（因为弱依赖允许并行），但需要明确并行开发的前提条件，避免两个团队各自定义数据模型导致后续集成冲突。

**修改建议**：在备注中说明："并行开发的前提是世界规则引擎先完成数据模型定义（§2.1-2.4），NPC系统基于共享数据模型开始实现。"

### 🟢 问题12：加速模式中NPC行为完全空白

**涉及文档**：《V3.0》§3.3、《NPC》全文

**问题描述**：
V3.0 §3.3 详细描述了加速模式中**玩家**的自动导航行为，但完全没有提及加速模式中**NPC**的行为。NPC 是跟随加速时间正常运转（时间表推进、需求增长、互动发生），还是暂停等待玩家恢复正常速度？

如果 NPC 正常运转，世界叙事Agent需要在摘要流中报告 NPC 的显著行为（"在你休息的8小时里，哨兵老张因伤口感染去世了"）。如果 NPC 暂停，则世界在加速期间是"死的"，违背了 V3.0 "世界持续运转"的核心设计目标。

**修改建议**：在 V3.0 §3.3 加速模式中增加一条：
"8. NPC行为系统在加速期间以批量追赶模式运行——不逐小时结算，加速结束时一次性推进NPC的时间表、需求和互动。世界叙事Agent的摘要流中包含显著NPC行为（死亡、离开、关系阶段跨越）。"
