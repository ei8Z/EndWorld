# 世界规则引擎详细设计文档 V1.0

> **所属项目**：末日求生 · AI叙事游戏 V3.0
> **模块定位**：模拟层核心——管理全球范围的宏观状态变化
> **设计原则**：确定性规则引擎，日常结算零AI调用，仅在阈值触发时使用轻量AI评估（见§4），配置驱动
> **参考模型**：池-流模型（系统动力学）+ 区域所有权 + 兰彻斯特战斗结算 + SIR事件传播


## 一、模块职责

世界规则引擎是V3.0模拟层的核心组件。它负责在玩家不行动时，持续推动世界状态的演变。

**它做什么**：
- 每游戏日结算一次全球状态
- 管理势力、区域、资源、事件四大类数据
- 输出结构化的状态变更列表
- 检测质变阈值，触发AI评估

**它不做什么**：
- 不生成叙事文本（由世界叙事Agent负责）
- 不模拟单个NPC行为（由NPC自主行为系统负责）
- 不处理玩家行动的直接后果（由裁决Agent负责）


## 二、数据模型

### 2.1 区域

世界被划分为若干区域。区域是模拟的基本空间单元。

**区域属性**：

| 属性 | 类型 | 说明 |
|------|------|------|
| 区域ID | 唯一标识 | — |
| 区域名称 | 显示文本 | — |
| 地形类型 | 枚举 | 城市废墟/郊区/荒野/水域/山地 |
| 资源丰度 | 0-100 | 该区域自然资源的丰富程度（影响食物生产和物资搜索） |
| 威胁等级 | 0-100 | 该区域的危险程度（影响事件触发概率和行动DC） |
| 控制势力ID | 势力ID或null | 当前控制该区域的势力（null=无主之地） |
| 相邻区域列表 | 区域ID数组 | 决定移动路径和事件传播方向 |
| 连接强度 | 与相邻区域对应的强度数组 | 道路=高，荒野=低，河流=中 |
| 末日等级影响系数 | 0.0-2.0 | 该区域对末日等级的敏感度（城市废墟高，荒野低） |
| 状态标签 | 字符串数组 | 如“断电”、“辐射污染”、“尸潮经过” |

**设计要点**：
- 区域按叙事重要性划分，非均匀大小。一个关键的医院可以单独成为一个区域，而一大片无人荒野可以是一个大区域。
- 初始配置由作者设定，不同末日类型（丧尸/核战/凛冬）使用不同的区域配置文件。

### 2.2 势力

势力是世界中的主要行为体。每个势力控制若干区域，拥有资源池。

**势力属性**：

| 属性 | 类型 | 说明 |
|------|------|------|
| 势力ID | 唯一标识 | — |
| 势力名称 | 显示文本 | — |
| 势力类型 | 枚举 | 军事组织/幸存者聚居地/匪帮/游荡群体/官方残余 |
| 人口 | 整数 | 势力总人数 |
| 兵力 | 整数 | 可用于战斗的人数（人口×武装率） |
| 武装程度 | 0.0-1.0 | 兵力/人口 |
| 单位战力系数 | 浮点数 | 单个士兵的战斗力（受装备、训练影响） |
| 控制区域列表 | 区域ID数组 | — |
| 势力关系矩阵 | 势力ID→关系状态映射 | 同盟/中立/敌对/求援中 |
| 领袖性格 | 枚举 | 谨慎保守/激进扩张/外交优先/自保为主 |
| 势力目标 | 枚举 | 扩张/防守/撤离/寻求同盟 |
| 状态标签 | 字符串数组 | 如“内部动荡”、“食物短缺”、“扩张中” |

**势力资源池**：

| 资源池 | 类型 | 说明 |
|--------|------|------|
| 食物储备 | 浮点数 | 单位：可维持人口天数 |
| 水资源 | 浮点数 | 单位：可维持人口天数 |
| 医疗物资 | 浮点数 | 单位：人口天等效。1单位=1人口天的日常防疫。伤病治疗消耗20单位/人次（≈1个标准医疗包）。与§3.1换算表对齐 |
| 弹药储备 | 浮点数 | 单位：可支持战斗次数 |
| 士气 | 0-100 | 影响战斗力和稳定性 |

### 2.3 全局事件

全局事件是世界规则引擎产出的”正在发生的事”。它们在地理上传播，随时间消退。

**事件产生规则**：

全局事件有三种产生途径：

| 产生途径 | 触发条件 | 频率限制 | 说明 |
|----------|----------|----------|------|
| 概率自动生成 | 每日结算时，每个势力/区域有基础概率触发新事件 | 每势力每日最多1个；全局每日最多N个（N=max(势力数×0.3, minEventsPerDay)，minEventsPerDay为配置参数，默认值：丧尸末日=1，核战凛冬=0，内战崩溃=1） | 模拟末日环境中的随机变故 |
| 阈值触发 | 势力/区域指标跨过危机阈值时（§4.1） | 跟随阈值检测 | 由状态恶化自然引发的事件 |
| AI评估产生 | AI评估输出中包含 `newEntities` 或建议的新事件 | 跟随AI评估频率 | AI推断的质变后果 |

概率自动生成的参数：
- 基础生成概率 = 0.03/势力/日（每天3%概率产生一个新事件）
- 事件类型由势力所在区域的地形类型和末日类型决定（如城市废墟→匪帮/军事冲突概率高；水域→疫病概率低）
- 事件源区域从势力的控制区域中随机选取
- 事件强度 = 50 + 随机浮动（±30），受末日等级修正
- 若当天AI评估已产生事件，概率自动生成跳过该势力

> **概率模型与保底机制的关系**：在势力数量较少（<30个）的典型配置中，实际事件生成主要由 `minEventsPerDay` 保底机制驱动（期望事件数 = 势力数×0.03，以10个势力为例仅0.3个/日，远低于保底值1个/日）。这不是设计缺陷——保底机制确保小规模世界仍然有足够的事件密度以维持末日氛围。概率模型在势力数量增长（如扩展到30+势力的大型世界配置）后逐渐成为主导。

**事件属性**：

| 属性 | 类型 | 说明 |
|------|------|------|
| 事件ID | 唯一标识 | — |
| 事件类型 | 枚举 | 尸潮/难民潮/军事冲突/疫病/谣言/资源发现 |
| 当前影响区域 | 区域ID数组 | 当前正在受影响的区域 |
| 传播速率 | 0.0-1.0 | 每天传播到相邻区域的概率 |
| 剩余持续天数 | 整数 | 到达0后事件消退 |
| 强度 | 0-100 | 影响程度 |
| 源区域 | 区域ID | 事件最初爆发的区域 |
| 关联势力 | 势力ID或null | 事件的发起方或相关方 |


### 2.4 势力-区域-NPC 关联模型

> 与NPC行为系统文档 §3.1.1 对齐。三者层级关系如下：

```
世界规则引擎管理                      NPC行为系统管理
┌─────────────────┐                ┌─────────────────┐
│ 势力(Faction)    │──控制────────→│ 区域(Region)     │
│ · 资源池         │                │ · 威胁等级       │
│ · 兵力/士气      │                │ · 资源丰度       │
│ · 控制区域列表   │                │ · 包含多个场景    │
└─────────────────┘                └────────┬────────┘
                                            │ 包含
                                            ▼
                                ┌─────────────────┐
                                │ 场景(Location)   │
                                │ · NPC可位于此    │
                                └────────┬────────┘
                                         │ 位于
                                         ▼
                                ┌─────────────────┐
                                │ NPC             │
                                │ · 所属势力=所在  │
                                │   区域的控制势力  │
                                │   (默认，可覆盖) │
                                └─────────────────┘
```

**关联规则**：
- 区域是模拟的基本空间单元，场景(Location)是区域内的具体地点
- 背景NPC的群体标签绑定在区域级别，人口数量计入控制势力的总人口
- NPC跨区域移动 → NPC行为系统发送 `NpcMovementNotification`（见§6.1）→ 世界规则引擎据此更新：原势力人口-1，目标区域势力人口+1
- 势力废弃/失去一个区域时，该区域内的所有NPC触发"迁移"或"脱离势力"判定

## 三、核心算法

### 3.1 资源更新：池-流模型

**基础更新公式**（每游戏日执行，每种资源池使用独立的消耗逻辑）：

```
食物储备 = 食物储备 + 食物生产 - 食物消耗 - 食物损耗
  食物生产 = Σ(控制区域的 食物丰度 × 区域末日等级影响系数) × 采集效率
  采集效率 = 基础采集率 × 季节修正 × 末日等级修正 × 人力修正
  食物消耗 = 人口 × 人均日食物消耗（1人口天）
  食物损耗 = 食物储备 × 损耗率

水资源 = 水资源 + 水生产 - 水消耗 - 水损耗
  水消耗 = 人口 × 人均日水消耗（1人口天） × 天气修正（炎热×1.3，正常×1.0，寒冷×0.8）
  水损耗 = 水资源 × 损耗率

医疗物资 = 医疗物资 + 医疗生产 - 日常防疫消耗 - 额外伤病治疗消耗 - 医疗损耗
  日常防疫消耗 = 人口 × 人均日医疗消耗（1单位/人日，即0.05个标准医疗包）
  额外伤病治疗消耗 = 治疗次数 × 20单位/次（由NPC系统每日结算时反馈治疗次数）
  医疗损耗 = 医疗物资 × 损耗率

弹药储备 = 弹药储备 + 弹药生产 - 弹药消耗
  弹药消耗 = 仅在战斗结算时产生（兰彻斯特公式输出弹药消耗率，每场战斗消耗 弹药储备 × 消耗率）。非战斗日无弹药消耗。

士气值变化不参与池-流公式，由事件、战斗结果、领袖决策直接增减。
```

**标准单位换算**（1人口天 = 1个成年人1天的基本生存需求）：

| 资源类型 | 1人口天对应 | 备注 |
|----------|------------|------|
| 食物 | 2000 kcal ≈ 500g 干粮 / 1.0 份标准口粮 | 与V2.3物品系统的"食物份"和"干粮重量"对应 |
| 水 | 3000 ml（饮用+基本卫生） | 与V2.3的ml计量直接对应 |
| 医疗物资（日常防疫） | 1人次的日常防疫保障 ≈ 0.05 个标准医疗包 | 预防性消耗（消毒、绷带更换、预防用药），计入宏观公式中的人口 × 人均日消耗。1个标准医疗包 = 20人口天的日常防疫物资 |
| 医疗物资（伤病治疗） | 1人次伤病治疗 ≈ 1.0 个标准医疗包 = 20 单位 | 治愈一次实际伤病（手术、伤口缝合、感染处理），从势力资源池额外扣除。与玩家使用1个完整医疗包的成本等价 |
| 弹药 | 不直接换算为人口天 | 弹药通过影响战斗结算（单位战力系数）间接关联 |

玩家与势力交互（捐赠/领取/偷窃物资）时，系统自动按此标准换算。

**宏观消耗与个体消耗的协调规则**：
- 宏观公式（人口 × 人均日消耗）为"理论消耗上限"，用于每日结算时的势力资源池扣减
- 接触NPC的个体消耗（进食、饮水）不从势力资源池中再次扣除——其份额已包含在宏观扣减中
- 换算关系：1个接触NPC的日消耗 = 1人口天。宏观公式中的人口参数 = 背景NPC人口 + 接触NPC数量
- 玩家自身的势力资源消耗（加速模式自动导航、正常模式捐赠/领取）同步调整模拟层资源池——因为玩家的消耗不在"人口 × 人均消耗"的计算范围内（玩家不计入势力人口）

**正常速度下玩家与势力物资交互流程**：
1. 玩家发出物资交互行动（捐赠/领取/偷窃）
2. 若为捐赠或合法领取 → 跳过裁决Agent判定（非对抗行动），由 GameRepository 直接执行换算（按标准单位换算表）和扣除/添加
3. 若为偷窃 → 经过裁决Agent判定（对抗行动），成功后执行换算
4. 势力资源池变更后立即触发阈值检查（可能触发即时推送，见§4.2）

**关键修正系数**：

| 修正项 | 取值范围 | 说明 |
|--------|----------|------|
| 季节修正 | 0.3-1.5 | 冬季低，秋季高 |
| 末日等级修正 | 1.0-2.0 | 等级越高，采集效率越低（环境恶化） |
| 人力修正 | 0.1-1.0 | 人口中可用于采集的比例。自动推导：人力修正 = max(0.1, 1.0 - 武装率 - 伤病率)。武装率 = 兵力/人口（战斗人员被占用）；伤病率 = 受伤人口/总人口；下限0.1确保总有最基本劳动力 |
| 区域末日等级影响系数 | 0.0-2.0 | 每个区域的独立系数（城市废墟高，荒野低） |
| 损耗率 | 0.01-0.05 | 每天自然损耗比例 |

**伤病率的计算来源**（人力修正公式的依赖变量）：
人力修正公式中使用的 `伤病率 = 受伤人口/总人口` 由世界规则引擎在每日结算 Step 2 状态检查时计算：
- 世界规则引擎维护一个势力级估算值 `estimatedInjuryRate`（浮点数，0.0-1.0），初始值为 0
- 每次收到 CasualtyReport 时，将 `newInjuries` 条目数量 / 势力总人口 累加到 `estimatedInjuryRate`
- 每日结算时，根据 NPC 行为系统反馈的"势力自动分配治疗次数"，按 `治疗次数 / 势力总人口` 扣减 `estimatedInjuryRate`
- 同时使用群体标签中的伤亡描述作为辅助校验：群体状态"最近伤亡X人"中的 X/总人口 ≈ `estimatedInjuryRate`（允许 20% 偏差，用于日志警告）
- `estimatedInjuryRate` 下限 0，无上限但实际不会超过 1.0
- 此估算值不需要精确到个体——人力修正本身就是一个宏观系数，10% 的偏差不影响资源生产的大趋势

**阈值检测**：
- 食物储备 < 人口×7天 → 标记”食物短缺”（警告）
- 食物储备 < 人口×3天 → 标记”饥荒”，触发AI评估（危机，与§4.1势力级阈值对齐）
- 水资源、医疗物资、弹药类似逻辑

### 3.2 势力控制：区域所有权

**控制判定规则**：
- 一个区域同时只能被一个势力控制
- 势力可以控制与已有区域相邻的区域（通过扩张）
- 无主区域自动被相邻势力的最强方“宣称”（但不一定控制）

**控制变更触发条件**：
- 势力主动放弃（资源不足维持）
- 被敌对势力攻占（战斗结果）
- 势力解散（触发AI评估，区域变为无主或有新势力填补）

### 3.3 战斗结算：兰彻斯特平方律

**适用场景**：两个敌对势力在相邻区域发生冲突时。

**结算公式**：

```
势力A战斗力 = (兵力A)² × 单位战力系数A
势力B战斗力 = (兵力B)² × 单位战力系数B

战力比 = 战斗力A / 战斗力B

势力A战损比例 = √(1 / 战力比)  （若战力比≥1，即A占优）
势力B战损比例 = √(战力比)      （若战力比≥1，即B劣势）

最终：
  势力A剩余兵力 = 兵力A × (1 - 战损比例)
  势力B剩余兵力 = 兵力B × (1 - 战损比例)
```

**直觉解释**：
- 战力比=2:1 → 强者战损约30%，弱者战损约70%
- 战力比=4:1 → 强者战损约50%，弱者几乎全灭
- 兵力优势比质量优势更重要（平方项放大了兵力差距）

**宏观战损到微观NPC的映射规则**：

兰彻斯特结算输出的是宏观兵力损失（百分比），需要映射到具体的NPC实体：

1. **兵力损失首先由背景NPC（第一层）吸收**：背景NPC人口按其所在区域的比例分摊战损。背景人口减少同步更新区域群体标签（如"最近伤亡X人"）。
2. **背景NPC不足时的溢出规则**：若背景人口不足以吸收全部战损（背景人口 < 战损人数），超出部分从该势力控制区域内的接触NPC中随机选取。
3. **接触NPC被选中死亡的概率修正**：
   - 非战斗身份NPC（平民、商人、工匠）：死亡概率 × 0.3
   - 战斗身份NPC（哨兵、士兵、守卫）：死亡概率 × 1.0
   - 关键NPC：死亡判定前触发轻量AI评估（允许叙事保护但非绝对豁免——AI有权判定关键NPC在特定情境下死亡）
4. **势力覆灭处理**：势力兵力降至0时，所有剩余接触NPC触发"迁移"或"被俘"判定（见NPC文档§4.4）
5. **伤亡名单推送**：每次战斗结算后，向NPC行为系统推送伤亡名单，包含：
   ```
   CasualtyReport {
     casualties: [{npcId?, "background"}, ...]  // null npcId表示背景NPC人口
     survivors: [npcId, ...]                     // 幸存的接触NPC
     newInjuries: [{npcId, severity}, ...]       // 新增伤病的接触NPC
   }
   ```
   NPC行为系统据此更新接触NPC的状态（死亡标记/伤病标记）。

**冲突概率**：

```
冲突概率 = 基础概率 × 兵力比因子 × 资源压力因子 × 领袖性格因子

基础概率 = 0.05（每天5%基础概率）
兵力比因子 = min(己方兵力/敌方兵力, 2.0)（兵力优势方更倾向进攻）
资源压力因子 = 1.0 + (1.0 - 食物储备/安全线)（资源越紧张越倾向进攻）
领袖性格因子 = 激进1.5 / 保守0.5 / 正常1.0
```

**弱势方修正与第三方介入**（防止"强者恒强"单极霸权）：

兵力比因子的 `min(己方兵力/敌方兵力, 2.0)` 设计意味着优势方更倾向进攻、劣势方倾向防守——这反映了末日世界中势力对实力差距的理性评估。但以下条件触发例外：

- **弱势方绝境反击**：若己方兵力/敌方兵力 < 0.3 且己方士气 ≥ 50，兵力比因子取反转为 2.0（弱势方在绝境中拼死一搏）。若士气 < 50 且兵力比 < 0.2，跳过冲突判定——势力直接溃败或投降
- **第三方介入条件**：若交战双方兵力差距 > 3:1，相邻的第三方势力在满足以下任一条件时，有概率介入协防弱势方：
  - 与弱势方有"同盟"关系（介入概率 60%）
  - 与弱势方有"中立偏友好"关系且与强势方为"敌对"（介入概率 30%，满足"唇亡齿寒"逻辑）
  - 介入方能从战斗中获取高额报酬（如强势方资源储备 > 弱势方的 5 倍，此时介入成功可瓜分战利品，介入概率 20%）
- 势力濒临覆灭（兵力 < 总人口×5% 的危机阈值，见 §4.1）时，触发 AI 评估——AI 可能生成新的同盟、外部干涉，或判定势力解散。AI 评估结果覆盖上述概率判定

此设计意图：强者吞并弱者是末日世界的自然规律，但弱者并非毫无还手之力——忠诚度（士气）、外交关系（同盟）和第三方自利动机（战利品）为多极动态平衡提供了机制。完全的"单极霸权"只有在所有平衡机制都失效后才可能出现——这本身就是一个值得叙事的重大世界事件。

### 3.4 事件传播：SIR模型变体

> **与现有事件系统的关系**：V3.0的三层事件体系中，本节的SIR传播模型管理第一层（全局事件）。第二层（区域事件）由全局事件传播自动产生。第三层（遭遇事件）由现有 `EventDeck`（26张冷却制事件卡）继续管理，服务于裁决Agent的行动判定。现有 `WorldEventManager`（8个按天数触发的预设事件）将在 V3.0 时标记 `@Deprecated`，其功能由全局事件引擎替代。

**适用场景**：全局事件在地理上的扩散。

**传播规则**（每游戏日）：

```
对每个活跃事件的每个受影响区域：
  对每个相邻区域：
    若相邻区域尚未受影响：
      传播概率 = 基础传播率 × 连接强度修正 × 区域类型修正
      若随机判定通过 → 相邻区域加入受影响列表

基础传播率 = 0.3（每天30%概率传播到一个相邻区域）
连接强度修正 = 道路1.5 / 荒野0.5 / 河流0.8
区域类型修正 = 城市废墟1.2 / 郊区1.0 / 荒野0.6 / 水域0.3
```

**事件消退**：
- 每天剩余持续天数-1
- 归零后，事件从活跃列表移除
- 受影响区域的状态标签更新（如“尸潮经过”改为“尸潮后恢复中”）

**事件叠加**：
- 同一区域可同时受多个事件影响
- 叠加时威胁等级累加，但不超过100
- 世界叙事Agent收到叠加事件的描述（如“尸潮+疫病=绝望之地”）


## 四、阈值检测与AI触发

### 4.1 阈值定义

世界规则引擎维护一组预设阈值。每次状态变更后，检查是否有指标跨过阈值。

**势力级阈值**：

| 指标 | 警告阈值 | 危机阈值 | 触发内容 |
|------|----------|----------|----------|
| 食物储备 | <7天 | <3天 | 势力生存危机，评估解散/求援/掠夺可能性 |
| 兵力 | <总人口×10% | <总人口×5% | 势力防御崩溃，评估投降/逃亡/最后抵抗 |
| 士气 | <30 | <15 | 内部动荡，评估哗变/分裂/领袖更替 |
| 控制区域数 | 减少50% | 减少80% | 势力收缩或濒临覆灭 |

**区域级阈值**：

| 指标 | 警告阈值 | 危机阈值 | 触发内容 |
|------|----------|----------|----------|
| 威胁等级 | >60 | >85 | 区域失控，评估居民撤离/势力放弃 |
| 资源丰度 | <20 | <5 | 资源枯竭，评估该区域是否彻底废弃 |

> **NPC个体级别的阈值检测**（如好感度跨越、生存状态突变）由NPC行为系统负责，见《NPC自主行为系统》§3.5"阶段跨越"。世界规则引擎仅管理势力级和区域级阈值。

### 4.2 AI评估流程

当阈值被跨越时：

1. **冻结当前状态**：保存触发阈值时的完整世界状态快照
2. **收集上下文**：收集影响该评估的所有相关数据（周边势力、区域状态、历史事件、NPC信息）
3. **组装AI请求**：结构化输入，描述触发事件和当前全局状态
4. **调用轻量AI**：非独立Agent，一次对DeepSeek的标准调用（非流式，max_tokens=1024）
5. **接收结构化输出**：AI返回局势分析和可能的演变方向
6. **更新世界状态**：将AI评估结果转化为具体的数据变更
7. **记录评估日志**：保存评估的输入和输出，用于调试和回溯

**AI评估的输入结构**：

```
【触发事件】：[阈值类型] [势力/区域名称] [具体指标] 从[旧值]变为[新值]，跨过[阈值线]

【当前世界状态】：
- 相关势力：[势力名称]（人口/兵力/资源/控制区域/领袖性格）
- 周边势力：[列表及关系]
- 相关区域：[区域名称]（威胁/资源/控制者）
- 当前季节：[季节] | 末日等级：[等级]
- 近期相关事件：[最近发生的与该势力/区域相关的事件摘要]

【请评估】：
1. 该势力/区域最可能做出的反应是什么？
2. 这对周边势力会产生什么连锁影响？
3. 是否有新的势力或群体应该出现？
4. 输出结构化JSON，不要叙事文本。
```

**即时推送 vs 每日推送**：

阈值跨越有两种触发路径，推送方式不同：

| 触发路径 | 触发来源 | 推送方式 | 说明 |
|----------|----------|----------|------|
| 每日结算触发 | Step 2 状态检查 | 每日推送（与每日结算合并） | 常规资源消耗导致的阈值跨越 |
| 玩家行动触发 | 裁决Agent→ActionResult→模拟层修改 | 即时推送 | 玩家行动导致的状态变更跨过阈值（如炸毁军火库→弹药储备骤降） |

即时推送时：世界规则引擎立即将变更推送给NPC行为系统，NPC系统执行中断检查——不等待每日结算。

**AI评估的输出结构**：

```
{
  "evaluation": {
    "triggerType": "势力食物危机",
    "subjectName": "红松幸存者营地",
    "mostLikelyReaction": "向周边势力求援",
    "alternativeReactions": ["内部缩减人口（驱逐老弱）", "转变为掠夺模式"],
    "chainEffects": [
      {"affectedSubject": "蓝河军事哨站", "effect": "收到求援，可能派兵支援或要求合并"},
      {"affectedSubject": "灰烬匪帮", "effect": "察觉红松营地虚弱，可能趁火打劫"}
    ],
    "newEntities": [],
    "stateChanges": [
      {"target": "红松幸存者营地", "attribute": "势力目标", "newValue": "寻求同盟"},
      {"target": "红松幸存者营地", "attribute": "士气", "change": -10}
    ]
  }
}
```


## 五、每日结算流程

世界规则引擎在每个游戏日结束时执行一次完整结算。

```
┌─────────────────────────────────────────────┐
│ Step 1: 资源更新                             │
│ - 遍历所有势力                                │
│ - 更新所有资源池（食物/水/医疗/弹药/士气）      │
│ - 产出：资源变更列表                          │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│ Step 2: 状态检查                             │
│ - 遍历所有势力                                │
│ - 检查各资源池是否跨过阈值                     │
│ - 产出：阈值触发列表（如有）                   │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│ Step 3: 冲突判定                             │
│ - 遍历所有相邻且敌对的势力对                   │
│ - 判定是否发生冲突                            │
│ - 产出：冲突列表                              │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│ Step 4: 战斗结算                             │
│ - 对每场冲突使用兰彻斯特公式                   │
│ - 更新双方兵力、控制区域                      │
│ - 产出：战斗结果列表                          │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│ Step 5: 事件传播                             │
│ - 遍历所有活跃事件                            │
│ - 尝试传播到相邻区域                          │
│ - 检查事件到期                                │
│ - 产出：事件变更列表                          │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│ Step 6: 阈值触发处理                         │
│ - 合并Step 2的阈值触发和Step 4-5产生的新触发   │
│ - 若触发数>1，合并为一次AI评估                 │
│ - 调用AI评估，接收结构化输出                   │
│ - 应用AI输出的状态变更                        │
│ - 产出：AI评估结果                            │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│ Step 7: 汇总输出                             │
│ - 合并所有步骤的变更                          │
│ - 产出：WorldStateUpdate（结构化数据）        │
│ - 存储到数据库                                │
│ - 通知NPC行为系统和世界叙事Agent               │
└─────────────────────────────────────────────┘
```

**性能考量**：
- 以10-20个区域、5-10个势力计算，Step 1-5的计算量在毫秒级
- Step 6仅在阈值触发时执行，大多数游戏日无需AI调用
- 整体结算可在玩家阅读叙事时后台完成，无感知延迟


## 六、与V3其他模块的交互

### 6.1 向NPC行为系统输出

世界规则引擎每日结算后，向NPC行为系统推送（**每日推送通道**）：
- 当前区域的状态变更（威胁等级变化、控制势力变化）
- 全局事件影响（该NPC所在区域是否被事件波及）
- 所属势力的状态变更（食物短缺、士气下降）

此外，当玩家行动导致模拟层数据变更并跨越阈值时，世界规则引擎通过**即时推送通道**立即通知NPC行为系统：
- 触发条件：玩家行动 → 裁决Agent判定生效 → 模拟层数据变更 → 跨过 §4.1 定义的阈值
- 推送内容：变更的区域/势力状态 + 跨越的阈值类型
- NPC行为系统收到即时推送后立即执行中断检查（见NPC文档§4.2-4.3），不等待每日结算
- 示例：玩家炸毁军火库 → 弹药储备跨过危机阈值 → NPC系统立即收到通知 → 哨兵中断当前时间表

NPC行为系统据此更新NPC的位置、状态、需求。

此外，当NPC跨Region移动时，NPC行为系统立即发送 `NpcMovementNotification`：

```
NpcMovementNotification {
  npcId: String
  fromRegion: RegionId
  toRegion: RegionId
  oldFaction: FactionId?
  newFaction: FactionId?
  timestamp: GameDateTime
}
```

世界规则引擎接收此通知后更新势力人口统计：原势力人口-1，目标Region控制势力人口+1（若NPC更换势力归属则同步更新关系矩阵）。

此外，NPC行为系统在接触NPC非战斗死亡或降级时，发送 PopulationChangeNotification（见NPC文档§4.4）。世界规则引擎据此更新势力人口和背景/接触子计数——非战斗死亡（starvation/dehydration/injury_deterioration/environment）使人口-1，降级（demotion_to_background）使背景NPC子计数+1、接触NPC子计数-1，总数不变。

### 6.2 向世界叙事Agent输出

当玩家选择时间跨度行动（block/chapter）或世界事件抵达玩家所在区域时，世界规则引擎提供：
- 期间发生的状态变更摘要
- 影响玩家所在区域的事件描述
- 玩家所在区域的新状态

世界叙事Agent将这些数据转化为时间流逝叙事或世界事件广播。

### 6.3 向裁决Agent输出

裁决Agent在正常行动判定时，接收：
- 玩家所在区域的当前威胁等级
- 玩家所在区域的控制势力及其状态
- 附近NPC的当前状态

这些数据作为裁决的精确输入，替代V2中模糊的“环境描述”。

### 6.4 与剧情管理器的协调：冻结/解冻协议

剧情管理器优先级高于世界规则引擎。当关键剧情节点正在推进时，需冻结相关模拟。

#### SimulationFreeze 规范

与NPC行为系统文档 §7.3 对齐。剧情管理器在关键节点开始时发出冻结请求：

```
SimulationFreeze {
  targetType: "faction" | "region"
  targetIds: [...]
  freezeBehavior: "full" | "resources_only"
  maxFreezeDays: Int (超时自动解冻，默认5天，PlotManager在构造时强制指定)
}
```

> **路由说明**：SimulationFreeze 由 PlotManager 统一发出，按 `targetType` 路由到对应子系统：
> - `targetType = "npc"` → 仅发给NPC行为系统，行为枚举：`full` / `needs_only` / `position_only`
> - `targetType = "faction" | "region"` → 仅发给世界规则引擎，行为枚举：`full` / `resources_only`
> 
> 世界规则引擎不接收 `targetType = "npc"` 的冻结请求。

- `full`：完全冻结——资源不更新、冲突不判定、事件不传播（用于关键战争/外交剧情）
- `resources_only`：仅冻结冲突和事件——资源池继续每日更新（数值变化），但不触发冲突和事件响应

#### 解冻追赶规则

剧情节点完成后，PlotManager 调用 `thaw(targetIds)`：

- 若 `累计冻结天数 = 0`：无追赶，引擎从当前状态继续
- 若 `累计冻结天数 > 0`：执行批量追赶——一次性执行冻结期间跳过的每日结算步骤。对于 `resources_only` 模式，追赶时额外执行冲突判定和事件传播

#### 剧情覆盖权限

- 剧情管理器可覆盖势力/区域的特定属性（如强制设置控制势力、强制变更资源池数值）
- 覆盖操作写入日志，标记为 `source: "plot_override"`
- 剧情覆盖不阻止后续的模拟层自然演变——覆盖只是一个"新基线"


## 七、配置驱动设计

### 7.1 配置文件类型

| 配置文件 | 内容 | 可修改性 |
|----------|------|----------|
| 区域定义 | 区域列表、属性、邻接关系 | 作者设定，不同末日类型用不同配置 |
| 势力初始状态 | 势力列表、初始资源、控制区域、关系 | 作者设定 |
| 算法参数 | 所有公式中的系数和阈值 | 可调优 |
| 阈值定义 | 触发AI评估的具体数值线 | 可调优 |

### 7.2 作者设定示例

作者在创建新游戏时，只需配置：
1. 选择末日类型（自动加载对应的区域和势力配置）
2. 可选调整几个关键参数（世界大小、势力数量、恶化速度）
3. 其余由引擎自动运行

**预设末日类型**：
- **丧尸末日**：威胁来自丧尸密度，势力以幸存者聚居地为主
- **核战凛冬**：威胁来自辐射和低温，资源生产极低
- **内战崩溃**：威胁来自军事冲突，势力以军事组织为主


## 八、开发建议

### 8.1 最小可行实现

首次实现建议只包含：
- 5-8个区域
- 3-5个势力
- 3个资源池（食物、兵力、士气）
- 基础池-流模型
- 简化的冲突判定（跳过兰彻斯特，先用兵力比直接判定胜负）
- 简化的阈值检测（只检测食物和兵力）

这个最小版本可以在2-3天内实现，足以验证整个架构的可行性。

### 8.2 渐进扩展

验证通过后逐步加入：
- 更多资源池（水、医疗、弹药）
- 兰彻斯特战斗结算
- SIR事件传播
- 完整的阈值检测+AI评估

### 8.3 调试与可视化

> **移动端适配**：本项目为 Android 应用。推荐方案：
> - 开发阶段使用 `adb logcat` 输出结构化 JSON 日志，配合桌面端可视化脚本解析
> - 每日结算完成后输出 `WORLD_ENGINE_DAILY_REPORT` JSON 日志标签
> - 阈值触发和AI评估的输入/输出写入 Room DB 调试日志表，供回溯分析

调试功能清单：
- 显示当前所有区域的状态（威胁等级、控制势力、资源丰度）
- 显示当前所有势力的资源池（食物/水/医疗/弹药/士气）
- 显示活跃全局事件列表（含传播路径和剩余天数）
- 显示最近的阈值触发和AI评估日志（含输入/输出完整记录）
- 支持手动触发一次每日结算（跳过时间推进，仅结算当前状态）
