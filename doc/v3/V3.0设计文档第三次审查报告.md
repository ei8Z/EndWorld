### 🔴 深水问题A：宏观战损与微观NPC存活的"映射断层"

**涉及文档**：《世界规则引擎》§3.3 vs 《NPC》§4.4

**问题推演**：

世界规则引擎 §3.3 兰彻斯特平方律结算结果是一个百分比——"势力A损失30%兵力"。"兵力"的基数 = 势力总人口 × 武装率，这是一个宏观统计数据。

NPC §4.4 定义了接触层NPC（第二层）的独立死亡判定条件——"NPC受伤且未获得医疗，或所在场景遭遇灾难"。每个接触NPC是独立实体，拥有自己的HP/伤病状态。

两者之间存在一个**未定义的映射通道**：

**场景推演**：红松营地（人口200，兵力100）与灰烬匪帮（人口80，兵力60）发生战斗。兰彻斯特结算后红松损失30%兵力 = 30人。玩家的朋友"老张"（红松营地哨兵，接触NPC）是否还活着？

- **方案A（不包含）**：30人损失全部来自背景NPC（第一层）。后果——无论红松营地被打得多惨，玩家熟悉的那几个接触NPC（老张、李队长、王医生）永远不死。产生"主角光环"幻觉，严重削弱末日感。
- **方案B（包含）**：从接触NPC中按概率随机挑选死亡。后果——需要一套规则：概率怎么算？接触NPC在战场上的角色（哨兵vs厨师）是否影响死亡概率？关键NPC是否豁免？
- **方案C（混合）**：背景NPC承担大部分损失，但接触NPC有非零死亡概率。后果——概率参数需要设计，否则可能太随机（玩家感到不公平）或太安全（回到方案A）。

**核心缺陷**：文档从未定义从"势力兵力"这个宏观数字到"接触NPC实例集合"的映射。战斗结算时哪些NPC参战？死亡如何选取？这些是实现时绕不开的决策。

**修改建议**：在世界规则引擎 §3.3 末尾增加"宏观战损到微观NPC的映射规则"小节：

```
战损分配规则：
1. 兵力损失首先由背景NPC（第一层）吸收。背景NPC人口按其所在区域的比例分摊战损。
2. 若背景NPC不足以吸收全部损失（背景人口 < 战损人数），超出部分从接触NPC中随机选取。
3. 接触NPC被选中死亡的概率与其"战斗角色"相关：
   - 非战斗NPC（平民、商人）：概率 × 0.3
   - 战斗NPC（哨兵、士兵）：概率 × 1.0
   - 关键NPC：死亡判定前触发轻量AI评估（允许叙事保护但非绝对豁免）
4. 势力兵力降至0时，所有剩余接触NPC触发"迁移"或"被俘"判定。
5. 每次战斗结算后，向NPC行为系统推送伤亡名单（含接触NPC的死亡/重伤/幸存状态）。
```

### 🔴 深水问题B：资源单位"换算黑洞"——玩家精确计量与势力池流的断裂

**涉及文档**：《世界规则引擎》§3.1 vs V2.3物品精确计量（在V3.0 §8.1中保留）

**问题推演**：

V2.3 的物品系统实现了精确计量——玩家背包里的水是 500.0 ml，食物是 1.0 份（具体重量/体积），弹药是 30 发。

V3.0 世界规则引擎 §3.1 定义势力资源池单位为**"人口天数"**（Population Days）——食物储备 = 可维持全势力人口的天数。资源更新公式中的食物生产/消耗/损耗都使用这个宏观单位。

两者之间的换算关系**未在任何文档中定义**。

**场景推演**：玩家决定"捐赠一瓶 500ml 的水给营地"。系统需要：
1. 从玩家背包扣除 500ml 水（V2.3精确计量）
2. 增加营地水资源池（V3.0 人口天数）

问题是：500ml 水 = 多少"人口天数"？

如果换算比例不明确：
- 玩家捐赠100瓶水，营地水资源从"3天"变成"3.001天"→ 玩家觉得捐赠无用，沮丧
- 玩家捐赠1瓶水，营地水资源从"3天"变成"30天"→ 数值崩坏，经济系统失效
- 反之，营地每天消耗200人口天数的水，折算成ml后玩家发现需要搬运一整条河 → 同样崩坏

这不仅是数值平衡问题，更是**两层建模范式之间的通信协议缺失**。V2.3是自下而上（每件物品精确计量），V3.0是自上而下（宏观池流），两者各自独立完整，但缺乏换算标准。

**修改建议**：在世界规则引擎 §3.1 增加"标准单位换算表"：

```
标准单位换算（1人口天 = 1个成年人1天的基本生存需求）：
- 食物：1人口天 = 2000 kcal ≈ 500g 干粮 / 1.0 份标准口粮
- 水：1人口天 = 3000 ml（饮用+基本卫生）
- 医疗物资：1人口天 = 1人次的日常医疗保障（约 0.05 个标准医疗包）
- 弹药：不换算为人口天。弹药通过影响战斗结算间接关联。

玩家与势力交互时，系统自动按此标准换算。
```

同时在 V3.0 §8.1 的"保留的部分"中增加说明：物品精确计量与势力池流之间的换算以世界规则引擎 §3.1 的换算表为准。

### 🔴 深水问题C：跨区域移动时NPC互动基于"陈旧需求"数据

**涉及文档**：《NPC》§4.3 vs §3.3

**问题推演**：

这是一个典型的**时间粒度不一致导致的因果倒置**。

NPC §3.3 明确了每日批量结算策略："需求紧迫度在每游戏日结算时一次性推进24小时……行为决策在每日结算时统一判定，消除'需求触发'与'行为响应'之间的时间差。"

上一轮修订在 NPC §4.3 和 V3.0 §3.5 中增加了"玩家从一个Region移动到另一个Region时，触发该场景内NPC的即时互动结算"。但这个即时结算使用的是 NPC **当前存储的需求值**——即上一次每日结算（午夜）更新的数据。

**场景推演**：现在是游戏内下午3点（距上次午夜结算已过15小时）。玩家从"红松营地"移动到"废墟医院"。NPC老王（在废墟医院）的需求值存储为午夜时的状态——饱食度55/100，尚未触发"饥饿"。玩家移动触发即时互动结算。

但在这15小时里，老王实际上应该已经消耗了约62.5%的日食物需求增量（15/24 × 120 = 75），真实的紧迫度应该是55 + 75 = 130（远超100上限）——他已经很饿了。

然而系统基于"旧需求"做互动判定：老王的需求是55，不会触发"资源分享"或"抢食"行为。玩家下午3点到达，看到一个"不太饿"的老王，正常社交。午夜结算时老王的食物需求突然跳到130，触发抢食——但玩家已经离开了，错失互动机会。

更深层的问题：如果玩家反复在两个Region之间来回移动（触发多次即时互动结算），每次都是基于同样的"旧需求"做判定——NPC就像时间凝固了一样，互动结果不可靠。

**修改建议**：在 NPC §4.3 "结算时机"中增加：

```
跨Region互动结算前的临时需求追赶：
玩家跨Region移动触发即时互动结算前，先对该场景内所有NPC执行一次"轻量需求追赶"——
按"当前GameClock时间 - 上次每日结算时间"的差值，按比例推进需求值。
此追赶仅用于本次互动判定，不写入持久存储（正式写入仍等午夜每日结算）。
若距离上次每日结算不足1小时，跳过追赶。
```

### 🟡 深水问题D：AI评估的"溯源幻觉"——记忆压缩导致因果链断裂

**涉及文档**：《NPC》§3.4记忆系统 vs §3.5阶段跨越AI评估 vs 《世界规则引擎》§4.2 AI评估流程

**问题推演**：

NPC §3.4 记忆系统设计：接触NPC只有3条详细记忆，第4条加入时最旧的一条被压缩为远期摘要（一句话概括）。

NPC §3.5 阶段跨越："若跨越涉及关键NPC，触发轻量AI评估"。

世界规则引擎 §4.2 AI评估流程中接收的输入包括"近期相关事件"和"NPC信息"。

**场景推演（时间线）**：
1. Day 1：玩家救下NPC老张的命（好感度+30）→ 写入详细记忆
2. Day 3：玩家帮老张找到失散的女儿（好感度+25）→ 写入详细记忆
3. Day 7：玩家答应帮老张取药但忘了（好感度-15）→ 写入详细记忆
4. Day 10：玩家给老张送食物（好感度+5）→ 第4条记忆写入，Day 1的"救命之恩"被压缩为远期摘要"玩家曾救过我的命"
5. Day 15：老张好感度累计达到+80，跨越"信任→亲密"边界 → 触发AI评估

AI收到的输入中最相关的是：3条详细记忆（找女儿、忘取药、送食物）和远期摘要（"曾救过我的命"）。AI基于这些信息评估"为什么老张如此信任玩家？"——但最关键的"救命之恩"只有一句摘要，AI无法了解当时的处境、情感强度、具体细节。AI可能基于"找女儿"给出一个OK的评估，但丢失了情感链条中最强烈的一环。

更糟糕的情况：如果远期摘要由多条记忆合并而来（如3条变1条），压缩过程中信息损失更严重。AI评估时看到的是"玩家曾多次帮助我"——完全无法回溯具体因果。

**这不是文档矛盾，而是系统设计层面的因果链断裂风险。** 记忆压缩是必要的性能策略，但压缩与AI评估之间的信息不对称会造成AI输出质量劣化。

**修改建议**：在 NPC §3.5 "阶段跨越"或世界规则引擎 §4.2 中增加：

```
AI评估的增强输入：
当触发好感度阶段跨越的AI评估时，除了NPC行为系统提供的标准上下文外，额外包含：
1. 该NPC的全部详细记忆（当前队列中的所有条目，不压缩）
2. 远期摘要
3. 从MemOS检索与该NPC相关的历史交互片段（若可用，最多3条）
4. 好感度变化的完整时间序列（每个关键变化节点的时间、原因、变化值）

这些增强输入仅供AI评估使用，不改变记忆系统的正常压缩行为。
```

### 🟡 深水问题E：加速模式下自动导航消耗与势力供养的冲突

**涉及文档**：《V3.0》§3.3加速模式 vs §2.2数据权威

**问题推演**：

V3.0 §3.3 加速模式定义了玩家自动导航规则：

> "若背包有食物且饱食度低于阈值→自动进食"
> "若背包有水且口渴度低于阈值→自动饮水"
> "若受伤且有医疗物资→自动使用"

所有自动消耗都来自**玩家背包**。

**场景推演**：玩家在红松营地（友好势力，食物储备充足）养伤。选择加速3天等待伤口愈合。按当前规则：
- 玩家的自动导航每天消耗自己背包里的食物和水
- 3天后，背包应急干粮耗尽
- 但红松营地明明有充足的食物储备（势力池显示"食物储备>30天"），玩家却在营地里"饿着"

叙事上极其荒谬：玩家身处食物充足的友好营地，却在加速期间把自己的干粮吃光了。

更严重的是，这与 V3.0 §2.2 的"世界持续运转"设计目标相悖——加速期间的世界应该是"真实的"，而不是一个玩家背包隔离的真空。

**修改建议**：在 V3.0 §3.3 "加速期间的角色自动导航规则"中增加环境资源判断：

```
自动导航的资源消耗优先级：
1. 若当前Location属于友好/同盟势力（势力关系矩阵中标记为同盟或中立偏友好），
   且该势力的食物/水资源池 > 0：
   - 自动导航优先消耗势力资源池（同步扣除模拟层对应的人口天数）
   - 仅在势力资源耗尽后才消耗玩家背包
2. 若当前Location无友好势力或势力资源耗尽：
   - 使用玩家背包物资
3. 消耗势力资源时，记录消耗量并在加速结束摘要中体现（如"在红松营地休养3天，消耗了营地少量食物和水"）
```

### 🔴 问题1：世界规则引擎内部食物储备阈值双重标准

**涉及文档**：《世界规则引擎》§3.1 vs §4.1

**矛盾描述**：

同一份文档内，对"食物储备"的阈值定义有两套互不兼容的数值：

- §3.1 池-流模型阈值检测：
  - 食物储备 < 人口×3天 → 标记"食物短缺"
  - 食物储备 < 人口×1天 → 标记"饥荒"，触发AI评估

- §4.1 势力级阈值表：
  - 食物储备 < 7天 → 警告阈值
  - 食物储备 < 3天 → 危机阈值，触发"势力生存危机，评估解散/求援/掠夺可能性"

由于食物储备单位就是"可维持人口天数"，两套阈值直接可比：
- §3.1 的"食物短缺"(<3天) 比 §4.1 的"警告"(<7天) 更严格，且 §3.1 没有定义7天警告线
- §3.1 的"饥荒/AI触发"(<1天) 比 §4.1 的"危机/AI触发"(<3天) 更极端，触发时机差了3倍

如果代码同时实现两套标准，同一段食物储备变化会触发不同级别的响应。

**修改建议**：统一使用 §4.1 的三级体系（将 §3.1 改为与 §4.1 一致）：
- 食物储备 < 人口×7天 → 标记"食物短缺"（警告）
- 食物储备 < 人口×3天 → 标记"饥荒"，触发AI评估（危机）
- 删除 §3.1 的 <1天 阈值（已被 <3天 覆盖）

或者按 §3.1 的逻辑，说明 §4.1 的 7天/3天 是设计时占位数值，实际以 §3.1 的 3天/1天 为准。两种方向均可，但必须选一个并保持一致。

### 🔴 问题2：NPC §7.1 未描述即时推送通道

**涉及文档**：《NPC》§7.1 vs 《世界规则引擎》§6.1 vs 《NPC》§4.3

**矛盾描述**：

上一轮审查已在 NPC §4.3 和世界规则引擎 §6.1 中新增了即时推送通道的定义。但 NPC §7.1（"接收：来自世界规则引擎"）仅描述了每日结算后的推送：

> "世界规则引擎每日结算后，向NPC行为系统推送：
> - 当前区域的状态变更（威胁等级变化、控制势力变化）
> - 全局事件影响（该NPC所在区域是否被事件波及）
> - 所属势力的状态变更（食物短缺、士气下降、势力迁移）"

完全没有提及即时推送通道的存在。当开发者阅读 §7.1 作为"模块交互"的入口时，会遗漏整个即时推送机制。

此外，"每日结算后"的限定词暗示只有每日结算才会推送，但 §4.3 和世界规则引擎 §6.1 都定义了非每日结算的即时推送。

**修改建议**：在 NPC §7.1 增加即时推送的描述：

```
此外，当玩家行动导致模拟层阈值跨越时，世界规则引擎通过即时推送通道立即通知：
- 触发条件：玩家行动 → 裁决Agent判定生效 → 模拟层数据跨过阈值（见世界规则引擎§4.1-4.2）
- 推送内容：变更的区域/势力状态 + 跨越的阈值类型
- NPC行为系统收到后立即执行中断检查（见§4.2-4.3），不等待每日结算
```

### 🟡 问题3：世界规则引擎 §2.4 关联规则中NPC移动通知的被动语气未更新

**涉及文档**：《世界规则引擎》§2.4 vs §6.1

**矛盾描述**：

上一轮审查在世界规则引擎 §6.1 中新增了 `NpcMovementNotification` 数据结构，明确了"NPC行为系统主动发送通知"。但 §2.4 的关联规则仍保留了旧文本：

> "NPC跨区域移动 → 世界规则引擎收到通知：原势力人口-1，目标区域势力人口+1"

§2.4 未引用 `NpcMovementNotification`，也未说明通知是 NPC 行为系统主动发送的（语气上仍是世界规则引擎被动接收一个未定义格式的"通知"）。而 §6.1 已经定义了完整的通知结构。

两个章节对同一事物的描述粒度不一致，新读者可能先读到 §2.4 的模糊描述，只有读到 §6.1 才找到数据结构定义。

**修改建议**：将 §2.4 的关联规则改为：

```
- NPC跨区域移动 → NPC行为系统发送 NpcMovementNotification（见§6.1）→ 世界规则引擎据此更新：原势力人口-1，目标区域势力人口+1
```

与 NPC §3.1.1 的表述对齐。

### 🟡 问题4：V3.0 §3.5 "生存状态机被动消耗"与 §8.3 advanceWorldTime 的隐含矛盾

**涉及文档**：《V3.0》§3.5 vs §8.3

**矛盾描述**：

上一轮审查将"生存状态机被动消耗"从每日 bullet 中提出为独立段落：

> §3.5："生存状态机被动消耗：不跟随每日结算——每次玩家行动时，按该行动消耗的实际时间推进（与V2.x逻辑一致）"

但 §8.3 定义了 `advanceWorldTime(hours)` 方法：

> "纯时间推进+被动消耗+模拟层结算，不触发裁决"

此方法用于加速模式或时间追赶场景，在这些场景中**没有玩家行动**（玩家在加速期间不发出具体行动），但被动消耗仍然需要推进（否则加速期间角色不会饥饿/口渴/死亡）。

§3.5 "每次玩家行动时"的表述与 advanceWorldTime 的存在构成矛盾——advanceWorldTime 恰好在没有玩家行动时触发被动消耗。

**修改建议**：将 §3.5 的表述改为：

```
生存状态机被动消耗：不跟随每日结算——在正常/减速模式下跟随每次玩家行动推进，
在加速模式下通过 advanceWorldTime() 按跳跃的时间段推进（与V2.x逻辑一致）。
```

### 🟡 问题5：世界规则引擎 §4.1 "NPC个人阈值"的模块归属模糊

**涉及文档**：《世界规则引擎》§4.1 vs 《NPC》§3.5

**矛盾描述**：

世界规则引擎 §4.1 "NPC个人阈值"定义了：

| 指标 | 触发阈值 | 触发内容 |
|------|----------|----------|
| 好感度跨越边界 | 中立→信任/信任→仇恨 | AI评估关系质变的原因和后果 |
| 生存状态突变 | 重伤/失去庇护所/失去重要的人 | AI评估NPC行为模式的转变 |

两个问题：
1. **好感度数据**的权威来源是NPC行为系统（V3.0 §2.2 数据权威表明确），变化检测自然应在NPC行为系统内完成。将此阈值放在世界规则引擎中，暗示世界规则引擎需要持续监控NPC好感度——但世界规则引擎的"不做什么"中明确写了"不模拟单个NPC行为"。
2. **生存状态突变**（重伤/失去庇护所）的检测需要NPC系统内部的个体数据（NPC生命值、所在位置），世界规则引擎不持有这些数据。

实际上 NPC §3.5 的"阶段跨越"已经定义了相同的逻辑（好感度跨越关系阶段边界时触发AI评估），§4.1 的阈值表与之重复但描述不同。

**修改建议**：
- 将"NPC个人阈值"从世界规则引擎 §4.1 移除（世界规则引擎不管理NPC个体数据）
- 在 NPC §3.5 "阶段跨越"中增加生存状态突变的触发条件（与好感度跨越并列）
- 世界规则引擎 §4.1 保留势力级和区域级阈值即可

### 🟡 问题6：NPC §4.3 互动判定范围中"同一势力"跨Location情况未定义

**涉及文档**：《NPC》§4.3

**问题描述**：

> "在结算点，检查同一场景内的NPC对（或同一势力的NPC对）"

"或同一势力的NPC对"暗示：即使两个NPC不在同一场景(Location)，只要同属一个势力就可能触发互动。但这带来一组未定义的行为：
- 跨Location的势力内互动（如资源分享、争执）如何在物理空间上实现？
- 如果允许跨Location互动，NPC位置系统的意义被削弱
- 如果只允许同Location互动，括号中的"或同一势力"就是多余的

合理的解释是：当NPC对在同一场景时，检查所有互动类型；当NPC对同属一个势力但不同场景时，仅触发有限的势力级互动（如势力内部秩序变化）。但文档没有区分这两种情况。

**修改建议**：明确互动判定的空间约束：

```
在结算点，检查同场景内的NPC对（所有互动类型均适用）。
同势力但不同场景的NPC对，仅触发以下有限互动：
- 势力内部秩序变化（群体士气传播）
- 势力领袖决策影响（自上而下）
向下兼容：同一势力且同一场景的NPC对，适用全部互动类型。
```

### 🟡 问题7：全局事件的自动产生机制未定义

**涉及文档**：《世界规则引擎》§2.3 / §3.4 vs 《V3.0》§4

**问题描述**：

V3.0 §4 三层事件体系表述：全局事件"每日结算时自动产生或AI评估产生"。

世界规则引擎 §3.4 详细描述了事件传播（SIR模型），§4.2 描述了AI评估产生事件的流程。但**全局事件如何"自动产生"**——即在没有AI评估的情况下，系统根据什么规则决定"现在是时候生成一个新尸潮了"——没有在任何文档中定义。

缺失的具体问题：
- 自动产生的触发条件是什么？（时间驱动？阈值驱动？概率驱动？）
- 新事件的类型、强度、源区域如何确定？
- 自动产生的频率上限是多少？（防止事件泛滥）
- 与 AI 评估产生的事件如何协调？（避免重复产生相似事件）

**修改建议**：在世界规则引擎 §2.3 中增加"事件产生规则"小节，或在 §3.4 事件传播之前增加事件生成的触发条件和参数定义。

### 🟢 问题8：V3.0 §3.2 正常模式"世界暂停"描述过度简化

**涉及文档**：《V3.0》§3.2

**问题描述**：

§3.2 三速控制表：

| 正常 | 世界暂停，等待玩家行动 | 探索、社交、搜索 |

"世界暂停"与实际行为矛盾——§3.1 明确说"玩家做出消耗时间的行动后世界解冻并推进"。在正常模式下，当玩家选择了一个消耗时间的行动（如"搜索物资，耗时30分钟"），世界时钟会推进30分钟，期间模拟层可能跨越午夜触发每日结算。

"世界暂停"更适合描述**玩家思考期间**（阅读叙事、考虑选项）的状态，而非正常模式的全部行为。当前表述可能让读者误以为正常模式下世界时钟永远不会推进。

**修改建议**：将表格中的描述改为：

```
| 正常 | 世界仅在玩家行动消耗的时间中推进，其余时间暂停 | 探索、社交、搜索 |
```

### 🟢 问题9：NPC提取衰减与数量上限两种降级机制的交互关系未定义

**涉及文档**：《NPC》§2.2 vs §8

**问题描述**：

文档定义了两种触发接触NPC降级的独立机制：

- §2.2 提取衰减规则："连续30天无互动 → 触发降级检查"
- §8 性能控制："接触NPC上限：30（超过上限时，最不活跃的接触NPC降级为背景NPC）"

两种机制的交互未定义：
- 如果 NPC 已连续 29 天无互动（距降级还有1天），但此时第31个NPC加入触发上限降级——谁先降级？
- 上限降级选择"最不活跃"的标准是什么？（距离上次互动时间最长？累计互动次数最少？好感度最低？）
- 上限降级是否也执行 §2.2 的"结构化数据存档+群体标签更新"流程？

**修改建议**：在 §8 或 §2.2 中增加说明：

```
数量上限降级与时间衰减降级的关系：
- 时间衰减优先：先检查是否有NPC满足"连续30天无互动"条件，若有则降级
- 上限补充：若时间衰减降级后仍超限，按"最近互动时间"排序，降级最久未互动的NPC
- 两种降级路径均执行相同的数据存档流程（保留好感度和记忆摘要，更新群体标签）
```
