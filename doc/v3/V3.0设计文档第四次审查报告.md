### 🔴 问题1：NPC "战斗/非战斗身份"分类在NPC数据模型中缺失

**涉及文档**：《世界规则引擎》§3.3 vs 《NPC》§3.1

**矛盾描述**：

世界规则引擎 §3.3 "宏观战损到微观NPC的映射规则"第3条使用了明确的NPC身份分类：

> "非战斗身份NPC（平民、商人、工匠）：死亡概率 × 0.3"
> "战斗身份NPC（哨兵、士兵、守卫）：死亡概率 × 1.0"

但 NPC §3.1 "基础信息"中定义的"身份"字段是自由文本：

> "身份：如'哨卡士兵'、'流浪商人'、'势力领袖'"

既没有"战斗/非战斗"二元分类，也没有枚举值列表。世界规则引擎的死亡概率修正依赖一个在NPC数据模型中不存在的字段。

如果开发时不做这个分类，世界规则引擎无法区分"哨兵"和"商人"——两者在宏观兵力统计中都算"人口×武装率"的一部分，但战损映射需要按身份区别对待。

**修改建议**：在 NPC §3.1 的"基础信息"中增加：

```
- 战斗角色：枚举（战斗人员/非战斗人员/领袖）
  - 战斗人员（哨兵、士兵、守卫）：计入势力兵力，战损概率×1.0
  - 非战斗人员（平民、商人、工匠）：不计入势力兵力，战损概率×0.3
  - 领袖（势力领袖、关键决策者）：计入势力兵力，死亡判定前触发AI评估
```

### 🔴 问题2：NPC死亡判定未引用CasualtyReport战斗伤亡路径

**涉及文档**：《NPC》§4.4 vs 《世界规则引擎》§3.3 vs 《NPC》§7.1

**矛盾描述**：

NPC §4.4 定义了五种离开原因，其中"死亡"的触发条件是：

> "NPC受伤且未获得医疗，或所在场景遭遇灾难"

NPC §7.1 明确写了：

> "当战斗结算产生伤亡时，世界规则引擎推送 CasualtyReport...NPC行为系统据此更新接触NPC的死亡/伤病标记。"

但 §4.4 的死亡判定条件**完全没有提及 CasualtyReport 路径**。两条死亡路径（§4.4 自身判定 vs §7.1 的 CasualtyReport 接收）是并行的，但 §4.4 作为"离开判定"的入口章节只描述了一条。

开发时如果只看 §4.4 实现死亡逻辑，会遗漏战斗伤亡推送的处理。

**修改建议**：在 NPC §4.4 的死亡行中增加 CasualtyReport 引用：

```
| 死亡 | NPC受伤且未获得医疗，或所在场景遭遇灾难，或收到世界规则引擎的 CasualtyReport 中标记该NPC为死亡 | NPC被标记为已死亡 |
```

并在 §4.4 末尾增加说明：

```
战斗伤亡的死亡由世界规则引擎 CasualtyReport（见世界规则引擎§3.3）直接推送，NPC行为系统收到后立即更新死亡标记，不等待每日结算。NPC自身判定逻辑仅处理非战斗原因的死亡（伤病恶化、灾难）。
```

### 🔴 问题3：接触NPC "饥饿/脱水致死"逻辑缺失

**涉及文档**：《NPC》§4.4 vs §3.3

**问题描述**：

NPC §4.4 当前定义的死亡触发条件（含第二轮修订的 CasualtyReport 路径）有三条：
1. NPC受伤且未获得医疗
2. 所在场景遭遇灾难
3. 收到世界规则引擎的 CasualtyReport 中标记该NPC为死亡

**逻辑漏洞**：缺少"需求过载致死"路径。

NPC §3.3 定义了需求系统——食物需求紧迫度日增量+120（约20小时达到上限100），饮水日增量+192（约12.5小时达到上限）。如果NPC所在势力发生饥荒（食物储备归零），宏观上世界规则引擎每日结算时会扣减人口（见世界规则引擎§3.1 阈值检测"饥荒→触发AI评估"），但接触NPC的个体死亡路径不存在——他不会因为食物需求连续触顶而死亡。

**场景推演**：红松营地连续5天食物储备=0。宏观上人口从200降到150（每日扣减），但接触NPC老王（没有受伤，场景无灾难，未被CasualtyReport抽中）5天后依然"存活"——尽管他的食物需求已经连续5天饱和（100/100）。这不合逻辑。

**修改建议**：在 NPC §4.4 的死亡行中增加"需求过载"条件：

```
| 死亡 | NPC受伤且未获得医疗，或所在场景遭遇灾难，或收到CasualtyReport死亡标记，或核心生存需求（食物/水）连续3游戏日处于100饱和状态 | NPC被标记为已死亡 |
```

并在 §3.3 的"需求满足"后增加说明：

```
需求过载致死：若NPC的食物或饮水需求连续3个每日结算均处于100（饱和），
在第3次结算时触发死亡判定——NPC因饥饿或脱水而死亡。
此判定与世界规则引擎的宏观人口扣减独立运行——宏观扣减的是背景NPC，
需求过载致死的是接触NPC个体。
```

### 🔴 问题4：个体消耗与宏观消耗的"双重扣费"风险

**涉及文档**：《世界规则引擎》§3.1 vs 《NPC》§3.3

**问题描述**：

这是一个典型的**两层消耗会计不一致**：

**宏观层**（世界规则引擎 §3.1）：
```
食物消耗 = 人口 × 人均日消耗
```
每日结算时，势力资源池按总人口扣除食物。

**个体层**（NPC §3.3 + 加速模式自动导航）：
- 接触NPC在需求满足时"进食"——意味着从势力资源中获取食物
- V3.0 §3.3 加速模式：玩家自动导航"优先消耗势力资源池（同步扣除模拟层对应的人口天数）"

**逻辑漏洞**：如果宏观结算按"总人口 × 人均消耗"预扣了所有资源，然后又让接触NPC个体"领粮"（再次扣除），同一份食物被算了两次。

**场景推演**：红松营地人口200，食物储备100人口天。每日结算扣除 200 × 1 = 200人口天的食物（但实际上只有100，超支）。同时，接触NPC老王（红松营地成员）需求满足时，从势力资源池中"领走"了相当于0.5人口天的食物。如果宏观预扣200人口天已经包含了老王的份额，老王的领粮就是额外扣费。

更隐蔽的问题是——如果接触NPC不领粮（不吃势力资源），他们会饿死（问题3）。但如果领粮，又会导致双重扣费。两条路都走不通。

**修改建议**：在世界规则引擎 §3.1 的消耗公式处增加说明：

```
宏观消耗与个体消耗的协调规则：
- 宏观公式（人口 × 人均日消耗）为"理论消耗上限"，用于每日结算时的势力资源池扣减
- 接触NPC的个体消耗（进食、饮水）不从势力资源池中再次扣除——其份额已包含在宏观扣减中
- 换算关系：1个接触NPC的日消耗 = 1人口天。宏观公式中的人口参数 = 背景NPC人口 + 接触NPC数量
- 玩家自身的势力资源消耗（加速模式自动导航）同步扣除模拟层资源池—— 
  因为玩家的消耗不在"人口 × 人均消耗"的计算范围内（玩家不计入势力人口）
```

### 🟡 问题5（原问题3重编号）：V3.0 §5.1 直接影响路径描述暗示场景变更通过生存状态机

**涉及文档**：《V3.0》§5.1 vs 《世界规则引擎》§4.2

**矛盾描述**：

V3.0 §5.1 描述直接影响路径：

> "通过裁决Agent→ActionResult→生存状态机，影响：
> - 玩家自身状态（HP、SP、饱食度、物资）
> - 当前场景的状态（如炸毁军火库→该区域物资-30%）"

箭头链"裁决Agent→ActionResult→生存状态机"暗示所有影响（包括场景状态）都经过生存状态机。但实际上：
- 玩家自身状态变更 → 确实经过生存状态机（状态机权威）
- 场景状态变更（如区域物资减少） → **不经过**生存状态机，直接写入模拟层（模拟层权威）

世界规则引擎 §4.2 更精确地描述了同一路径的另一个分支：
> "玩家行动触发 → 裁决Agent→ActionResult→模拟层修改"

两段文字描述的是 ActionResult 的两个分叉——一个分叉到生存状态机（玩家状态），一个分叉到模拟层（世界状态）。但 §5.1 的文字将两个分叉合并在一个箭头链下，造成"场景状态也经过生存状态机"的误导。

**修改建议**：将 §5.1 改为明确两条分叉：

```
通过裁决Agent→ActionResult，分两路影响：
- → 生存状态机：玩家自身状态（HP、SP、饱食度、物资背包）
- → 模拟层数据：当前场景状态（如炸毁军火库→该区域物资-30%）
两条路径均立即生效。
```

### 🟡 问题6：NPC初始需求值的随机范围未定义

**涉及文档**：《NPC》§2.2

**问题描述**：

NPC §2.2 提取规则：

> "初始需求随机分配"

需求紧迫度范围是0-100（§3.3），但"随机分配"没有说明：
- 是均匀随机（0-100之间任意值）？
- 还是加权随机（偏向中等值，如30-70）？
- 还是有上下文修正（如该势力食物短缺 → 新NPC初始食物需求偏高）？

如果全范围均匀随机，可能出现"刚认识一个饿得要死的NPC（食物需求=98）"或"刚认识一个极其满足的NPC（食物需求=2）"，两者的初始互动体验差异巨大。

**修改建议**：将 §2.2 的"初始需求随机分配"改为：

```
初始需求随机分配（基础值 = 30 + random(0, 40)，
再根据当前势力/区域状态修正：势力食物短缺→食物需求+20；区域高威胁→安全需求+20）
```

### 🟡 问题7：NPC初始好感度在负面互动提取时的计算未定义

**涉及文档**：《NPC》§2.2

**问题描述**：

NPC §2.2 提取规则说明触发条件之一是"好感度变化绝对值 ≥ 10"，变化可以是正向的也可以是负向的。但提取后的处理是：

> "初始好感度基于互动结果"

"基于互动结果"没有公式。如果互动是正面的（好感度变化 = +15），初始好感度设为多少？如果互动是负面的（好感度变化 = -20，即NPC对玩家产生负面看法，但从背景层提取时没有"之前的好感度"基准值），初始好感度如何计算？

背景NPC没有个体好感度——它们只有"群体态度"（欢迎/中立/警惕/敌意）。当一个NPC从背景层提取时，需要将群体态度转化为个体好感度的初始值，再叠加本次互动的变化量。

**修改建议**：在 §2.2 中增加公式：

```
初始好感度 = 群体态度基准值 + 本次互动变化值

群体态度→基准值映射：
- 欢迎 → +30 + random(0, 10)
- 中立 → 0 + random(-10, +10)
- 警惕 → -20 + random(-10, +10)
- 敌意 → -50 + random(-10, +10)

（好感度范围 -100~+100，见§3.5）
```

### 🟡 问题8：世界规则引擎事件生成的"每日至少1个"与概率模型的张力

**涉及文档**：《世界规则引擎》§2.3

**问题描述**：

§2.3 事件产生规则表格：

> "全局每日最多N个（N=势力数×0.3，至少1个）"

同时：

> "基础生成概率 = 0.03/势力/日（每天3%概率产生一个新事件）"

如果只有5个势力，N=1.5，至少1个。但5个势力 × 3% = 0.15个期望事件/日，远低于"至少1个"。这意味着系统需要在大约6天才有1个期望事件（0.15×6≈1）的情况下，强制每天至少产生1个事件。

这种强制保底机制会导致事件泛滥——在丧尸末日设定中可能合理，但在核战凛冬设定中就过度活跃了。"至少1个"应该是可配置的，而非硬编码。

**修改建议**：将"至少1个"改为配置项：

```
全局每日最多N个（N=max(势力数×0.3, minEventsPerDay)，其中 minEventsPerDay 为配置参数，
默认值按末日类型：丧尸末日=1，核战凛冬=0，内战崩溃=1）
```

### 🟡 问题9：正常速度下玩家与势力物资交互的流程未定义

**涉及文档**：《世界规则引擎》§3.1 vs V3.0各章节

**问题描述**：

世界规则引擎 §3.1 定义了标准单位换算表："玩家与势力交互（捐赠/领取/偷窃物资）时，系统自动按此标准换算。"

V3.0 §3.3 加速模式中明确了自动导航消耗势力资源的流程。

但在**正常速度**下——即游戏主要的交互模式——玩家如何与势力资源池交互，完全没有流程定义。比如：
- 玩家说"我把这瓶水给营地"→ 谁处理这个请求？裁决Agent？剧情管理器？
- 裁决Agent的职责是"判定行动成败"，物资捐赠需要判定吗（捐赠通常不会失败）？
- 物资扣除和资源池增加的事务性操作由谁执行？

**修改建议**：在 V3.0 §5.1 或世界规则引擎 §3.1 中增加：

```
正常速度下玩家与势力物资交互流程：
1. 玩家发出物资交互行动（捐赠/领取/偷窃）
2. 若为捐赠或合法领取 → 跳过裁决Agent判定（非对抗行动），由 GameRepository 直接执行换算和扣除/添加
3. 若为偷窃 → 经过裁决Agent判定（对抗行动），成功后执行换算
4. 换算公式见世界规则引擎§3.1标准单位换算表
5. 势力资源池变更后立即触发阈值检查（可能触发即时推送）
```

### 🟡 问题10：NPC间互动的"记忆缺失"——社交快照缺失

**涉及文档**：《NPC》§3.4 vs §4.3

**问题描述**：

NPC §4.3 明确规定常规互动只记录数值变更，不模拟过程：

> "常规互动只记录结果（数值变更），不模拟过程。"

NPC §3.4 记忆系统定义的详细记忆条目包含"交互摘要（一句话描述）"和"情感变化（好感度变化值+情感倾向标签）"。但这些记忆条目目前仅针对**NPC与玩家的交互**。

**逻辑漏洞**：NPC间的互动（争执、合作、资源分享）会改变好感度，但不会在任何一方的记忆中留下记录。

**场景推演**：NPC_A（老王）和 NPC_B（李队长）在一次资源分配中发生争执，好感度从 +30 降到 +10。之后玩家向老王询问"你对李队长的看法如何？"系统提供给叙事Agent的上下文是：好感度 +10（关系阶段"中立/陌生"），但老王的3条详细记忆中没有任何关于李队长的信息，远期摘要也没有。叙事Agent只能看到"他不太喜欢李队长"但不知道为什么——因为没有"争执"事件的记忆。AI 很可能会因此产生因果链幻觉（自己编造一个原因）。

这本质上与第三轮深水问题D（AI溯源幻觉）同源，但从"玩家-NPC交互记忆压缩"扩展到了"NPC-NPC交互记忆缺失"。

**修改建议**：在 NPC §4.3 "互动粒度"中增加社交快照机制：

```
NPC间互动的社交快照：
即使是常规互动（不触发AI），也应在双方记忆队列中插入一条简化的社交快照：
- 格式：[时间] 与 [对方NPC姓名] 发生 [互动类型]，原因：[触发条件摘要]
- 示例：[Day 5 下午] 与 李队长 发生 争执，原因：食物资源竞争
- 社交快照计入详细记忆队列（会触发压缩规则），与玩家交互记忆共用队列容量
- 仅在以下情况跳过社交快照：日常社交（无显著情感变化）且好感度变化 < |5|
```

### 🟡 问题11：势力覆灭/NPC被俘时的"远景记忆保护"缺失

**涉及文档**：《NPC》§3.4 vs §2.2 vs 《世界规则引擎》§3.3

**问题描述**：

世界规则引擎 §3.3 规定势力兵力降至0时：

> "所有剩余接触NPC触发'迁移'或'被俘'判定"

NPC §4.4 "被驱逐"和"迁移"处理了NPC位置变更，NPC §2.2 的提取衰减规则处理了"超过7天未互动权重降低→30天无互动降级"。

**逻辑漏洞**：当NPC被俘到玩家无法接触的遥远区域时（玩家不可见），NPC的记忆系统仍在运行——每游戏日需求推进、NPC间互动（与俘虏营中的其他NPC）、记忆压缩均正常执行。

**场景推演**：
- Day 1-7：玩家与NPC老张建立深厚关系（救命之恩→找女儿→送食物），好感度 +80（亲密），3条详细记忆全是与玩家相关的关键事件。
- Day 8：红松营地覆灭，老张被灰烬匪帮俘虏，转移至300公里外的匪帮据点。
- Day 8-18：老张在战俘营中每天经历"被殴打"（受伤）、"与守卫争执"（好感度变化）、"被分到馊饭"（进食）。每1-2天产生一条新记忆。
- Day 18：玩家攻破匪帮据点，救出老张。

此时老张的5条详细记忆（关键NPC）全部是10天战俘营生活的内容——玩家当年的"救命之恩""找女儿""送食物"早已被压缩为一句远期摘要"玩家曾多次帮助我"。

这与第三轮深水问题D同根同源，但多了一个**不可逆性**维度：问题D的压缩是因为玩家自己制造了足够多新记忆来挤压旧记忆（可控），而本问题的压缩是因为NPC在玩家不可见期间经历了大量低质量互动（不可控）。

**修改建议**：在 NPC §3.4 "远期摘要"后增加远景记忆保护机制：

```
远景记忆保护（Remote Memory Preservation）：
当NPC的状态为"被俘"、"失踪"或"玩家连续30天未访问该NPC所在Region"时：
1. 该NPC的记忆压缩频率降为正常的1/3（如接触NPC每12条新记忆才压缩1条，关键NPC每15条才压缩1条）
2. 压缩时优先保留标记为"与玩家相关"的记忆条目（玩家参与的记忆不压缩，或最后被压缩）
3. 若详细记忆队列中所有条目均为非玩家相关，至少保留1条与玩家相关的最早远期摘要不被合并
4. NPC被玩家重新接触（解救/重逢）时，记忆压缩频率恢复正常
```

### 🟡 问题12（原问题8重编号）：NPC §4.2 区域事件响应的作用范围模糊

**涉及文档**：《NPC》§4.2

**问题描述**：

> "当世界规则引擎推送区域状态变更时，NPC行为系统执行'中断检查'。"

没有定义"哪些NPC"执行中断检查：
- 该区域内所有接触NPC？
- 该区域内所有NPC（含背景NPC——但背景NPC没有个体行为）？
- 仅事件直接影响到的Location内的NPC？

背景NPC没有个体行为，理论上无法执行中断检查。但背景NPC占人口的绝大部分，如果一个区域事件（如尸潮接近）只影响接触NPC而不影响背景NPC，背景NPC会显得"对灾难免疫"。应该在群体标签层面体现响应。

**修改建议**：明确作用范围：

```
区域事件响应的作用范围：
- 接触NPC：个体级别执行中断检查（按§4.2事件→行为映射表）
- 背景NPC：群体级别响应——更新该Region的群体标签（如"因尸潮逼近，群体状态变为'恐慌中'"、群体士气-20）
- 区域事件的群体响应由世界规则引擎在每日结算时直接更新群体标签，NPC行为系统仅处理接触NPC的个体响应
```

### 🟢 问题13：玩家非加速模式死亡时的叙事Agent切换未定义

**涉及文档**：《V3.0》§7.2 vs §6.3

**问题描述**：

V3.0 §7.2 角色死亡后处理：

> "世界叙事Agent生成'角色最后时刻'叙事"

V3.0 §6.3 明确世界叙事Agent的调用时机：

> "仅在加速模式下调用"

如果玩家在减速模式（战斗中HP归零）或正常模式（特定剧情死亡）中死亡，此时世界叙事Agent不在活跃状态。§7.2 要求世界叙事Agent生成死亡叙事，但 §6.3 限制它只在加速模式调用。

**修改建议**：将 §7.2 改为：

```
系统生成"角色最后时刻"叙事：
- 若死亡发生在加速模式 → 由世界叙事Agent生成
- 若死亡发生在正常/减速模式 → 由叙事Agent（以特殊模式）生成，输入包含死亡原因和角色最终状态
```

### 🟢 问题14：NPC提取后是否立即参与当日结算未定义

**涉及文档**：《NPC》§2.2 vs §4.3

**问题描述**：

NPC §2.2："触发提取时，系统即时创建一个接触NPC实例"

NPC §4.3：NPC间互动在"每游戏日结束时"结算。

如果一个NPC在下午3点被提取（第1天），当晚午夜的每日结算中，这个新提取的NPC是否参与NPC间互动？

两种选择都有道理：
- 参与：NPC从提取那一刻起就是"真实存在的人"，应该参与世界运转
- 不参与：NPC的属性刚刚初始化（随机需求、默认时间表），当天参与结算可能导致不合逻辑的行为（如刚认识就被随机配对争执）

**修改建议**：在 §2.2 或 §4.3 中增加：

```
新提取NPC的当日结算参与规则：
- 若提取时间距下次每日结算 > 6游戏小时：参与当日结算（正常更新需求、互动判定）
- 若提取时间距下次每日结算 ≤ 6游戏小时：跳过当日需求更新和互动判定（仅执行时间表布置），从次日结算开始完整参与
```

### 🟢 问题15：需求紧迫度的实际饱和情况未在文档中说明

**涉及文档**：《NPC》§3.3

**问题描述**：

NPC需求紧迫度范围是0-100，但日增量远超100：

| 需求类型 | 日增量 | 从0到100所需时间 |
|----------|--------|-----------------|
| 食物 | +120 | ~20小时 |
| 饮水 | +192 | ~12.5小时 |
| 医疗(受伤时) | +360 | ~6.7小时 |
| 安全(高威胁) | +240 | ~10小时 |

采用每日批量结算时，每次结算直接+120食物需求。这意味着几乎所有NPC的紧迫度在每日结算后都会**触顶饱和**（cap在100）。程序员自然会在实现时处理cap，但文档没有明确说明这个设计事实：

- 紧迫度到达100后是否溢出（超出的部分在需求满足时是否体现）？
- 多个NPC需求同时触顶时，紧迫度排序失效——大家都100，如何决定优先级？

这是一个实现细节而非矛盾，但应在文档中明确，避免实现时混乱。

**修改建议**：在 §3.3 结算频率说明后增加：

```
紧迫度触顶与溢出规则：
- 每日结算推进后，紧迫度上限为100（超出部分不保留，不溢出）
- 多个NPC同需求触顶时，按需求"权重"（食物/饮水/医疗 > 安全 > 社交 > 自我实现）决定优先级
- 同需求同权重时，按NPC与玩家的好感度（负优先——敌人更危险）、身份（战斗人员优先）排序
- 这意味着：在资源紧张的末日环境中，大多数NPC的大多数时间都处于需求饱和状态。
  这不是bug，是设计意图——末日世界本来就稀缺，NPC总是在"需要什么"的状态中。
```

**建议**：🔴问题1-4涉及跨模块数据字段定义和资源会计——实现后修改成本高，应在编码前修订。🟡问题5-12和🟢问题13-15可在实现阶段逐项明确。
