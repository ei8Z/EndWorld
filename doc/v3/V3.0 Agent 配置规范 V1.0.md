## 一、AI 调用总览

V3.0 有四类 AI 调用点，按推理深度和调用频率区分：

| 调用点 | 类型 | Model | reasoningEffort | maxTokens | Stream | 典型延迟 | 调用频率 |
|--------|------|-------|-----------------|-----------|--------|----------|----------|
| 裁决Agent | 独立Agent | deepseek-flash | max | 8192 | false | 8-20s | 每次玩家行动(正常/减速) |
| 叙事Agent | 独立Agent | deepseek-flash | medium | 8192 | true | 3-8s(首token 2-5s) | 每次玩家行动(正常/减速) |
| 世界叙事Agent | 双模 | 模板引擎(本地) + deepseek-flash(云端) | —(本地) / medium(云端) | —(本地) / 4096(云端) | 本地实时 / 云端非流式 | <1ms(本地) + 5-15s(云端一次) | 仅加速模式 |
| 轻量AI评估 | 非独立调用 | deepseek-flash | low | 4096 | false | 1-3s | 数个游戏日一次 |

> 注：轻量 AI 评估走 `completeRaw`（`low` / 4096）。max_tokens 取 4096 是因为真实 API 下 1024 会被推理 token 占满、`content` 为空（`finish_reason=length`）。

**设计原则**：
- **当前统一使用 Flash 模型**：裁决、叙事、世界叙事、轻量评估四个调用点均发送 `deepseek-flash`，优先成本与延迟；`deepseek-v4-pro` 保留为可选升级路径
- **切回 Pro 的条件**：若质量评估显示 Flash 的裁决/叙事质量不足，可切回 Pro，但必须同步本表、README 与代码中的 `model` 字段，避免三方漂移
- **本地模板用于延迟敏感的实时场景**：世界叙事Agent 的加速期间摘要使用客户端预设模板引擎（<1ms），不依赖任何 AI 模型；仅加速结束时调用一次云端 AI
- **非独立调用**（轻量AI）复用 `DeepSeekApiService` 的标准 `/chat/completions` endpoint，不需要独立的 ApiClient 类

## 二、裁决Agent

### 2.1 API 参数

```
model: "deepseek-flash"
reasoningEffort: "max"
responseFormat: json_object
maxTokens: 81920
stream: false
userId: 稳定用户ID（用于 KV Cache 优化）
```

### 2.2 System Prompt

`PromptBuilder.buildReasonerSystemPrompt()` — 已在 V2.x 中实现。包含：世界时钟规则、基础DC选取、掷骰判定、物资校验与精确计量、伤病判定、事件触发、剧情节点、记忆参考、技能影响、NPC深度规则、输出JSON格式。

### 2.3 User Message

`PromptBuilder.buildReasonerUserMessage()` — 已在 V2.x 中实现。V3.0 集成阶段（V2.9）扩展为注入 RulingContext 结构（见 V3.0 总纲 §6.1.1）。

### 2.4 输出

`ActionResult` — 结构化 JSON，字段：result/dcValue/rollValue/totalValue/modifiersBreakdown/resourceChanges/injuriesApplied/injuriesRecovered/narrativeSummary/eventTriggered/plotNodeCompleted/plotNodeHint/memoryContextChecked。

### 2.5 降级策略

API 异常或 JSON 破损时返回降级结果（`result="失败"`，`narrativeSummary="行动因不明原因中断"`），状态机不做任何变更。

## 三、叙事Agent

### 3.1 API 参数

```
model: "deepseek-flash"
reasoningEffort: "medium"
responseFormat: json_object
maxTokens: 81920
stream: true（流式输出，打字机效果）
userId: 稳定用户ID
```

### 3.2 System Prompt

`PromptBuilder.buildStorytellerSystemPrompt()` — 已在 V2.x 中实现。包含：角色定义、五感描写、节奏控制、建议选项生成规则、statusUpdate/输出格式/字段约束。

V3.0 扩展（V2.4+）：suggestions 的 `timeCost` 为建议值，裁决Agent的实际消耗时间可能与建议值存在偏差（±30%）。速度模式切换时（正常↔减速），suggestions 由叙事Agent重新生成而非时间缩放。当 nearbyNpcs 为空（无人区）时，叙事Agent切换为环境叙事模式（聚焦环境描写、氛围营造、生存状态），suggestions 过滤所有社交类选项（仅保留探索/移动/生存/制作类）。

V3.0 末日类型叙事风格（V3.0新增）：叙事Agent的 user message 中注入末日类型标签（丧尸末日/核战凛冬/内战崩溃），System Prompt 根据末日类型调整叙事基调——丧尸末日侧重"危机四伏的紧张与幸存者的人性光辉"，核战凛冬侧重"静默的绝望与荒芜中的坚韧"，内战崩溃侧重"信任的瓦解与秩序的崩塌"。

### 3.3 User Message

`PromptBuilder.buildStorytellerUserMessage()` — 已在 V2.x 中实现。输入：玩家行动标签 + ActionResult + PostRuling WorldSnapshot + PlotContext + 记忆上下文 + speedMode（速度档位：normal/deceleration，供叙事Agent调整叙事密度）。

V3.0 加速退出模式（V2.7 新增）：调用 `PromptBuilder.buildStorytellerAccelExitUserMessage()`（新建方法），输入：世界叙事Agent最终摘要（summary + playerStatus + notableChanges）+ WorldSnapshot + 附近NPC状态 + PlotContext + 记忆上下文。此模式下无玩家行动标签和 ActionResult——叙事Agent 基于世界叙事Agent 的摘要直接生成初始场景叙事和新的行动选项。

V3.0 死亡叙事模式（V3.0 新增）：当玩家在正常/减速模式下死亡时，调用 `PromptBuilder.buildStorytellerDeathUserMessage()`（新建方法），输入：死亡原因 + ActionResult（包含致死行动信息）+ 角色最终状态快照 + WorldSnapshot + PlotContext + 记忆上下文。此模式下叙事Agent 输出仅包含死亡叙事文本（无 suggestions、无 statusUpdate），以终结语气收束故事线。详见 V3.0 总纲 §7.2。

### 3.4 输出

`GameResponse` — 流式 JSON：header(story 文本增量) + suggestions(结构化建议选项) + statusUpdate(状态更新块)。流结束时发射完整的 GameResponse 对象。

死亡叙事模式下，输出仅包含 header（死亡叙事文本），无 suggestions 和 statusUpdate。

### 3.5 降级策略

流中断或 JSON 破损时返回降级 GameResponse（空statusUpdate、默认suggestions、通用叙事文本）。状态机不做任何变更。

死亡模式降级：返回通用死亡叙事文本（"生命在这一刻画上了句点..."）。

## 四、世界叙事Agent

### 4.0 架构：双模设计

世界叙事Agent 采用**客户端模板引擎 + 云端 AI**的双模架构，解决 AI 延迟与实时性需求的矛盾。

| 阶段 | 引擎 | 延迟 | 职责 |
|------|------|------|------|
| 加速期间 | 客户端预设模板引擎（纯 Kotlin/Java） | <1ms | 将结构化"预期变化"数据按预设模板格式化为状态栏文本 |
| 加速结束 | DeepSeek `v4-pro`（云端） | 5-15s | 基于累积的实际结算结果 + 模板文本序列，生成高质量最终叙事总结 |

**为什么不能用云端 AI 做实时摘要**：最快的 Flash 模型单次调用延迟 1.5-4 秒。"每 3 秒一次摘要"意味着请求堆积——这是物理上不可行的设计。

**为什么用模板而非 AI 模型做实时摘要**：最快的 AI 模型（Flash）单次调用延迟 1.5-4 秒。"每 3 秒一次摘要"意味着请求堆积——这是物理上不可行的设计。MemOS 的 `memos-extractor-0.6b` 是云端 HTTP API（非本地模型），同样有网络延迟（1-3s），且其核心能力是"对话文本→结构化记忆"而非"结构化数据→自然语言文本"。模板引擎方案的优势：零延迟（<1ms）、零云端成本、不依赖网络连接。文本流畅度由模板设计质量保证，而非 AI 生成。

> V3.1 可选方向：若未来 MemOS 提供"结构化数据→自然语言摘要"的专用接口，可用于增强模板引擎的文本多样性。届时本地模板引擎作为保底，云端 API 作为增强——而非完全替代。此方向与 V3.0 中 extractor 的当前用途（NPC 记忆抽取，见 NPC 文档 §6.3）完全独立。

### 4.1 本地阶段：客户端模板引擎

**引擎信息**：
- 实现：纯 Kotlin/Java 字符串格式化，`WorldNarrativeTemplateEngine` 类
- 延迟：<1ms（纯 CPU 字符串操作）
- 输入：结构化数据（由世界规则引擎在加速开始时提供"预期变化"数据）
- 输出：格式化状态栏文本（1-2 句）

**输入数据结构**（除 `previousTemplateText` 外，由世界规则引擎在加速开始时计算一次；`previousTemplateText` 由模板引擎每次生成后自行更新，用于下一轮去重判断。模板引擎定时读取最新数据）：

```kotlin
data class ExpectedChanges(
    val timeMarker: String,           // "第3天 14:00"
    val elapsedGameHours: Float,      // 已过的游戏小时数
    val resourceTrends: List<ResourceTrend>,  // 势力资源趋势
    val eventProximities: List<EventProximity>, // 事件接近程度
    val playerVitals: PlayerVitals,   // 玩家生命体征（加速开始时的快照；模板规则当前不引用此字段，保留供 V3.1+ 模板扩展使用）
    val previousTemplateText: String? // 上一轮模板文本（用于去重）
)

data class ResourceTrend(
    val factionName: String,
    val resource: String,      // "食物"/"水"/"医疗"/"弹药"
    val trend: String,         // "declining"/"stable"/"critical"
    val daysUntilWarning: Int
)

data class EventProximity(
    val eventName: String,
    val distanceInRegions: Int,
    val propagationProb: Float
)
```

**预设模板规则**（`WorldNarrativeTemplateEngine.generate()` 按优先级匹配）：

```kotlin
// 优先级1：致命威胁（立即警报）
val immediateThreat = eventProximities
    .filter { it.distanceInRegions <= 1 && it.propagationProb > 0.5 }
    .maxByOrNull { it.propagationProb }
if (immediateThreat != null) {
    return "⚠️ ${immediateThreat.eventName}已逼近至邻区！"
}

// 优先级2：资源危机
val criticalFaction = resourceTrends.firstOrNull { it.daysUntilWarning <= 2 }
if (criticalFaction != null) {
    return "${criticalFaction.factionName}${criticalFaction.resource}仅够维持${criticalFaction.daysUntilWarning}天"
}

// 优先级3：资源趋势
val decliningFaction = resourceTrends.firstOrNull { it.trend == "declining" }
if (decliningFaction != null) {
    return "${decliningFaction.factionName}的${decliningFaction.resource}储备正在缓慢下降"
}

// 优先级4：事件动态
val approachingEvent = eventProximities.firstOrNull { it.distanceInRegions <= 3 }
if (approachingEvent != null) {
    return "${approachingEvent.eventName}仍在${approachingEvent.distanceInRegions}个区域外"
}

// 优先级5：平淡期
return "周围一片寂静。时间在流逝..."
```

**模板去重**：若本轮生成的文本与 `previousTemplateText` 完全相同，追加"（持续中）"后缀，避免 UI 显示重复内容。

**刷新间隔**：客户端可自由控制（推荐 2-5 秒），不受 AI 延迟约束。

### 4.3 调用节奏

```
加速开始：
  ├─ 启动模板引擎本地循环（每 2-5 秒一次，<1ms 生成状态栏文本）
  ├─ UI 展示本地状态更新流
  └─ 等待玩家发出"恢复正常速度"元行动

玩家发出"恢复正常速度"：
  ├─ 停止本地循环
  ├─ 世界规则引擎执行批量追赶结算（N个游戏日的资源更新+冲突判定+事件传播）
  ├─ NPC行为系统批量追赶（NPC需求+互动+离开判定）
  ├─ 收集自动导航报告
  ├─ 判断加速时长：若 < 2 游戏小时 → 跳过云端调用，直接使用本地模板摘要交接给叙事Agent；若 ≥ 2 游戏小时 → 调用云端世界叙事Agent（DeepSeek Pro，单次，5-15s）
  ├─ UI 展示"正在生成加速总结..."加载动画（仅云端调用时）
  └─ 收到最终摘要 → 转交给叙事Agent 生成初始场景叙事
```

### 4.4 降级策略

**本地阶段降级**（模板引擎异常——极端罕见，仅代码bug场景）：
- 回退到最简格式化——直接显示"第X天 | 食物 Y 天 | 尸潮 Z 区域外"的纯数据状态栏

**云端阶段降级**（API 异常）：
```
{"timeMarker": "[当前时间]", "summary": "时间加速流逝。当你回过神来，世界已经悄然改变。", "notableChanges": [], "playerStatus": {...}, "final": true}
```
降级时，`playerStatus` 中的 `hp`/`hunger`/`thirst`/`consumedFactionResources`/`injuriesHealed`/`injuriesSustained` 仍从自动导航报告（客户端本地数据）中填充——这些数据在 AI 调用前已确定，不受 API 异常影响。仅 `summary` 和 `notableChanges` 使用降级默认值。
不重试——降级摘要直接转交给叙事Agent。叙事Agent 基于 WorldSnapshot 仍然可以生成有效叙事。

## 五、轻量AI评估

### 5.1 设计原则

"轻量"的含义：
- **非独立Agent**：不维护独立的 Agent 类，复用 `DeepSeekApiService` 的标准 `/chat/completions` endpoint
- **快速响应**：Flash 模型 + 低推理强度 + 小 token 预算 = 首次 token 延迟通常 < 1s
- **统一 System Prompt**：所有轻量AI调用点共用同一个 System Prompt（角色定义），仅 user message 因场景而异
- **确定性优先**：阈值是否跨越由规则引擎确定性判定。轻量AI仅在规则无法判定的**后果**（阈值跨越后的势力反应方向、关键NPC生死、道德困境、局势质变方向）时才触发

**触发条件**：世界规则引擎 §4.1 定义的任何危机阈值被跨越（食物<3天、兵力<5%、士气<15、控制区减80%、区域威胁>85），或世界规则引擎 §3.2 定义的势力解散判定触发

```

```

**代码验证规则**（在世界规则引擎侧，AI 输出后执行）：
- `triggerType` 必须为以下合法值之一，不匹配→取 `"未知触发"`：
  势力食物危机 / 势力食物警告 / 势力兵力危机 / 势力兵力警告 / 势力士气危机 /
  势力士气警告 / 势力控制区危机 / 势力控制区警告 / 区域威胁危机 / 区域威胁警告 /
  区域资源危机 / 区域资源警告 / 势力解散
- JSON 解析器需配置为忽略未知字段（如 Gson 默认行为，或 kotlinx.serialization 的 `ignoreUnknownKeys = true`），以兼容 Agent 配置规范可能在 `evaluation` 对象中新增的辅助字段（如 `rationale`、`suggestedNarrativeAngle`）
- `stateChanges[].target` 必须匹配现有势力ID或区域ID，不匹配→丢弃该条目
- `stateChanges[].attribute` 必须为已知属性名。势力级属性：势力目标/士气/状态标签/领袖性格。区域级属性：控制区域/威胁等级。资源池属性（食物储备/水资源/医疗物资/弹药储备）允许修改但需额外校验：|change| ≤ 对应资源池当前值的50%，变更日志标记为 `source: "ai_triggered_resource_change"` 以与确定性池-流更新区分。不匹配任何合法属性名→丢弃
- `stateChanges[].change` 若为数值，|change| ≤ 对应属性的合理上限。非资源池属性的特殊上限：士气|change|≤30。资源池属性的上限见上条（50%规则）
- `newEntities` 最多 2 个，新势力名称不能与现有势力重名
- 校验日志标记为 `source: "ai_evaluation_validated"`

### 5.11 代码验证规则（通用）

所有轻量AI场景共享以下通用验证规则（场景1的特定验证见 §5.4 末尾）：

- `decision` / `evaluation` 对象必须存在且非 null，否则 → 触发降级策略
- **JSON基础类型校验**（在字段级验证之前执行）：期望String的字段收到Number/Boolean/null → 取该字段的降级默认值；期望Number的字段收到String/Boolean/null → 取0；期望Array的字段收到String/Number/Object → 取空数组[]；期望Boolean的字段收到非Boolean → 取false。类型校验在反序列化层执行，失败时记录日志 `source: "lightweight_ai_type_mismatch"` 但不触发整体降级（仅该字段回退）
- 枚举字段必须在定义的合法值集合内，否则 → 取合法值集合的第一个值作为默认值
- 数值字段若为 NaN / Infinity / 负数（除明确允许负数的字段外）→ clamp 到合法范围
- 字符串字段若为空字符串 → 取该场景降级策略中的默认值
- 校验日志标记为 `source: "lightweight_ai_validated"`，记录原始值 → 修正值

### 5.12 轻量AI降级策略

所有轻量AI场景共享同一降级逻辑：

1. API 异常（网络超时/服务不可用）→ 选择"最保守的决策"：
   - 场景1（质变评估）：`mostLikelyReaction = "维持现状"`，不产生 stateChanges
   - 场景2（关系跨越）：`behaviorModeChange = null`（不改变行为模式）
   - 场景3（战斗死亡）：检查该NPC在最近10天内是否已有 spare 降级记录 → 若有则本次 `outcome = "kill"`；若无则 50% 概率 `"spare"`、50% 概率 `"severe_injury"`（防止 API 不稳定时关键NPC 获得事实上的死亡免疫）
   - 场景4（生存突变）：`newBehaviorMode = "maintain_current"`（维持现有行为）
   - 场景5（罕见互动）：`outcome = "无显著后果"`，affinityChanges 为空
   - 场景6（失踪判定）：`outcome = "return_injured"`，`returnDays = 2`（保守估计）
   - 场景7（异常解释）：`anomalyCause = "原因不明"`，`permanence = "temporary_extended"`
2. JSON 解析失败 → 同 API 异常降级策略
3. 记录降级日志：`source: "lightweight_ai_fallback"`，原始错误信息
4. 连续 5 次降级 → 暂停该场景的轻量AI调用 24 游戏小时（防止高频错误调用）

### 5.13 场景间连锁触发规则

同一结算周期内，一个轻量AI场景的输出可能立即触发另一个场景：

**已知连锁链**：
- 场景3（战斗死亡判定：`outcome = "severe_injury"`）→ 场景4（生存状态突变：重伤）
- 场景5（罕见互动：`outcome` 涉及势力结构变更）→ 场景1（势力质变评估）
- 场景6（失踪判定：`outcome = "joined_other_faction"`）→ 场景1（若势力人口变更跨过阈值）

**处理规则**：
1. 连锁触发的场景**排队**在当前场景的AI调用完成后执行——不并发，保证上下文完整
2. 连锁场景的AI输入中**包含前一个场景的完整输出**（作为"触发来源"附加到 User Message 中），确保AI评估有完整的因果链
3. 连锁深度上限为 **2 跳**（场景A→场景B→场景C 时，场景C 推迟到下一次每日结算），防止AI调用无限递归
4. 若连锁触发的场景与当前正在排队（或已执行）的场景重复 → 跳过，不重复调用

## 5.14 Function Calling（check_inventory）

**挂载位置**：裁决 Agent（非流式）。叙事 Agent 只挂"裁决后回写"类工具，当前没有此类工具。

**工具定义**：
```json
{"type":"function","function":{"name":"check_inventory","description":"查询玩家背包中特定物品的数量，用于防止数量幻觉","parameters":{"type":"object","properties":{"item_name":{"type":"string"}},"required":["item_name"]}}}
```

**调用规则**：
1. `tool_choice = "auto"`；模型可自行决定是否调用；
2. 客户端本地执行，回填 `role=tool` 消息后再次请求；
3. 最多 2 轮工具调用，超过则按降级策略返回失败结果；
4. 未知工具或参数 JSON 破损：返回 `{"error":...}` 作为工具结果，不中断对话；
5. 工具执行是只读的，无副作用。

**成本**：tools 定义每轮进入 prompt；仅在主线行动挂载，支线与元行动不挂。

## 七、AI 调用中断恢复

当应用进程在 AI 调用期间被系统终止（内存不足/崩溃/强制关闭）时，重启后的恢复策略：

**中断点检测**：每次 AI 调用前，在 Room 数据库中记录 `pendingAction` 状态（包含行动类型、时间戳、调用阶段）。重启时检查是否存在未完成的 pendingAction。

**恢复策略（按中断阶段）**：

| 中断阶段 | 世界/玩家状态 | 恢复策略 |
|----------|-------------|----------|
| 裁决Agent调用中（请求已发送，未收到响应） | 未变更（ActionResult未应用） | 丢弃该次调用，记录日志 `source: "ai_interrupted"`。叙事Agent生成"你的行动被打断了..."的通用叙事，玩家重新选择行动 |
| 裁决Agent已完成，ActionResult已应用，叙事Agent调用中 | 已变更（ActionResult已持久化） | 补调用叙事Agent（`buildStorytellerUserMessage()`），使用已持久化的ActionResult。叙事文本中可自然提及"一阵恍惚后..." |
| 轻量AI评估调用中 | 部分变更（确定性结算已完成，AI结果未返回） | 判定为降级场景，使用§5.12的降级策略。确定性部分的变更保留，AI评估结果在下一次触发时重新请求 |

**pendingAction 超时**：若 pendingAction 存在超过 1 小时现实时间（表明应用长时间未重启而非崩溃），自动清除并视为降级处理。

## 八、调用链中的 Agent 切换

```
正常/减速模式：
  玩家行动 → 裁决Agent → ActionResult → 叙事Agent → GameResponse → UI

加速模式：
  玩家选择"加速" → 模板引擎本地循环（<1ms 状态栏刷新）→ UI 时间流摘要面板
  玩家选择"恢复正常" → 世界规则引擎批量追赶结算（N个游戏日的资源更新+冲突判定+事件传播）
                      → NPC行为系统批量追赶（NPC需求+互动+离开判定）
                      → 收集自动导航报告
                      → 世界叙事Agent云端调用（最终摘要 5-15s）→ 叙事Agent（初始场景叙事）→ UI

每日结算（后台）：
  世界规则引擎阈值触发 → 轻量AI评估（场景1）→ stateChanges 应用到模拟层
  NPC 事件触发 → 轻量AI评估（场景2-7）→ 应用到 NPC 行为系统
```
