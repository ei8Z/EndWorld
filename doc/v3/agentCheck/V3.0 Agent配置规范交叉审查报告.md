### 🔴 问题1：场景1输出JSON的顶层键名与主文档不一致

**涉及文档**：Agent §5.4 vs 世界规则引擎 §4.2

**矛盾描述**：

世界规则引擎 §4.2 定义的 AI 评估输出结构：

```json
{
  "evaluation": {
    "triggerType": "势力食物危机",
    "subjectName": "红松幸存者营地",
    "mostLikelyReaction": "...",
    ...
  }
}
```

Agent §5.4 定义的输出结构：

```json
{
  "decision": {
    "subjectName": "势力/区域名称",
    "mostLikelyReaction": "...",
    ...
  },
  "rationale": "...",
  "suggestedNarrativeAngle": "..."
}
```

两个差异：
1. **顶层键名不同**：主文档用 `"evaluation"`，Agent 用 `"decision"`
2. **新增字段**：Agent 在顶层增加了 `rationale` 和 `suggestedNarrativeAngle`，主文档的输出结构中不存在这两个字段。主文档中 `triggerType` 字段在 Agent 中被移除

**后果**：世界规则引擎的 Step 6（阈值触发处理）按 `"evaluation"` 键解析 → Agent 返回的 JSON 中这个键不存在 → 解析失败 → 触发降级策略。首次调用就炸。

**修改建议**：二选一：
- 方案A（推荐）：修改 Agent §5.4 的输出结构，保持 `"evaluation"` 为顶层键名，将 `rationale` 和 `suggestedNarrativeAngle` 移入 `evaluation` 对象内部
- 方案B：同步修改世界规则引擎 §4.2 的输出结构，使其与 Agent 一致

### 🔴 问题2：场景3的"注册剧情角色跳过AI"约束与主文档"非绝对豁免"语义冲突

**涉及文档**：Agent §5.6 vs 世界规则引擎 §3.3

**矛盾描述**：

世界规则引擎 §3.3：

> "关键NPC：死亡判定前触发轻量AI评估（允许叙事保护但非绝对豁免——AI有权判定关键NPC在特定情境下死亡）"

Agent §5.6 末尾约束：

> "若该 NPC 在当前章节的关键剧情节点中为必需角色（剧情管理器中注册且未完成），`outcome` 强制为 `'spare'`（不调用 AI，直接走代码判定）"

两段话的语义冲突：
- 主文档说"非绝对豁免"——AI 有最终决定权，可以判定死亡
- Agent 说"注册剧情角色强制 spare + 不调用 AI"——代码层面剥夺了 AI 的决定权

这不一定是错误——"注册剧情角色"是一个更窄的条件（仅限剧情管理器注册且未完成节点的角色），而主文档的"非绝对豁免"针对的是"关键NPC"这个更宽泛的类别。但**"不调用 AI"这一行为在主文档中完全没有提及**。主文档的预期是"调用 AI，AI 判定"，Agent 的实现是"满足条件 → 跳过 AI"。

**修改建议**：在世界规则引擎 §3.3 的"关键NPC"行增加补充说明：

```
关键NPC：死亡判定前触发轻量AI评估（允许叙事保护但非绝对豁免——AI有权判定关键NPC在特定情境下死亡）。
例外：若该NPC在当前章节的关键剧情节点中为必需角色（剧情管理器中注册且未完成），
死亡判定自动跳过AI评估，outcome强制为spare。
```

### 🟡 问题3：场景2-7缺少代码验证规则

**涉及文档**：Agent §5.5-5.10

**问题描述**：

Agent §5.4（场景1）定义了详细的代码验证规则（target 校验、attribute 校验、change 范围 clamp、newEntities 限制）。但场景 2-7 没有任何验证规则。

虽然场景 2-7 的 AI 输出字段更少、更简单，但仍然存在 AI 返回非法值的可能性：
- 场景2：`behaviorModeChange` 可能返回未定义的字符串
- 场景3：`outcome` 可能返回 `"kill"/"spare"/"severe_injury"` 之外的非法值
- 场景6：`returnDays` 可能返回负数

**修改建议**：在 Agent §5.11（降级策略）之前增加"代码验证规则（通用）"小节：

```
所有轻量AI场景共享以下通用验证规则（各场景的特定验证见各场景模板）：
- decision 对象必须存在且非 null
- 枚举字段必须在定义的合法值集合内，否则 → 取合法值集合的第一个值作为默认值
- 数值字段若为 NaN/Infinity/负数（除明确允许负数的字段外）→ clamp 到合法范围
- 字符串字段若为空 → 取该场景降级策略中的默认值
- 校验日志标记为 source: "lightweight_ai_validated"
```

### 🟡 问题5：世界叙事Agent的"预期变化"数据源未定义

**涉及文档**：Agent §4.3 vs V3.0 总纲 §3.3

**问题描述**：

V3.0 总纲 §3.3 加速模式步骤 5：

> "加速期间：按固定现实时间间隔（如每3秒）生成阶段性摘要，内容基于加速开始时状态的逻辑推演（世界规则引擎提供'预期变化'而非结算结果）"

Agent §4.3 的 User Message 结构中包含"【状态变更】"数据源，但描述为"期间发生的模拟层状态变更列表（来自世界规则引擎 WorldStateUpdate）"。

**矛盾**：主文档说的是加速期间摘要基于**"预期变化"**（未发生的推演），而 Agent 说的是基于**"WorldStateUpdate"**（实际结算结果）。加速期间世界规则引擎处于批量追赶模式（不逐日结算），不存在 WorldStateUpdate。

**修改建议**：将 Agent §4.3 的"【状态变更】"改为分两种情况描述：

```
【状态变更】（加速期间）：
基于加速开始时状态的逻辑推演——世界规则引擎根据当前势力资源消耗率、活跃事件传播概率等因素，
生成"预期变化"列表（非结算结果，仅为推演）：
- 预期：[势力名称] 食物储备将在 [X] 天后降至警告线以下
- 预期：[区域名称] 的尸潮事件有 [Y]% 概率在 [Z] 天内传播至此
...

【状态变更】（加速结束时）：
基于批量追赶结算的实际结果（来自世界规则引擎 WorldStateUpdate）：
- [变更类型]：[具体描述]
...
```

### 🟡 问题6：Agent 降级策略场景3的 default 与场景3约束的语义冲突

**涉及文档**：Agent §5.11 vs §5.6

**问题描述**：

Agent §5.11 场景3降级默认值：

> `outcome = "spare"`（叙事保护）

Agent §5.6 约束：

> "若该 NPC 在当前章节的关键剧情节点中为必需角色 → outcome 强制为 spare（不调用 AI）"

这两个说的是同一件事（spare），但触发路径不同：
- §5.6 约束：剧情必需角色 → 代码层面跳过 AI，强制 spare
- §5.11 降级：API 调用失败 → 降级默认 spare

对于**非剧情必需的关键NPC**：AI 调用失败时降级为 spare。这意味着任何 API 异常都会导致关键NPC 存活——与主文档"非绝对豁免"的设计意图相悖（API 不稳定时所有关键NPC 都死不了）。

**修改建议**：将场景3的降级默认值改为：

```
场景3（战斗死亡）：outcome = 随机选择。若该NPC在最近10天内已有过"spare"降级记录 → 本次降级为 "kill"。否则 50% 概率 "spare"，50% 概率 "severe_injury"。
```

这样防止 API 不稳定导致关键NPC 获得事实上的免疫。

### 🟢 问题7：成本估算中 System Prompt token 数偏低

**涉及文档**：Agent §8

**问题描述**：

裁决Agent 的 System Prompt（`buildReasonerSystemPrompt()`）在 V2.x 中约 3000-4000 tokens（包含完整的伤病库列表、世界时钟规则、DC选取规则、物资校验规则、事件触发规则、剧情节点规则、记忆参考规则、技能影响规则、NPC深度规则、输出格式等）。Agent §8 估算裁决Agent 每次输入 ~3000 tokens——这个数字可能只覆盖了 user message，System Prompt 是固定的但也会计入每次调用的输入 token（除非 KV Cache 命中）。

```
System Prompt 的 token 消耗在 KV Cache 命中时大幅降低（仅首次调用或 Cache 过期时全额计费）。
以上估算为 KV Cache 命中率 ~80% 的均值。实际首次调用或 Cache miss 时输入 token 会更高。
```

### 🟢 问题8：Agent 配置总表中世界叙事Agent 的 model 与 §4.1 注释不一致

**涉及文档**：Agent §1 vs §4.1

**问题描述**：

Agent §1 总览表写世界叙事Agent Model = `deepseek-v4-flash`。Agent §4.1 注释写"摘要生成不需要深度叙事质量，flash 成本更低更快"。

## 三、专题：AI 交互延迟与现实可行性分析

> 触发点：问题 3（场景2-7缺验证规则）引申出对"每3秒摘要"的可行性质疑。
> 本节是本次审查的核心发现——V3.0 设计中存在多处对 AI API 延迟的不现实假设。

---

### 3.1 基线数据

当前 V2.x 代码中的实际超时配置（`RetrofitClient.kt`）：
- `connectTimeout`: 60 秒
- `readTimeout`: 120 秒

DeepSeek V4 API 特性文档中的延迟记录：
- `reasoning_effort=max` 时首次 token 延迟**可达 10 秒以上**
- 思考模式下 `temperature`/`top_p` 参数不生效

以 DeepSeek V4 Flash（轻量AI和世界叙事Agent的指定模型）为基准，实测级延迟估算：

| 指标 | Flash (reasoning=low) | Pro (reasoning=medium) | Pro (reasoning=max) |
|------|----------------------|----------------------|---------------------|
| TTFT（首次 token 延迟） | 0.5-2s | 2-5s | 5-12s |
| 总响应时间（maxTokens=1024） | 1-3s | 3-8s | 8-20s |
| 总响应时间（maxTokens=8192） | 3-8s | 8-15s | 15-30s |
| 网络+排队抖动 | +0.5-3s | +0.5-3s | +0.5-5s |

---

### 🔴 问题9：世界叙事Agent "每3秒摘要" — 物理上不可能

**涉及文档**：V3.0 总纲 §3.3 / Agent 配置规范 §4.4

**矛盾推演**：

V3.0 §3.3：
> "加速期间：按固定现实时间间隔（如每3秒）生成阶段性摘要"

Agent §4.4：
> "加速期间：按固定现实时间间隔（每 3 秒）发送一次请求"

即使使用最快的 Flash 模型（TTFT 0.5-2s，总响应 1-3s），加上网络往返和 JSON 解析，一次完整调用的最短时间是 **1.5-4 秒**。3 秒的间隔意味着：**第一个请求还没返回，第二个请求已经发出了**。

实际推演：假设加速 1 分钟（现实时间），"每 3 秒"意味着 20 次请求。Flash 模型每次 2-4 秒 → 20 次请求需要 40-80 秒才能串行完成。但只有 60 秒的现实时间——即使并发两个请求也才刚刚好。而并发会增加 API rate limit 风险和服务端排队。

**更根本的问题**：加速期间玩家在看摘要流——如果每 3 秒更新一次，但 AI 需要 2-4 秒生成每次更新，玩家看到的不是"流"而是断断续续的延迟更新。这与"让玩家感知世界变化"的设计目标相悖。

**修改建议**：

方案A（推荐）：**改为纯客户端模板生成 + 最后一次 AI 摘要**

```
世界叙事Agent 的调用策略改为"两端模式"：
- 加速期间：不使用 AI。客户端根据规则引擎提供的"预期变化"数据（势力资源消耗趋势、事件传播概率），
  使用预设模板填充生成阶段性摘要。这不是 AI 叙事——这是数据可视化转文本：
  "第3天 14:00 | 红松营地食物储备降至 4 天 | 灰烬匪帮仍在 2 个区域外"
  此模板填充逻辑完全在客户端运行，延迟 < 10ms

- 加速结束时：调用一次世界叙事Agent（使用 Pro 模型，reasoning=medium，maxTokens=4096），
  输入整个加速期间的所有累积变更和模板摘要序列，生成一个高质量的"加速总结"叙事。
  这一次调用的 5-15 秒延迟被"回顾加速过程"的 UI 过渡动画自然覆盖
```

方案B：**增大间隔到 15-20 秒**

```
加速期间：每 15-20 秒调用一次世界叙事Agent（Flash 模型）
间隔期间，UI 显示简单的状态栏更新（客户端驱动，非 AI）：
"时间推进中... 第X天"
这给 AI 留出足够的响应时间（2-4 秒），确保不会请求堆积
```

推荐方案A——因为它不仅解决了延迟问题，还解决了"加速期间摘要没有数据源"的问题（交叉审查问题5）：加速期间客户端用预期数据填充模板，加速结束用批量追赶的实际结算结果生成 AI 摘要。

### 🔴 问题10：双Agent串行调用 — 每次玩家行动等待 10-30 秒

**涉及文档**：V3.0 总纲 §6.1 / §6.2（未在文档中明示延迟）

**现实推演**：

正常模式下每次玩家行动的执行流程：

```
玩家发出行动 → 裁决Agent（Pro/max/非流式/8192 tokens）→ 等待完成（8-20s）
              → 生存状态机应用结果（<1ms）
              → 叙事Agent（Pro/medium/流式/8192 tokens）→ 等待首token（2-5s）→ 文本流式输出（3-8s）
              → UI 渲染（<100ms）
```

总延迟：裁决 8-20s + 叙事首token 2-5s = **玩家至少等待 10-25 秒才能看到第一行叙事文本**。在减速（子弹时间）模式下更糟——玩家发出"侧身闪避"后要等 15 秒才知道结果。

**当前 V2.x 代码的实际行为**（验证）：`GameRepository.processMainline()` 中，裁决Agent 调用是 `suspend` 函数，叙事Agent 调用在裁决完成之后。代码没有并发优化——这是正确的（叙事需要 ActionResult），但延迟是客观存在的。

**文档中从未提及这个等待时间**。

**修改建议**：

在 V3.0 总纲 §6.1 或 §6.2 中增加"玩家感知延迟"说明：

```
裁决Agent + 叙事Agent 的串行调用延迟：
- 两次 API 调用的累计延迟为 10-25 秒（取决于模型负载和网络条件）
- UI 在等待期间展示"判定中..."加载状态，裁决完成后展示"叙事生成中..."
- 减速模式下延迟不变（AI 调用时间不受游戏速度影响）——这是子弹时间的代价：
  玩家获得更细腻的叙事密度，但每次行动的等待时间相同
- 未来优化方向（V3.1+）：裁决Agent 改为流式输出（先出判定结果，不等完整 JSON），
  使叙事Agent 可以提前开始处理——并行化减少 30-40% 的感知延迟
```

### 🟡 问题11：轻量AI评估批量触发可能阻塞每日结算

**涉及文档**：世界规则引擎 §4.2 / §5

**现实推演**：

世界规则引擎 §5 的每日结算流程中，Step 6（阈值触发处理）是同步的——"若触发数>1，合并为一次AI评估"。文档假设多个阈值触发时可以合并为单次 AI 调用。但这是针对**世界规则引擎内部的阈值**。

如果同一次每日结算中还触发了 NPC 系统的轻量 AI 调用（场景2-7），这些调用与 Step 6 的 AI 评估是并行的还是串行的？文档未定义。

最坏情况：一次每日结算触发 3 个质变阈值（Scene 1）+ 2 个关键NPC关系跨越（Scene 2）+ 1 个 NPC 间罕见互动（Scene 5）= 如果全部串行，最多 6 次 AI 调用 × 每次 1-3s = 6-18 秒。而文档声称"整体结算可在玩家阅读叙事时后台完成，无感知延迟"——6-18 秒的后台任务不是"无感知"的。

**修改建议**：

在世界规则引擎 §5 "性能考量"中增加说明：

```
Step 6 的 AI 调用延迟：
- 单次阈值评估的 AI 调用延迟约 1-3 秒（Flash/light）
- 若合并后仍有多类 AI 调用（世界规则引擎 + NPC 系统），按优先级排队：
  1. 势力/区域质变评估（先执行——可能影响 NPC 行为判定的上下文）
  2. NPC 系统调用（后执行——可能依赖质变评估的结果）
- 排队期间的结算流程不阻塞——Step 7 的 WorldStateUpdate 先输出不含 AI 评估结果的
  确定性部分（资源变更、战斗结果、事件传播），AI 评估结果在完成后异步追加
- 这意味着：每日结算的确定性部分在毫秒级完成并推送，
  AI 评估的"质变分析"延迟 2-10 秒后追加——不影响基础结算节奏
```

### 🟢 问题12：流式输出的"初始空白期"未在设计文档中提及

**涉及文档**：V3.0 总纲 §6.2 / Agent 配置规范 §3.1

**问题描述**：

叙事Agent 使用流式输出（`stream: true`）实现"打字机效果"。但流式输出并不能消除**首次 token 延迟**——在第一个 token 到达之前（2-5 秒），UI 是空白的。当前 V2.x 代码的 `StorytellerApiClient` 在流开始前没有任何"pre-stream"状态通知。

**修改建议**：在 Agent 配置规范 §3.1 中增加：

```
流式输出的用户体验：
- stream: true 仅消除"等待完整响应"的延迟——首次 token 延迟（2-5s）仍然存在
- UI 应在流开始前展示"叙事生成中..."加载动画，收到第一个 token 后切换为打字机效果
- 裁决Agent 的判定结果（成败/DC/消耗）可以在叙事文本流开始前先展示——让玩家在等待叙事时
  先看到"判定：部分成功 | 消耗：水 -150ml"等关键信息，减少感知等待
```

## 六、整体评价（更新）

Agent 配置规范的场景覆盖和参数定义是正确的。但本次审查暴露了一个更底层的问题：**V3.0 的多处设计假设 AI 调用的延迟可以忽略不计**——"每3秒摘要"、双Agent串行"无感知"、批量AI评估"后台完成"。这些假设在真实 API 延迟面前不成立。

最严重的两个延迟问题（#9 世界叙事Agent 间隔、#10 双Agent 串行等待）不是 Agent 配置规范的问题——它们是 V3.0 总纲本身的设计假设缺陷。Agent 配置规范忠实地转录了这些假设，将它们暴露在 API 参数的放大镜下。

建议优先级：先修 🔴 #9（否则加速模式核心功能设计不可行），再修 🔴 #10（用户体验影响最大），其余问题按严重度依次处理。
