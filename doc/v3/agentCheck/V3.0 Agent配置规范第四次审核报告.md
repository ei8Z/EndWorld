### 🔴 问题1：世界规则引擎 §5 Step 6 声称"合并为一次AI评估"与 Agent §5.4 场景1 User Message 仅支持单个触发事件矛盾

**涉及文档**：世界规则引擎 §5 Step 6 vs Agent §5.4

**问题描述**：

世界规则引擎 §5 Step 6：

> "若触发数>1，合并为一次AI评估"

Agent §5.4 场景1 User Message 模板：

```
【触发事件】：[阈值类型] [势力/区域名称] [具体指标] 从[旧值]变为[新值]，跨过[阈值线]
```

模板只容纳**单个**触发事件——一个阈值类型、一个势力/区域名称、一个指标变化。但实际场景中可能同时触发多个阈值。例如一次大规模战斗后：
- 势力A 兵力跨过危机阈值（兵力 < 总人口×5%）
- 势力A 士气跨过警告阈值（士气 < 30）
- 势力A 控制区域减少跨过警告阈值（减50%）

世界规则引擎说合并为一次调用，但 Agent 模板无法表达"合并后的多触发事件"。AI 收到的 User Message 中只有一个触发事件槽位，多余的信息无处安放。

Agent 的 System Prompt（§5.3）说：

> "你的输入全部来自系统提供的结构化数据——不要编造输入中不存在的事实"

如果系统只传入了一个触发事件，AI 不会知道还有另一个触发事件同时发生，评估必然不完整。

**后果**：多阈值同时触发时，AI 评估可能只基于第一个触发事件做出判断，遗漏其他同时发生的质变——导致评估结果片面（如只处理了士气危机，未处理兵力危机）。

**修改建议**：在 Agent §5.4 的 User Message 模板中增加多触发事件的支持：

```
【触发事件】（可能多个同时触发）：
- [阈值类型1] [势力/区域名称1] [具体指标1] 从[旧值1]变为[新值1]，跨过[阈值线1]
- [阈值类型2] [势力/区域名称2] [具体指标2] 从[旧值2]变为[新值2]，跨过[阈值线2]
（若仅1个触发事件，仅列1条）
```

同时在 System Prompt 中增加指示：若存在多个触发事件，综合评估所有事件的交互影响。

### 🔴 问题2：叙事Agent 输入定义仅覆盖正常/减速模式，未定义加速退出时的特殊输入路径

**涉及文档**：Agent §3.3 vs V3.0 总纲 §6.3

**问题描述**：

Agent §3.3 定义叙事Agent 的 User Message 输入：

> `PromptBuilder.buildStorytellerUserMessage()` — 已在 V2.x 中实现。输入：玩家行动标签 + ActionResult + PostRuling WorldSnapshot + PlotContext + 记忆上下文。

这个输入格式假设了"玩家行动 → 裁决Agent → ActionResult → 叙事Agent"的标准流水线。

但 V3.0 总纲 §6.3 定义了加速模式退出的特殊路径：

> "加速模式退出时，世界叙事Agent 的云端阶段输出包含当前场景完整状态的最终摘要。叙事Agent 接收此摘要作为初始上下文，生成进入正常模式的第一个叙事段落和新的行动选项。"

Agent §7 调用链也确认了此路径：

```
世界叙事Agent云端调用（最终摘要）→ 叙事Agent（初始场景叙事）→ UI
```

此路径中**不存在**"玩家行动标签"和"ActionResult"——叙事Agent 的输入是"世界叙事Agent 的输出 + PostRuling WorldSnapshot"，而非标准的五元组。当前 Agent §3.3 完全没有定义这一输入模式。

这意味着 `PromptBuilder.buildStorytellerUserMessage()` 需要一个新的重载或分支方法来支持"加速退出模式"的输入组装。但文档没有提到这个方法的存在。

**后果**：开发者在 V2.7 实现加速退出流程时，发现叙事Agent 没有适配的 user message 构建方法——要么临时 hack，要么遗漏这条路径。

**修改建议**：在 Agent §3.3 中增加加速退出模式的输入定义：

```
V3.0 加速退出模式（V2.7 新增）：叙事Agent 接收世界叙事Agent 的云端输出
（summary + playerStatus + 当前场景状态）替代 ActionResult 和玩家行动标签。
此时调用 PromptBuilder.buildStorytellerAccelExitUserMessage()（新建方法），
输入：世界叙事Agent最终摘要 + WorldSnapshot + 附近NPC状态 + PlotContext + 记忆上下文。
```

### 🟡 问题3：世界规则引擎 §6.2 未声明向模板引擎提供"预期变化"数据

**涉及文档**：世界规则引擎 §6.2 vs Agent §4.1

**问题描述**：

Agent §4.1 定义模板引擎的输入数据 `ExpectedChanges` 由世界规则引擎提供：

> "输入数据结构（除 previousTemplateText 外，由世界规则引擎在加速开始时计算一次）"

但世界规则引擎 §6.2 "向世界叙事Agent输出" 仅描述：

> "当玩家选择时间跨度行动（block/chapter）或世界事件抵达玩家所在区域时，世界规则引擎提供：
> - 期间发生的状态变更摘要
> - 影响玩家所在区域的事件描述
> - 玩家所在区域的新状态"

三行描述全部指向**结算后的实际结果**（"状态变更摘要"、"新状态"），完全没有提及加速开始时需要提供的**预期变化**数据（`resourceTrends`、`eventProximities`）。

ExpectedChanges 需要的是世界规则引擎基于当前状态做的**前瞻性计算**（如 `daysUntilWarning`、`propagationProb`），这与 §6.2 描述的"结算后报告"是完全不同的数据产品。

**后果**：世界规则引擎的开发者只看自己模块文档时，完全不知道需要为模板引擎提供预期变化数据。模板引擎启动时收不到 `ExpectedChanges`，加速期间状态栏无内容可展示。

**修改建议**：在世界规则引擎 §6.2 中增加"加速开始时"数据输出说明：

```
此外，当玩家进入加速模式时，世界规则引擎在加速开始时一次性计算并输出"预期变化"数据
（ExpectedChanges），供世界叙事Agent 的本地模板引擎使用：
- 各势力资源消耗趋势（当前消耗速率下的预计告警天数）
- 活跃全局事件对各区域的传播概率和预计到达时间
- 当前时间标记和玩家生命体征快照
此数据为前瞻推演而非结算结果，模板引擎定时读取以生成加速期间的状态栏文本。
```

### 🟡 问题4：世界规则引擎 §4.2 AI评估输入结构缺少"势力目标"字段

**涉及文档**：世界规则引擎 §4.2 vs Agent §5.4

**问题描述**：

世界规则引擎 §4.2 AI评估输入结构：

```
- 相关势力：[势力名称]（人口/兵力/资源/控制区域/领袖性格）
```

Agent §5.4 场景1 User Message：

```
- 相关势力：[势力名称]（人口/兵力/资源/控制区域/领袖性格/势力目标）
```

Agent 的模板比世界规则引擎多了 **势力目标** 字段。

"势力目标"是世界规则引擎 §2.2 中定义的合法势力属性（枚举：扩张/防守/撤离/寻求同盟），对 AI 评估势力反应有直接影响——一个"扩张"目标的势力面对食物危机时比"防守"目标势力更可能选择掠夺而非求援。Agent 包含此字段是正确的增强，但世界规则引擎自己的文档没有同步。

**后果**：世界规则引擎的实现者按 §4.2 组装 AI 输入时不会包含势力目标 → AI 缺少关键判定依据 → 评估结果可能不符合势力的实际行为倾向。

**修改建议**：在世界规则引擎 §4.2 AI评估输入结构中增加"势力目标"：

```
- 相关势力：[势力名称]（人口/兵力/资源/控制区域/领袖性格/势力目标）
```

### 🟡 问题5：Agent §4.2 User Message "附近NPC：[列表]" 格式严重缺失

**涉及文档**：Agent §4.2 vs V3.0 总纲 §6.1.1

**问题描述**：

Agent §4.2 世界叙事Agent User Message 中：

```
【当前场景】：
- 位置：[Region/Location]
- 控制势力：[势力名称]
- 天气：[天气]
- 时间：[游戏内时间]
- 附近NPC：[列表]
```

"附近NPC：[列表]" 的格式完全未定义。对比同一个文档中其他场景对 NPC 状态的描述：

- 裁决Agent 的 RulingContext（V3.0 总纲 §6.1.1）：`nearbyNpcs` 每人含姓名/身份/性格/好感度/关系阶段/当前需求/情感倾向
- 场景2 User Message（Agent §5.5）：NPC状态含当前需求/最近记忆/好感度变化时间线/历史交互片段

世界叙事Agent 需要基于 NPC 当前状态生成加速总结叙事（如"哨兵老张因伤口感染去世"需要知道老张的姓名+身份+状态）。仅给一个 `[列表]`，AI 无法区分"哨兵老张（受伤、沮丧）"和"商人王二（健康、愉快）"——这将导致 notableChanges 中的 npc_death 等条目缺乏上下文支撑。

**修改建议**：将"附近NPC"格式明确为结构化列表：

```
- 附近NPC：
  · [NPC姓名]（[身份]）| 好感度：[值] | 状态：[正常/受伤/饥饿/...] | 最近变化：[简述]
  · ...
```

至少需要"姓名+身份+状态"三个字段，世界叙事Agent 才能在叙事总结中正确引用 NPC。

### 🟡 问题6：世界规则引擎 §6.2 使用 V2 术语 "block/chapter" 而非 V3 "加速模式"

**涉及文档**：世界规则引擎 §6.2 vs V3.0 总纲 §3.3

**问题描述**：

世界规则引擎 §6.2：

> "当玩家选择**时间跨度行动（block/chapter）**或世界事件抵达玩家所在区域时，世界规则引擎提供"

"block/chapter" 是 V2.x 的时间跨度行动术语。V3.0 已用"加速模式"（§3.3 三速控制）替代了 V2 的时间跨度概念。虽然 `block/chapter` 的行为与 V3 加速有相似之处（都是跳过一段游戏时间），但 V3.0 总纲和 Agent 配置规范全篇已统一使用"加速模式"术语，此处仍使用 V2 术语会造成概念混淆。

**后果**：读者看到"block/chapter"可能误以为 V3.0 中仍存在独立的 block/chapter 行动类型，而非统一的加速模式。

**修改建议**：将世界规则引擎 §6.2 第一句改为：

```
当玩家进入加速模式或世界事件抵达玩家所在区域时，世界规则引擎提供：
```

### 🟢 问题7：Agent §5.4 L396-L397 资源池属性 clamp 规则存在冗余

**涉及文档**：Agent §5.4

**问题描述**：

Agent §5.4 代码验证规则：

L396：
> 资源池属性（食物储备/水资源/医疗物资/弹药储备）允许修改但需额外校验：|change| ≤ 对应资源池当前值的50%

L397：
> `stateChanges[].change` 若为数值，|change| ≤ 对应属性的合理上限（士气|change|≤30，**食物储备|change|≤当前值的50%**）

食物储备的 50% clamp 在两条规则中重复出现。L396 是资源池属性的通用规则（已覆盖食物储备），L397 又单独提到食物储备。虽然不矛盾，但维护时可能产生分歧——如果修改资源池 clamp 比例为 40%，改 L396 容易漏掉 L397。

**修改建议**：将 L397 中的"食物储备|change|≤当前值的50%"移除，仅保留通用规则 L396 中的定义。L397 改为仅覆盖非资源池属性的特殊上限（如士气|change|≤30）。

### 🟢 问题8：Agent §5.1 "确定性优先" 原则表述与场景1实际触发机制不完全匹配

**涉及文档**：Agent §5.1 vs §5.4

**问题描述**：

Agent §5.1：

> "确定性优先"：常规情况不调用——只有在规则无法判定（关键NPC生死、道德困境、局势质变）时才触发

"规则无法判定"暗示场景1（阈值评估）是因为规则无法判定才调用 AI。但实际上场景1的触发条件（阈值跨越）**完全由规则判定**——世界规则引擎 §4.1 定义了精确的阈值线（食物<3天、兵力<5%等），阈值检测是100%确定性的。

AI 被调用的原因不是"规则无法判定阈值是否跨越"，而是"规则无法判定跨越阈值后势力/区域应如何反应"。当前表述将两个不同层面的"判定"混为一谈。

**修改建议**：将 Agent §5.1 中的对应描述改为：

```
"确定性优先"：常规情况不调用——阈值是否跨越由规则引擎确定性判定。
轻量AI仅在规则无法判定的**后果**（阈值跨越后的势力反应、关键NPC生死、
道德困境、局势质变方向）时才触发。
```

## 五、整体评价

经过四轮审核（累计 38 个问题），Agent 配置规范 V1.0 与三份主文档之间的一致性已达到**可冻结水平**。本轮发现的问题集中在两个领域：

1. **异常路径覆盖**（问题1、2）——多触发合并、加速退出模式等非常规代码路径的 Agent 输入定义缺失
2. **跨文档同步遗漏**（问题3、4、5、6）——Agent 配置规范做了正确的增强或定义，但主文档未跟进

问题1 和 2 是需要在代码实现前解决的结构性缺口。其余问题属于文档完善级别，不影响架构设计评审。
