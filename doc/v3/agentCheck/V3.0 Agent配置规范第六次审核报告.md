### 🔴 问题1：场景3 输出结构违反 §5.3 通用结构契约 —— `rationale` 位于 `decision` 内部而非顶层

**涉及文档**：Agent §5.6 vs Agent §5.3

**问题描述**：

Agent §5.3 定义了场景2-7的统一输出结构：

```json
{
  "decision": { /* 场景特定的决策字段 */ },
  "rationale": "一句话说明决策依据（≤50字）",          // ← 顶层
  "suggestedNarrativeAngle": "..."                      // ← 顶层
}
```

所有场景应遵守此契约：`rationale` 和 `suggestedNarrativeAngle` 位于 JSON 顶层，与 `decision` 平级。

逐场景验证：

| 场景 | `rationale` 位置 | `suggestedNarrativeAngle` 位置 | 合规 |
|------|-----------------|------------------------------|------|
| 2 (§5.5) | 顶层 ✅ | 顶层 ✅ | ✅ |
| 3 (§5.6) | **decision 内部** ❌ | 顶层 ✅ | ❌ |
| 4 (§5.7) | 顶层 ✅ | 顶层 ✅ | ✅ |
| 5 (§5.8) | 顶层 ✅ | 顶层 ✅ | ✅ |
| 6 (§5.9) | 顶层 ✅ | 顶层 ✅ | ✅ |
| 7 (§5.10) | 顶层 ✅ | 顶层 ✅ | ✅ |

场景3 的结构：

```json
{
  "decision": {
    "npcId": "...",
    "outcome": "kill" | "spare" | "severe_injury",
    "rationale": "判定理由（如'他在关键时刻被同伴拖走'或'命运没有眷顾他'）"  // ← 在 decision 内部
  },
  "suggestedNarrativeAngle": "供叙事Agent使用的死亡/幸存叙事角度"
  // ← 缺少顶层 "rationale"
}
```

对比场景2（正确范本）：

```json
{
  "decision": {
    "npcId": "...",
    "behaviorModeChange": "警惕→开放" | ...,
    "narrativeHint": "一句话叙事提示（供叙事Agent使用）"   // ← narrative rationale 在 decision 内
  },
  "rationale": "...",                                        // ← meta rationale 在顶层
  "suggestedNarrativeAngle": "..."
}
```

场景2 清晰地区分了两个层面的 rationale：
- `decision.narrativeHint`：供叙事Agent使用的角色内叙事提示
- 顶层 `rationale`：AI 评估的元级决策依据

场景3 将两者合并为一个 `decision.rationale`，缺少顶层 `rationale`。这破坏了 §5.3 的结构契约，且场景2的语义区分（叙事提示 vs 元级依据）在场景3中丢失。

**后果**：
1. AI 按 §5.3 System Prompt 试图输出顶层 `rationale`，但场景3模板不显示此字段 → AI 行为不确定
2. 代码解析器按 §5.3 契约期望顶层 `rationale` → 字段缺失 → 触发降级策略
3. 场景3的 `decision.rationale` 语义过载——既承载判定理由（叙事用途），又被当作元级依据（日志用途）

**修改建议**：将场景3的输出结构改为与场景2一致的模式：

```json
{
  "decision": {
    "npcId": "...",
    "outcome": "kill" | "spare" | "severe_injury",
    "narrativeHint": "判定理由（如'他在关键时刻被同伴拖走'或'命运没有眷顾他'）"
  },
  "rationale": "一句话说明决策依据（≤50字）",
  "suggestedNarrativeAngle": "供叙事Agent使用的死亡/幸存叙事角度"
}
```

将 `decision.rationale` 改名为 `decision.narrativeHint`（与场景2对齐），新增顶层 `rationale`。

### 🟡 问题2：降级策略 `behaviorModeChange = null` 与代码验证规则 `使用空字符串` 不一致

**涉及文档**：Agent §5.12 vs Agent §5.5

**问题描述**：

Agent §5.12 场景2降级默认值：

> `behaviorModeChange = null`（不改变行为模式）

Agent §5.5 代码验证规则：

> `behaviorModeChange` 必须为 `"X→Y"` 格式……不匹配→丢弃，使用空字符串

降级策略指定 `null`，验证规则指定空字符串 `""`。在 Kotlin 中 `null` 和 `""` 是不同的值，需要不同的空值检查逻辑。

设计意图分析：`null` 表示"无变化"（语义更准确），空字符串 `""` 表示"有值但为空"。在 NPC 行为系统的消费侧，应使用 `null` 检查来判断"是否需要修改 behaviorMode"。

**后果**：若代码实现统一使用验证规则（空字符串）而 NPC 系统消费侧期望 `null` → 行为模式被错误地设置为空字符串而非"不改变"。

**修改建议**：将验证规则中的 `使用空字符串` 改为 `使用 null`，与降级策略对齐：

```
不匹配→丢弃，使用 null（表示不改变行为模式）
```

### 🟢 问题3：多触发合并场景下 `triggerType` 是单值字段，未定义多触发时的赋值规则

**涉及文档**：Agent §5.4 vs Agent §5.4（内部）

**问题描述**：

Agent §5.4 的 User Message 已支持多触发列表：

```
- [阈值类型1] [势力/区域名称1] [具体指标1] ...
- [阈值类型2] [势力/区域名称2] [具体指标2] ...
```

但输出 JSON 中 `triggerType` 是单值字符串：

```json
"triggerType": "势力食物危机"
```

当两个阈值同时触发（如 势力食物危机 + 势力士气警告），`triggerType` 应填什么？

- 取第一个触发事件？
- 取最严重的（危机 > 警告）？
- 拼接（如 `"势力食物危机+势力士气警告"`）？
- 改为数组？

System Prompt 中没有任何指示。AI 会自行选择，导致输出不一致。

**后果**：轻量级不一致——AI 可能以不同策略选择 triggerType，下游日志分析时 triggerType 的值不稳定。

**修改建议**：在 Agent §5.4 的输出模板注释中增加说明：

```
"triggerType": "势力食物危机",  // 若多触发，取最严重的阈值类型（危机优先于警告）
```

或在代码验证规则中增加：

```
- 若 AI 输出的 triggerType 不在合法值集合中但包含多个合法值的拼接（如"势力食物危机+势力士气警告"），
  取第一个合法值（按拼接顺序）
```
