### 🔴 问题1：§8 成本估算表中世界叙事Agent行与实际双模架构矛盾

**涉及文档**：Agent §8 vs Agent §4

**矛盾描述**：

Agent §8 成本估算表第3行：

```
| 世界叙事Agent | v4-flash | 输入 ~1000 + 输出 ~300 | 加速期间 20-60 | 26K-78K |
```

Agent §4.2 实际设计：

```
model: "deepseek-v4-pro"
maxTokens: 4096
调用时机：仅加速结束时一次
```

四个维度的矛盾：

| 维度 | §8 表 | §4 实际设计 |
|------|-------|-----------|
| Model | v4-flash | v4-pro |
| 每次输入 tokens | ~1000 | ~2500-3500（本地摘要序列 + 结算结果 + 自动导航报告 + 场景状态） |
| 每次输出 tokens | ~300 | ~600（≤300字叙事 + JSON结构） |
| 每日调用次数 | 20-60 | ~3-8（每次加速结束1次） |

**值得注意的是**，§8 表格下方的补充说明文字**已经正确**描述了双模架构的成本优势：*"加速期间的摘要由客户端模板引擎生成（零云端成本），仅加速结束时的一次云端调用（Pro, maxTokens=4096）"*。但表格数据行本身未同步更新，仍然保留了旧设计方案（v4-flash + 高频调用）的数值。

**后果**：读者看到表格数据会误以为加速模式仍需要 20-60 次 Flash 调用，与文字描述矛盾。

**修改建议**：将 §8 成本估算表中世界叙事Agent 行修正为：

```
| 世界叙事Agent | v4-pro | 输入 ~3500 + 输出 ~600 | 加速结束 1 次/加速 | ~4K/加速 |
```

同时将"每日调用次数"改为基于加速频率的估算（如玩家平均加速 3-8 次/日，则每日 12K-32K tokens）。

### 🔴 问题2：§5.3 统一结构声明与 §5.4 场景1输出结构矛盾

**涉及文档**：Agent §5.3 vs Agent §5.4

**矛盾描述**：

Agent §5.3 定义轻量AI统一 System Prompt 中的通用输出结构：

```json
{
  "decision": { /* 场景特定的决策字段 */ },
  "rationale": "一句话说明决策依据（≤50字）",
  "suggestedNarrativeAngle": "一句话叙事建议（≤50字，供叙事Agent使用，可为null）"
}
```

声称："**所有**轻量评估共享以下外层结构"。

Agent §5.4 场景1实际输出结构：

```json
{
  "evaluation": {
    "triggerType": "...",
    ...
    "rationale": "...",
    "suggestedNarrativeAngle": "..."
  }
}
```

三个差异：
1. **外层键名不同**：§5.3 用 `"decision"`，§5.4 用 `"evaluation"`
2. **字段层级不同**：`rationale` 和 `suggestedNarrativeAngle` 在 §5.3 中位于顶层，在 §5.4 中位于 `evaluation` 对象内部
3. **§5.3 声明"所有"**，但场景2-7确实使用 `"decision"`（与 §5.3 一致），仅场景1使用 `"evaluation"`

场景1之所以特殊——是为了与 世界规则引擎 §4.2 的输出解析器（期望 `"evaluation"` 键）兼容。但 §5.3 的"所有轻量评估共享以下外层结构"声明因此不准确。

**后果**：实现者在阅读 §5.3 后可能会为场景1也构建 `"decision"` 结构 → 世界规则引擎解析失败 → 回退降级策略。

**修改建议**：在 §5.3 的统一结构声明中增加例外说明：

```
所有轻量评估共享以下外层结构（场景1除外——场景1使用 "evaluation" 作为外层键，
以兼容世界规则引擎 §4.2 的输出解析器）：
```

### 🔴 问题3：§4.1 模板规则中变量名不一致 —— `${event.name}` 未定义

**涉及文档**：Agent §4.1 内部

**矛盾描述**：

Agent §4.1 定义了 `EventProximity` 数据类：

```kotlin
data class EventProximity(
    val eventName: String,        // ← 字段名为 eventName
    val distanceInRegions: Int,
    val propagationProb: Float
)
```

模板规则优先级1使用了未定义的变量名：

```kotlin
// 优先级1：致命威胁（立即警报）
if (eventProximities.any { it.distanceInRegions <= 1 && it.propagationProb > 0.5 }) {
    return "⚠️ ${event.name}已逼近至邻区！"     // ← 应为 ${event.eventName}
}
```

优先级4正确使用了 `eventName`：

```kotlin
return "${approachingEvent.eventName}仍在${approachingEvent.distanceInRegions}个区域外"
```

**后果**：代码实现时优先级1模板将输出空字符串或编译错误（取决于 Kotlin 模板引擎实现方式）。纯 Kotlin 字符串模板会在编译时报错。

**修改建议**：将优先级1中的 `${event.name}` 改为 `${event.eventName}`。

### 🔴 问题4：§7 调用链图中加速模式的数据流缺失中间步骤

**涉及文档**：Agent §7 vs V3.0 总纲 §3.3

**矛盾描述**：

Agent §7 调用链图：

```
加速模式：
  玩家选择"加速" → 模板引擎本地循环（<1ms 状态栏刷新）→ UI 时间流摘要面板
  玩家选择"恢复正常" → 世界叙事Agent云端调用（最终摘要 5-15s）→ 叙事Agent（初始场景叙事）→ UI
```

V3.0 总纲 §3.3 步骤 4-5 实际描述了更多步骤：

```
4. 世界规则引擎标记为追赶模式——不逐日连续结算
5. 世界叙事Agent采用双模架构
...
7. UI从suggestions面板切换为时间流摘要面板
```

Agent §7 缺失的关键步骤：
- **批量追赶结算**："恢复正常"后、云端调用前，世界规则引擎执行批量追赶结算（V3.0 总纲 §3.3 步骤4）。Agent §7 跳过了这一步，直接从"恢复正常"到"云端调用"
- **自动导航报告生成**：加速期间的自动导航结果需要先收集汇总，再作为云端调用的输入

正确的调用链应为：

```
玩家选择"恢复正常" 
  → 世界规则引擎批量追赶结算（N个游戏日的资源更新+冲突判定+事件传播）
  → NPC行为系统批量追赶（NPC需求+互动+离开判定）
  → 收集自动导航报告
  → 世界叙事Agent云端调用（输入：批量结算结果 + 本地摘要序列 + 自动导航报告 + 当前场景）
  → 叙事Agent（初始场景叙事）
  → UI
```

**后果**：开发者按 Agent §7 的调用链实现，可能遗漏批量追赶结算步骤，导致世界叙事Agent 的输入数据不完整。

**修改建议**：在 Agent §7 加速模式流程中补充"世界规则引擎批量追赶结算"和"收集自动导航报告"两步。

### 🟡 问题5：§4.1 ExpectedChanges "计算一次"与模板去重机制的语义矛盾

**涉及文档**：Agent §4.1 内部

**矛盾描述**：

Agent §4.1 描述：

> 输入数据结构（由世界规则引擎在加速开始时**计算一次**，模板引擎定时读取）

模板去重规则（Agent §4.1）：

> 模板去重：若本轮生成的文本与 `previousTemplateText` 完全相同，追加"（持续中）"后缀

`ExpectedChanges` 数据类包含：

```kotlin
val previousTemplateText: String? // 上一轮模板文本（用于去重）
```

矛盾在于：
- "计算一次"意味着 `ExpectedChanges` 对象在世界规则引擎侧创建后不再更新
- `previousTemplateText` 需要在**每一轮**模板生成后更新（上一轮的输出 → 下一轮的输入）
- 如果 `ExpectedChanges` 真的只"计算一次"，`previousTemplateText` 永远是初始值 `null`，去重永远不会触发

实际实现中，`previousTemplateText` 应由模板引擎自身管理（每次 `generate()` 后更新），而非依赖世界规则引擎重新计算。描述"由世界规则引擎在加速开始时计算一次"应明确排除 `previousTemplateText` 字段，或标注此字段由模板引擎自身维护。

**修改建议**：将 §4.1 描述改为：

```
输入数据结构（除 previousTemplateText 外，由世界规则引擎在加速开始时计算一次。
previousTemplateText 由模板引擎每次生成后自行更新，用于下一轮去重判断。）
```

### 🟡 问题6：§4.2 云端阶段输入中"遭遇威胁"报告格式完全未定义

**涉及文档**：Agent §4.2 vs V3.0 总纲 §3.3

**矛盾描述**：

Agent §4.2 User Message 结构中：

```
【自动导航报告】：
- 生命值：当前/最大
- 饱食度/口渴度：当前值
- 消耗的势力资源：[势力名称] 食物 -X 人口天，水 -Y 人口天
- 使用医疗物资：背包 X 个 / 势力 Y 次
- 遭遇威胁：[威胁描述]（如有）
```

V3.0 总纲 §3.3 自动导航规则中：

> 若遭遇致命威胁→尝试逃跑

两份文档都没有定义"遭遇威胁"的数据结构。对比其他字段的精确度：
- 生命值：`当前/最大` ← 有明确的数值格式
- 消耗的势力资源：`[势力名称] 食物 -X 人口天，水 -Y 人口天` ← 有明确的计量单位
- 遭遇威胁：`[威胁描述]（如有）` ← 完全自由文本，无结构

这导致两个问题：
1. 自动导航代码不知道如何生成威胁报告（什么算"威胁"？如何描述？）
2. 世界叙事Agent 的 System Prompt 没有指导如何将威胁描述融入最终摘要

**修改建议**：在 V3.0 总纲 §3.3 或 Agent §4.2 中定义威胁报告的最小结构：

```
遭遇威胁：
- 威胁类型：[丧尸/敌对NPC/自然灾害/...]
- 威胁等级：[轻度/中度/致命]
- 处理结果：[成功逃跑/受伤逃脱/...]
- 消耗：[如有额外消耗]
```

### 🟡 问题7：§5.4 场景1新增字段与 世界规则引擎 §4.2 解析器的兼容性未声明

**涉及文档**：Agent §5.4 vs 世界规则引擎 §4.2

**问题描述**：

Agent §5.4 场景1输出在 `evaluation` 对象内部新增了两个字段：

```json
{
  "evaluation": {
    ...原有字段...,
    "rationale": "一句话说明决策依据（≤50字）",           // ← 新增
    "suggestedNarrativeAngle": "一句话叙事建议（≤50字）"   // ← 新增
  }
}
```

世界规则引擎 §4.2 定义的输出结构不含这两个字段。

大多数 JSON 解析库（Gson、Moshi、kotlinx.serialization 默认配置）会忽略未知字段，兼容性通常不是问题。但以下情况可能触发解析失败：
- 若世界规则引擎使用严格的 JSON Schema 校验（如 `additionalProperties: false`）
- 若解析器配置为 `ignoreUnknownKeys = false`

第一次审查的问题1（键名 `"decision"` vs `"evaluation"`）已修复，但新增字段的兼容性未被讨论。

**修改建议**：在 Agent §5.4 末尾或世界规则引擎 §4.2 中增加兼容性声明：

```
世界规则引擎的 AI 输出解析器需配置为忽略未知 JSON 字段
（如 Gson 默认行为，或 kotlinx.serialization 的 ignoreUnknownKeys = true）。
Agent 配置规范可能在 evaluation 对象中新增辅助字段（如 rationale），
解析器不应因新增字段而失败。
```

### 🟢 问题8：§4.2 System Prompt 中 `notableChanges` 类型仅示例了 2 种

**涉及文档**：Agent §4.2

**问题描述**：

Agent §4.2 System Prompt 输出格式中 `notableChanges` 的示例：

```json
"notableChanges": [
  {"type": "npc_death", "detail": "哨兵老张因伤口感染去世"},
```

### 🟢 问题9：§4.4 云端降级 JSON 中 `playerStatus` 字段的降级默认值未逐字段定义

**涉及文档**：Agent §4.4

**问题描述**：

Agent §4.4 云端阶段降级 JSON：

```json
{
  "timeMarker": "[当前时间]",
  "summary": "时间加速流逝。当你回过神来，世界已经悄然改变。",
  "notableChanges": [],
  "playerStatus": {...},
  "final": true
}
```

`"playerStatus": {...}` 使用了省略号，未指定各字段的降级默认值。对比正常输出的 `playerStatus` 结构：

```json
"playerStatus": {
  "hp": 85, "hunger": 40, "thirst": 35,
  "consumedFactionResources": "...",
  "injuriesHealed": [],
  "injuriesSustained": []
}
```

降级时，`playerStatus` 中的数值字段（hp/hunger/thirst）应该从客户端获取（自动导航报告仍在本地生成，不依赖 AI），而非留空。`consumedFactionResources` 同理——这些数据在 AI 调用前已经确定。

**修改建议**：明确降级时 `playerStatus` 的各字段来源：

```
降级时，playerStatus 中的 hp/hunger/thirst/consumedFactionResources/injuriesHealed/injuriesSustained 
仍从自动导航报告（客户端本地数据）中填充，仅 summary 和 notableChanges 使用降级默认值。
```

## 四、设计质量正面评价

本次审核中观察到以下设计选择值得肯定：

### 4.1 双模架构的根本性解决方案

Agent §4 的双模架构不是对"每3秒摘要"的修补（如增加间隔到15秒），而是从根本假设上重新设计——将实时性要求交给客户端模板引擎（<1ms），将质量要求留给单次云端调用（5-15s）。这个设计消除了整个类别的延迟问题，同时保持了叙事质量。

### 4.2 验证规则的逐场景完整性

Agent §5.4 的代码验证规则（target 校验、attribute 校验、change clamp、newEntities 限制）和 Agent §5.11 的通用验证规则（枚举校验、数值 clamp、空字符串回退）共同构成了完整的 AI 输出安全网。每个场景都有对应的降级默认值。

### 4.3 降级策略的渐进式设计

Agent §5.12 的降级策略体现了"逐步收紧"的思路：
- 单次降级：使用默认值
- 场景3特殊处理：检查历史 spare 记录防止免疫
- 连续5次降级 → 暂停该场景24游戏小时

这种分层降级避免了 API 不稳定时系统的两种极端——既不会让关键NPC 获得事实性免疫，也不会让失败调用无限重试。

### 4.4 三份主文档的对齐更新

Agent 配置规范的编写不是孤立行为——同步推动了 V3.0 总纲 §3.3、总纲 §6.1、世界规则引擎 §3.3 的更新，四份文档形成了可相互验证的网络。
