## 一、结论摘要

**结论：当前核心流程不能视为“已闭合”。** 现有 337 个测试全绿，但测试主要覆盖单函数/单次流程，缺少重启、跨午夜、加速退出、并发和“真实可达性”用例。本次清单共 **2 个 P0、10 个 P1、12 个 P2**；其中**真正新增的是 2 个 P0 + 4 个 P1**，其余 P1/P2 多为 2026-10-17 旧账未清，或旧报告已接受项的扩大化（见第十节的分诊）。

最严重的两条：

1. **NPC 需求/伤病只增不减**：所有接触 NPC 会在约第 4 次每日结算内饿死/渴死/伤重而死，场景 2/5/6 的对象迅速消失。
2. **每日结算账本只存在内存**：进程重启后 `lastMidnightSettlementDay` 回到 1，第一次主线行动会按 `currentDay - 1` 重放整日结算，造成不可逆的世界状态损坏；加速退出还会与批量追赶重复计数。

旧闭合声明中有 7 项与现状不符，见第六节。建议先做 P0 止血，再按“时间/结算 → NPC 接线 → 死亡/加速/输入 → 持久化”分四批修复，每批 TDD、小 diff。

## 二、核心链路与检查结论

| 流程 | 真实入口 | 本次结论 |
|---|---|---|
| 开局/初始化 | `MainActivity` → `GameViewModel.initializeGameV22` → `OpeningModule.prepare` | 成功路径可用；无事务、无重复点击保护，半初始化可卡死；新局清档不完整 |
| 主线行动 | 建议项带 `ActionParsed` → `GameRepository.processMainline` | 阶段顺序正确；但跨午夜结算异步、与同轮 prompt/persist 并发；死亡链路只完成检测 |
| 支线行动 | 自由文本 → `GameViewModel.sendAction(action, null)` → `processBranch` | 只推进时间，不做每日结算、不查死亡；自定义输入的主要路径 |
| 加速 | 三档速度 chip → `enterAcceleration/advanceAcceleration/exitAcceleration` | 不结算、不判死、不落玩家/V3；ACCEL→DECEL 绕过收尾；加速期间仍可发送行动 |
| 每日结算 | 主线跨午夜 → `repositoryScope.launch { repeat(pendingDays) { executeDailySettlement() } }` | 账本不持久化；fire-and-forget；游标先推进后执行；V3 多协程裸读写 |
| NPC 提取/模拟 | `syncGameData` / `tryV3NpcExtraction` → `npcRuntime` → `executeDailySettlement` | 需求只增不减导致团灭；KEY 层级无生产路径；位置用自由文本而非 regionId；场景 3 不可达、场景 5 过触发 |
| 死亡 | 主线致死 → `PlayerDied` → `DeathOverlay` | 死亡不持久化；读档/观察是空操作；继承不落库；支线/加速/重启都不判死 |
| 持久化 | `syncGameData` → 多 DAO；`persistV3State` → V3 五表事务 | V2 五表无事务；V3 快照浅拷贝、异步落库；场景回调可能晚于 persist |

## 三、P0 问题（存档/模拟核心）

### P0-1 NPC 需求与伤病只增不减，所有 NPC 约第 4 次每日结算死亡

- **位置**：`domain/npc/engine/NpcBehaviorEngine.kt:24-58`、`data/repository/GameRepository.kt:1350-1360`
- **证据**：
  - `advanceNeeds` 每日固定 `food +120`、`water +192`，`min(100, ...)` 封顶；`medical` 受伤时 `+360`。
  - `checkNeedOverloadDeath` 在 `consecutiveSaturatedFoodDays >= 3` 等条件返回死亡。
  - 全仓只有初始化、每日增加、DB 映射三类 `foodUrgency/waterUrgency/medicalUrgency` 写入，**没有任何减少/进食/饮水/治疗路径**；NPC 的 `statusTags` 也没有移除“受伤”的路径。
- **触发/复现**：新档提取任意 NPC，连续 4 次跨午夜结算。初始 30–70 → 第 1 次结算变 100，计数 0；第 2/3/4 次计数 1/2/3，第 4 次结算 `starvation` 标记 `DEAD`。若初始已 100，则第 3 次死亡；受伤 NPC 同样在第 4 次左右因 `medical 100` 死亡。
- **影响**：
  - 所有接触 NPC 在数个游戏日内团灭；场景 2/5 失去对象，`npcRuntime` 只增不减地积累 `DEAD`。
  - 需求 >90 触发的 `EXPLORING` 预期归来日是 `D+3`，但 NPC 在第 4 次结算（约 `D+3`）已死，场景 6 的超时判定要到 `D+4`，**场景 6 基本不可达**。
  - 同名 NPC 死亡后仍占用 `npcIdForName`，同名再提取永久早退（旧清单 A2 已接受的身份策略，在这里被放大为系统性问题）。
- **测试缺口**：`GameRepositorySettlementIntegrationTest` 只跑 2 次结算；`NpcBehaviorEngineTest` 只构造 `consecutive=2`，没有任何 5 日全流程测试。
- **最小修复方向**：先产品决策——要么实现“按势力/区域/玩家资源每日满足需求并清除伤病”，要么在满足模型落地前**禁用需求致死**（保留需求值用于叙事）。同时把连续饱和计数纳入 V3 持久化（见 P2）。补“5 日结算 NPC 仍存活/按规则死亡”的真 Room 集成测试。

### P0-2 每日结算账本只在内存，重启后重放 `N-1` 天

- **位置**：`data/repository/GameRepository.kt:1179`、`:352-357`、`:706`、`:816`、`:1035`
- **证据**：
  - `var lastMidnightSettlementDay: Int = 1`，构造即 1；只在 `resetV3World()` 置 1，全仓没有任何 DB/Prefs 读写。
  - 每次主线：`pendingSettlementDays(lastMidnightSettlementDay, sm.clock.currentDay)` → `lastMidnightSettlementDay = currentDay` → `repositoryScope.launch { repeat(pendingDays) { executeDailySettlement() } }`。
  - `seedStateMachine` 从 `world.totalGameMinutes` 恢复 `currentDay`；`syncGameData` 每次行动都把 `totalGameMinutes` 落库。
- **触发/复现**：玩到第 N 天（N≥2）→ 杀进程/系统回收 → 重开（`DependencyContainer` 是进程级单例，新 repo 账本回 1）→ 点任意带 `ActionParsed` 的建议。第 10 天重开 = 一次补 9 个整日结算；第 30 天 = 29 个。
- **影响**：每次重启都额外推进 `N-1` 天——扣势力资源、推进 NPC 需求/致死、战斗、事件过期/传播、随机事件、场景 1 AI。不可逆（V3 表被覆盖，无结算历史）；天数越大越严重。加速退出后批量追赶又未推进账本，下一次主线会把同一段天数再结算一次（见 P1-2）。
- **测试缺口**：`GameRepositoryTest.kt:349-353` 只测纯函数；`:495/:517/:548` 在模拟第 2 天时**手工把账本设为 2** 来绕过结算，正好说明没有重启用例。
- **最小修复方向**：把“已结算到第几天”持久化（`WorldInfo` 加列并迁移，或稳定的 Prefs 键），启动时从存档恢复；**结算成功后再推进账本**；加速退出同步推进账本或直接走统一 `advanceTime`。补“第 N 天重开→首行动不额外结算”的真 Room 回归测试。

## 四、P1 问题（正确性/数据/可达性）

### P1-1 每日结算 fire-and-forget，与同轮 prompt/持久化并发

- **位置**：`GameRepository.kt:355-357`、`:378-383`、`:953-954`、`:1007-1023`、`:1164-1174`
- **证据**：结算在 `repositoryScope.launch` 中执行且不 `await`；随后立即 `buildV3WorldProgressString`/`buildV3NpcDepthContext` 读取活的 `factions/regions/activeEvents/npcRuntime`；`v3Mutex` 只包结算与结算之间，`persistMutex` 只串行 save，`snapshotV3State()` 的 `toList()/toMap()` 是浅拷贝。
- **影响**：本轮 prompt 可能读到“资源已扣、事件未并、NPC 需求已推进”的混合状态；`persistV3State` 或结算遍历可抛 `ConcurrentModificationException`（异常被 `Log.e` 吞掉则整次 V3 落库丢失）；`syncGameData` 与 `resolveNpcSettlement` 对同一 `NpcRecord` 的读改写可互相覆盖。结算协程没有异常处理器，异常逃逸可能走 Android 默认未捕获异常路径。
- **测试缺口**：没有并发、异常回滚或“结算完成后再构建 prompt”的测试。
- **最小修复方向**：跨午夜结算改为同轮 `await` 完成后再构建 prompt；所有 V3 读改写收敛到单写者/Mutex；持久化用深拷贝快照；逐日 `try/catch`，成功后才推进账本。

### P1-2 支线与加速推进时间却完全不进每日结算

- **证据**：`processBranch` 只调 `sm.processBranchAction(minutes)`（时钟 + 天气 + 被动消耗 + 每小时伤病），没有 `pendingSettlementDays`/`executeDailySettlement`；`advanceAcceleration` 同样只做时钟 + 被动消耗 + 伤病 tick。

### P1-8 `estimatedTimeMinutes` 完全未钳制

- **位置**：`SurvivalStateMachine.kt:89-97`、`GameClock.kt:49-52`、`ActionParsed.kt:14`、`GameResponseValidator.kt:41-50`、`PromptBuilder.kt:713`
- **证据**：建议项的 `estimatedTimeMinutes` 直接来自叙事 AI 的 JSON，`GameResponseValidator` 只检查 `actionParsed` 对象存在，不校验数值；`sm.processPreRuling(actionParsed.estimatedTimeMinutes, ...)` 直接 `clock.advance`，`GameClock.advance` 只 `require(minutes >= 0)`。

### P1-9 `syncGameData` 跨 V2 五表无事务，AI 缺字段可造成“player 已写、world 抛 NPE”

- **位置**：`GameRepository.kt:789-875`、`:953-954`；`GameResponseValidator.kt:28-33`
- **证据**：`syncGameData` 依次写 `playerDao`/`worldDao`/`inventoryDao`/`memoryDao`/`npcDao`，没有 `database.withTransaction`（全仓跨表事务只在 `V3WorldStateStore`；`InventoryDao.syncInventory` 只是单表 `@Transaction`）；Validator 只要求 `statusUpdate.world` 是对象，不要求 `macroSituation`/`innerThought`。Gson 的 Unsafe 反序列化会让缺失的非空 `String` 实际为 null；`oldWorld.copy(macroSituation = update.world.macroSituation)` 可能在 player 已写之后抛 NPE。
- **触发/复现**：AI 返回 `"statusUpdate":{"world":{}...}` 或省略 `macroSituation` → player 已提交，world copy 抛 NPE；或任一 DAO 抛 SQLite/磁盘异常；或进程在两次写之间被杀。重试会再次推进时间/消耗，产生重复扣减。
- **影响**：HP/时间已落库、世界/背包/记忆/NPC 半套；下一轮 seed 出现“吃了食物但背包没扣”“NPC 好感丢失”；旧闭合声明“多表落库整体事务”只对 V3 五表成立。
- **最小修复方向**：用 `database.withTransaction` 包住 V2 五表写入（V3 保存也纳入同一事务/串行队列）；Validator 对 `innerThought`/`macroSituation`/`knownPoints` 做必填或默认值；补“world 缺字段/DAO 中途抛错”的故障注入测试。

### P1-10 伤病数值效果未接线：`hpLossPerHour` / `calculateSpPenalty` 无调用者

- **位置**：`domain/state/HealthSystem.kt:71-79`、`:88-110`；`SurvivalStateMachine.kt:96`、`:219`；`GameRepository.kt:1508-1511`
- **证据**：`HealthSystem.tickHourly()` 只做自然恢复倒计时和感染风险 +0.05，不扣 HP；`calculateHourlyHpLoss()` 和 `calculateSpPenalty()` 全仓没有调用者；`checkInfection()` 只在主线 `applyActionResult` 调用。
- **触发/复现**：玩家受“重伤/感染性休克”等 `hpLossPerHour > 0` 的伤病，连续行动/休息多个小时 → HP 不变；SP 消耗也不受 `spPenalty` 影响；支线/加速把感染风险累到 1.0 也不转脓毒症。HP 只能靠裁决 AI 显式在 `resourceChanges` 里扣。

- **测试缺口**：`HealthSystemTest` 只测恢复倒计时/感染风险；`InjuryLibraryTest` 只查 `hpLossPerHour` 的最大值，没有“伤病实际扣 HP/SP”的测试。
- **最小修复方向**：在统一 `advanceTime` 的每小时切片里调用 `calculateHourlyHpLoss()` 扣 HP（并 clamp、触发死亡检查），把 `calculateSpPenalty()` 接入 `applyActionCost`，每个切片后跑 `checkInfection()`；补“重伤 24h 扣 HP/感染转休克”的行为测试。
