## 一、冲突 1：场景 3 `outcome` 取值与规范不一致（Task 2，已提交）

### 1.1 三方对照

| 来源 | 内容 | 位置 |
|---|---|---|
| 计划 Review Focus #3 | 「场景 3 判定 `dead` → NPC 标记 DEAD，不再参与后续结算」 | `doc/plans/2026-10-18-第三批B-域信号.md:28` |
| 计划 Task 2 代码 | `if (outcome == "dead") { ... DEAD ... }` | 计划 `:257`；实际 `GameRepository.kt:1293-1295` |
| Agent 配置规范 §5.6 | `"outcome": "kill" \| "spare" \| "severe_injury"` | `doc/v3/V3.0 Agent 配置规范 V1.0.md:525` |
| Agent 配置规范 §5.6 模板 | 要求输出完整决策 JSON（含 `narrativeHint`、`rationale`、`suggestedNarrativeAngle`） | 同文件 `:516-531` |
| 实际 PromptBuilder | 只有一句「请判定该关键NPC是否死亡」，**没有输出 schema** | `PromptBuilder.kt:1029-1032` |

### 1.2 后果

- 如果模型按规范输出 `outcome: "kill"`，`evaluateScene3` 不会命中 `"dead"`，NPC **永远不会**被标记 `DEAD`；Review Focus #3 的验收实际失败。
- 如果模型碰巧输出 `"dead"`，则与 §5.6 的 schema 不一致；而 Prompt 里根本没有约束字段名，输出不可控。
- 这与 2026-10-18 已验证过的场景 2 缺陷同类：**提示词缺 `decision` 输出 schema → 模型输出自由文本/错误字段 → 校验失败静默降级**。场景 3 目前没有任何「输出要求」兜底。
- 现有 253 个测试只覆盖 `detectKeyNpcCasualty` 纯函数，**没有覆盖 `evaluateScene3` 的 JSON → 状态映射**，所以套件全绿但行为不可用。

### 1.3 候选修复

| 方案 | 改动 | 测试数 | 说明 |
|---|---|---|---|
| **A1. 对齐设计规范（推荐）** | PromptBuilder 补 §5.6 输出 schema（`kill/spare/severe_injury` + `narrativeHint`）；代码改判 `kill`；`severe_injury` 追加「重伤」标签；抽出纯映射函数并补测试 | 约 257-258 | 与 Spec 一致；改动 `PromptBuilder.kt` + `GameRepository.kt`，属计划外文件 |
| A2. 保留 `dead` | PromptBuilder 明确要求 `outcome: "dead"`，代码不动 | 约 256 | 改动最小，但与 §5.6 规范不一致，后续接场景 4 连锁时会产生语义分叉 |
| A3. 兼容双 token | 代码同时接受 `kill` / `dead`；PromptBuilder 补 schema | 约 257 | 兼容性最好，但长期保留两个死亡 token，容易再踩 |

## 二、冲突 2：场景 6 每天重复评估 + 绝对日 3（Task 3，未接线）

### 2.1 计划要求

- Review Focus #4（计划 `:30`）：「外出 NPC 超过预期归来日 → 标记 MISSING，**只评估一次**」。
- Task 3 Step 2（计划 `:325-355`）：在 `resolveNpcSettlement` 的 `shouldDepart` **之后**读 `npcDepartures[npcId]`，命中超时则改 `MISSING` 并异步评估场景 6。
- 计划预期终态 **255 tests / 0 failed**（只新增 2 个检测器测试，接线本身无测试）。

### 2.2 现有生产者行为

`NpcBehaviorEngine.shouldDepart`（`app/src/main/java/com/ei8z/endworld/domain/npc/engine/NpcBehaviorEngine.kt:235-241`）：

```kotlin
if (needs.foodUrgency > 90 || needs.waterUrgency > 90) {
    return DepartureInfo(
        DepartureStatus.EXPLORING,
        reason = "寻找物资",
        expectedReturnDay = 3 // 最多3天
    )
}
```

`resolveNpcSettlement`（`GameRepository.kt:1352-1355`）**每个游戏日、对每个 NPC 无条件调用** `shouldDepart`，非 null 就覆盖 `npcDepartures`：

```kotlin
val dep = engine.shouldDepart(npc, newNeeds, npcAffinities[npcId] ...)
if (dep != null) npcDepartures[npcId] = dep
```

两个问题叠加：

1. `expectedReturnDay` 写死为**绝对游戏日 3**，而设计文档语义是「从离队起最多 3 游戏日」。第 4 天以后首次外出，`currentDay > 3` 会在离队当天立刻判超时。
2. 食物/水需求 >90 时，`shouldDepart` 每天都会返回新的 `EXPLORING`，把前一天写入的 `MISSING` **覆盖回 EXPLORING**；下一天超时检测再次命中。场景 6 因此每天评估一次，直到需求连续饱和 3 天死亡为止（最多 3 次）。

### 2.3 实测证据

一次性探针（`TimeoutProbeTest`，已删除，未进任何提交）复刻「shouldDepart → detectDepartureTimeout」的每日循环，从第 10 天开始、需求 food=95：

```kotlin
for (day in 10..11) {
    engine.shouldDepart(...)?.let { departure = it }          // 每天覆盖回 EXPLORING
    val trigger = SceneTriggerDetector.detectDepartureTimeout("n1", departure!!, day)
    if (trigger != null) {
        triggerDays += day
        departure = departure!!.copy(status = MISSING, reason = "超时未归")
    }
}
assertEquals(listOf(10), triggerDays)   // 期望：只评估一次
```

实际运行结果：

```text
TimeoutProbeTest > probe scene 6 repeats every day FAILED
java.lang.AssertionError: expected:<[10]> but was:<[10, 11]>
```

### 2.4 影响

- Review Focus #4 的「只评估一次」不成立；每日结算会重复调用轻量 AI（场景 6），产生额外 token 成本与竞态写 `pendingSceneNotes`。
- 第 4 天以后第一次外出就判超时，NPC 的"外出探索"实际从未获得 3 天窗口。
- 计划给出的 255 个测试只覆盖 `detectDepartureTimeout` 纯函数，**不覆盖 `resolveNpcSettlement` 的每日循环**，所以按计划接线后套件仍会 255 全绿，问题不可见。

### 2.5 设计文档依据

`doc/v3/NPC自主行为系统详细设计 V1.0.md`：

- `:495`：「外出探索｜NPC需求驱使其外出（如寻找物资）｜NPC暂时离开，预期归来时间≤3游戏日」
- `:515`：「超时未归 → 标记为"失踪"，触发轻量AI评估判定结果：死亡/被俘/加入其他势力/重伤返回」
- `:516`：「失踪NPC的接触层数据保留7天」

`doc/v3/V3.0 Agent 配置规范 V1.0.md` §5.9（`:596` 起）同样是「外出探索超过 3 游戏日未归」的**相对时长**语义。

### 2.6 候选方案

| 方案 | 改动 | 测试数 | 风险 / 说明 |
|---|---|---|---|
| **A. 严格按计划原样接线** | 只在 `resolveNpcSettlement` 加计划片段；不动 `NpcBehaviorEngine` | 255 | 与计划逐字一致、无设计变更；但重复触发与绝对日语义保留，Review Focus #4 实际不成立，需作为遗留缺陷记录 |
