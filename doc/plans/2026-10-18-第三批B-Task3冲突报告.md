### 2.2 现有生产者行为

`NpcBehaviorEngine.shouldDepart`（`app/src/main/java/com/ei8z/endworld/domain/npc/engine/NpcBehaviorEngine.kt:235-241`）：

```kotlin
if (needs.foodUrgency > 90 || needs.waterUrgency > 90) {
    return DepartureInfo(
        DepartureStatus.EXPLORING,
        reason = "寻找物资",
        expectedReturnDay = 3 // 最多3天
    )
}
```

`resolveNpcSettlement`（`GameRepository.kt:1352-1355`）**每个游戏日、对每个 NPC 无条件调用** `shouldDepart`，非 null 就覆盖 `npcDepartures`：

```kotlin
val dep = engine.shouldDepart(npc, newNeeds, npcAffinities[npcId] ...)
if (dep != null) npcDepartures[npcId] = dep
```

两个问题叠加：

1. `expectedReturnDay` 写死为**绝对游戏日 3**，而设计文档语义是「从离队起最多 3 游戏日」。第 4 天以后首次外出，`currentDay > 3` 会在离队当天立刻判超时。
2. 食物/水需求 >90 时，`shouldDepart` 每天都会返回新的 `EXPLORING`，把前一天写入的 `MISSING` **覆盖回 EXPLORING**；下一天超时检测再次命中。场景 6 因此每天评估一次，直到需求连续饱和 3 天死亡为止（最多 3 次）。

### 2.3 实测证据

一次性探针（`TimeoutProbeTest`，已删除，未进任何提交）复刻「shouldDepart → detectDepartureTimeout」的每日循环，从第 10 天开始、需求 food=95：

```kotlin
for (day in 10..11) {
    engine.shouldDepart(...)?.let { departure = it }          // 每天覆盖回 EXPLORING
    val trigger = SceneTriggerDetector.detectDepartureTimeout("n1", departure!!, day)
    if (trigger != null) {
        triggerDays += day
        departure = departure!!.copy(status = MISSING, reason = "超时未归")
    }
}
assertEquals(listOf(10), triggerDays)   // 期望：只评估一次
```

实际运行结果：

```text
TimeoutProbeTest > probe scene 6 repeats every day FAILED
java.lang.AssertionError: expected:<[10]> but was:<[10, 11]>
```

### 2.4 影响

- Review Focus #4 的「只评估一次」不成立；每日结算会重复调用轻量 AI（场景 6），产生额外 token 成本与竞态写 `pendingSceneNotes`。
- 第 4 天以后第一次外出就判超时，NPC 的"外出探索"实际从未获得 3 天窗口。
- 计划给出的 255 个测试只覆盖 `detectDepartureTimeout` 纯函数，**不覆盖 `resolveNpcSettlement` 的每日循环**，所以按计划接线后套件仍会 255 全绿，问题不可见。

### 2.5 设计文档依据

`doc/v3/NPC自主行为系统详细设计 V1.0.md`：

- 第 495 行：「外出探索｜NPC需求驱使其外出（如寻找物资）｜NPC暂时离开，预期归来时间≤3游戏日」
- 第 515 行：「超时未归 → 标记为"失踪"，触发轻量AI评估判定结果：死亡/被俘/加入其他势力/重伤返回」
- 第 516 行：「失踪NPC的接触层数据保留7天」

`doc/v3/V3.0 Agent 配置规范 V1.0.md` §5.9（第 596 行起）同样是「外出探索超过 3 游戏日未归」的**相对时长**语义，且场景 6 的输出 schema 自带 `outcome` 字段（`death` / `captured` / `joined_other_faction` / `return_injured`）。

## 三、候选方案

| 方案 | 改动 | 测试数 | 风险 / 说明 |
|---|---|---|---|
| **A. 严格按计划原样接线** | 只在 `resolveNpcSettlement` 加计划片段；不动 `NpcBehaviorEngine` | 255 | 与计划逐字一致、无设计变更；但上述重复触发与绝对日语义保留，Review Focus #4 实际不成立，需作为遗留缺陷记录 |
| **B. 最小修正（推荐）** | ① `shouldDepart` 增加 `currentDay` 参数，`expectedReturnDay = currentDay + 3`；② 已非 `PRESENT` 的 NPC 不再重新生成离队状态；③ 补引擎测试与"只评估一次"测试 | 约 257 | 行为符合设计文档与 Review Focus；代价是偏离计划文件列表（改 `NpcBehaviorEngine.kt` + 其测试），且 `shouldDepart` 只有一个调用点，改动可控 |
| **C. 只加"已离队不重派"护栏** | 保留 `expectedReturnDay = 3`，只在 `npcDepartures[npcId]` 非 `PRESENT` 时跳过 `shouldDepart` | 约 256 | 能保证只评估一次；但第 4 天以后首次外出仍在当天超时，"≤3游戏日"依旧错误 |

> 方案 B 的 ② 会改变"已离队 NPC 次日重新离队"的现有行为。现状下 `MIGRATED/EXPLORING/MISSING` 每天都会被 `shouldDepart` 覆盖，本来就没有"归来/失踪保留"逻辑，因此该护栏更接近设计意图，但属于计划外改动。
